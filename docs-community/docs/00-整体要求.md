## 1. 项目定义

### 1.1 定位

基于 [HMCL](https://github.com/HMCL-dev/HMCL) 做一个**社区版 Minecraft 启动器**，具备独立产品身份，面向中国大陆用户。

### 1.2 三条核心约束

| # | 约束 | 含义 |
|---|---|---|
| 1 | **中国大陆用户可用** | 下载链路在大陆可用，且用户可自主配置源；不依赖上游服务器可达 |
| 2 | **独立产品身份** | 独立名称/图标/版本号/更新源，不与官方混淆；GPLv3 与附加条款合规 |
| 3 | **自身改动相对固定** | 长期只合并上游，代码侵入点保持固定并逐项登记，不做大规模重构 |

> MD3 / 莫奈取色**不再列为核心约束**：上游已提供 MonetFX token 体系（`-monet-*` CSS 变量 + `Theme` 接口），我们直接复用即可，见 §1.4。

### 1.3 三条不可动摇的原则

| 原则 | 说明 | 违反后果 |
|---|---|---|
| **GPLv3 合规** | 满足第 7 条附加条款；**不得添加**任何新的附加要求；fork 的 HMCLauncher 同样适用 | 法律风险，必须返工 |
| **改动外挂优先** | 新功能放新 package，不碰上游现有文件 | 同步成本失控，项目不可持续 |
| **绝不阻断启动** | 任何增强功能失败都必须**静默降级**，游戏照常启动 | 直接违背产品承诺，视为 P0 缺陷 |

第三条是硬约束，贯穿所有功能设计——体检失败、内存优化失败、快照失败、守护进程不可用，一律继续启动。

### 1.4 差异化方向

**UI 观感不再是差异化卖点。** 上游已具备 MonetFX token 体系（`HMCL/src/main/java/org/jackhuang/hmcl/theme/Themes.java` 的 `ColorScheme`/`ColorRole`（`getColorScheme()` :554）、`root.css` 的 `-monet-*` 变量、壁纸取色），新界面直接复用其 token 即可，不需要自建主题引擎。差异化从"好不好看"转向"好不好用"：

| 方向 | 内容 | 优先级 |
|---|---|---|
| **启动保障** | 启动前体检 / 崩溃现场还原 / 实例快照回滚 | P0（解决"能不能玩上"） |
| **性能优化向导** | Java 发行版偏好 + JVM 参数预设 + 内存优化 | P0/P1（解决"玩得顺不顺"） |
| 首页组件化 | 可自定义首页小组件（挂载在 `MainPage`） | P1（体验加分） |
| MD3 完善 | 跟随上游取色 token，做我们新增界面的视觉收口 | P2（不抢跑） |

## 2. 基座选型（已定案）

### 2.1 结论

**选 HMCL（基线 v3.16.4）。** 加权总分：**HMCL 4.35 / Prism 3.05 / 美西螈 2.70**。

| 维度 | 权重 | HMCL | Prism | 美西螈 | 依据摘要 |
|---|:--:|:--:|:--:|:--:|---|
| 国内下载可用性 | 25% | **5** | 2 | 4 | HMCL 已内建"大陆自动优先 BMCLAPI"；Prism 的 meta 镜像不含 assets |
| UI 改造难度（MD3） | 20% | **4** | 1 | 3 | HMCL 上游已有 MonetFX token；Prism 是 Qt Widgets（用不了 Qt Quick 的 M3 style） |
| CI / 构建复杂度 | 15% | **4** | 1 | 3 | HMCL 单 runner 出全产物；Prism 是 7 配置矩阵 + vcpkg |
| 长期同步痛苦度 | 15% | **4** | 3 | **1** | HMCL 单级同步 + 三模块分层；美西螈两级同步且每周多版 |
| 许可证与合规负担 | 10% | **4** | 3 | **1** | 美西螈混合许可（含 PCL 限制分发内容 + Modrinth 品牌约束） |
| 运行时性能 | 5% | 3 | **5** | 2 | Qt 原生最轻；但启动器内存不影响游戏帧率 |
| 平台覆盖 | 5% | **5** | 4 | 3 | HMCL 多出 FreeBSD、RISC-V、LoongArch、MIPS |
| 中文社区与用户基础 | 5% | **5** | 2 | 4 | HMCL 中文生态最大 |

### 2.2 决定性理由

1. **BMCLAPI 全链路镜像且已自动化**（MC 本体、库、资源、Forge/Fabric）—— 最难自建的部分，HMCL 白送。
2. **三模块分层**（HMCLBoot / HMCLCore / HMCL）—— 新功能可完全外挂。
3. **上游已提供 MonetFX token 体系** —— MD3 方向顺势，非逆流。
4. **单 runner 出全产物** —— exe 是 stub + jar 字节拼接，不依赖目标平台。
5. **平台覆盖最广** —— Win/Linux/macOS/FreeBSD，以及 x86/ARM/RISC-V/LoongArch/MIPS。

补充：Prism 那 5% 的性能优势兑现不了多少 —— 启动器与游戏是两个独立进程，启动器自身内存不影响游戏帧率。

### 2.3 已排除的候选（决策留痕，避免重复讨论）

| 基座 | 排除原因 |
|---|---|
| PCL2 / PCL CE | .NET + WPF，Windows 独占；官方明确不做 Mac 版，PCL CE 的 macOS 仅"交叉编译"，产物无法运行 |
| BakaXL / FluentLauncher | 同上，Windows 独占 |
| MultiMC | 开发基本停滞，要 fork 就 fork 其继任者 Prism |
| **Prism** | Qt Widgets 用不了 Qt 的 M3 style（属 Qt Quick Controls）；官方 QML 重写已放弃（Issue #980 因冲突过多于 2025-05 关闭）；UI 层 367 文件 / 约 4.4 万行；国内无文件级镜像 |
| **美西螈 / Modrinth App** | 混合许可证（桌面包 GPL-3.0-only，但内含 PCL 自定义许可证的 WikiEntries 快照、MIT 的日志查看器，且同步时不得引回 Modrinth 品牌资产）；两级同步且仓库内无 upstream sync workflow；继承 Tauri 的 WebView 病（Issue #421 内存不回收、#422 Linux 崩溃） |
| XMCL | Electron，内存偏重 |

美西螈实测（2026-10-20）：4,250 文件 / 121.76 MB（约 35 MB 为二进制资产）；Rust 496 文件、Vue 531、TS 988；建仓 2026-07-13；551 stars / **95 open issues**。

> **要学的是它的产品思路**（首页组件化、拖拽识别资源、模组版本回滚），**不是 fork 它**。

### 2.4 什么情况下应重新评估基座

出现以下任一情况时，回到本表重新打分：目标用户主转海外；团队具备 Qt/C++ 能力且愿做 MD3 自绘；愿自建国内文件级镜像并长期维护；极度在意启动器自身资源占用（低配常驻）。

### 3.3 条款号标注偏差（知晓即可，实质无影响）

HMCL README 将"必须改名"标为 7(b)/7(c)（不同版本表述略有差异），"保留版权声明"标为 7(b)。对照 GPLv3 原文，二者**同属 7(b)** 允许的类型：7(b)**(0)** 保留法律声明/作者归属 → "不得移除版权声明"；7(b)**(1)** 标记修改版 → "必须改名"。义务本身有效，仅索引不准。

### 3.4 由此推出的重要规则

**GPLv3 7(c)：下游不得添加新的附加要求。** 只能添加"附加许可"（放宽），不能添加"附加要求"（收紧）。

| 可以 | 不可以 |
|---|---|
| 商用、收费 | 添加"禁止商用"条款 |
| 修改、再分发（须同许可证 + 提供源码） | 添加"必须额外署名本项目" |
| 添加放宽性质的许可 | 闭源、更换许可证 |

### 3.5 命名边界

| 方案 | 示例 | 附加条款 | 混淆风险 | 建议 |
|---|---|---|---|---|
| **完全独立名称** | "Kaleido Launcher" | ✅ | 最低 | ⭐ 推荐 |
| 独立名 + 标注来源 | "Nova Launcher——基于 HMCL" | ✅ | 低 | ⭐ 推荐 |
| HMCL + 后缀 | "HMCL-Nova" | ✅ | 中 | 可接受 |
| 仅改版本号 | "HMCL 3.16-community" | ⚠️ 字面合规 | 高 | ❌ |
| 沿用原名 | "HMCL" | ❌ 违反 | 极高 | ❌ |

条款原文是"名称**或**版本号"，只改版本号严格讲字面满足 —— 但这正是条款要避免的情形，**不要钻这个空子**。社区现有 fork 多用 `HMCL-<标识>`，规范但搜索仍会与官方混合。

### 3.6 商标：GPL 不管这一块

开源许可证授予**版权**，不授予**名称权**。HMCL 的附加条款中没有商标条款（未使用 7(b)(3)），即上游未主动主张；但这**不等于可以随意使用其名称**——商标权独立于版权存在，且 "HMCL" 的实际注册状态无法从公开渠道确认。

**结论：正因为状况不明，独立名称最稳妥。**

### 4.3 上游同步方式

**patch 策略（推荐，适用于"固定几处"的现状）**

```bash
# 一次性导出改动（相对基线 tag）
git diff v3.16.4..main > patches/community.patch

# 上游更新时：从干净上游起新分支，重新 apply
git checkout -b build/3.16.5 v3.16.5
git apply patches/community.patch
```

优点：不堆积 merge commit、历史干净、改动可作为独立 patch 被审查。
缺点：需维护 patch 文件，上游大改致 patch 失效时要重新生成。

**merge 策略**：改动超过 20 处或高度分散时改用 merge。CI 的 `sync-upstream.yml` 默认按 merge 实现。

### 4.4 构建与产物（v3.16.4 实测）

- 官方产物：`.exe`（stub + jar 拼接的便携版）、`.jar`、`.sh`（脚本 + jar 拼接）、`.deb`。**没有安装器**，因此不存在"安装版"这一形态。
- 命名分层（本项目约定）：Gradle 工程名/模块目录保持上游 `HMCL`，内部构建产物仍为 `HMCL-<version>.*`（**不改** `archiveBaseName`）；发行时在 `dist/` 重命名为 `LMCL-<version>-<arch>.<ext>`（`arch`：exe=`win-x86`、jar/sh=`any`、deb=`all`）。修改 `Metadata.*` 与 VERSIONINFO 已足够满足 GPLv3 第 7 条的名称区分，无需动构建脚本。
- `HMCLauncher.exe` 实测 **454,144 B**，是 **32 位** C++ 程序（PE `machine=0x14c`）；发行 exe（`LMCL-<version>-win-x86.exe`）= stub 字节 + jar 字节；官方 v3.16.4 实测 jar 恰从偏移 **454,144** 开始（`PK\x03\x04`），stub 内不夹带 zip 条目、尾部补零。stub 只负责找 Java 并 `CreateProcess("java" -jar <自身>)`，**不转发命令行参数**。
- stub 内嵌的是链接器默认最小 manifest：只有 `asInvoker`（`trustInfo`），没有 `longPathAware`/`supportedOS`/DPI 声明。
- Windows stub 的 Java 查找（`HMCLauncher/HMCL/main.cpp` :56-181）：先 `HMCL_JAVA_HOME`（无效即报错），再同目录 `jre-<arch>`；否则收集 `.hmcl\java\windows-<arch>`、`JAVA_HOME`、`%APPDATA%\.hmcl\java\windows-<arch>`、`PATH`、`Program Files` 厂商目录与 `JavaSoft` 注册表，按版本取**最高且 ≥17**。Linux/macOS 的 `.sh` 顺序为 `HMCL_JAVA_HOME` → `jre-*` → `JAVA_HOME` → PATH（FreeBSD 另有 `javavm`）。
- 默认 JVM 参数：`HMCL_JAVA_OPTS` 未设置时 stub 用 `-Xmx1G -XX:MinHeapFreeRatio=5 -XX:MaxHeapFreeRatio=15`。
- **想"开箱即用"不必上 jpackage**：把绿色版 JRE 放进 `jre-x64`，与 `LMCL.exe` 一起打 zip 即可，零改动。
- 对比 jpackage：只能产当前平台的包（需三平台 matrix），且 macOS 需签名证书否则报"无法验证开发者"。

### 4.5 构建工具链

- Gradle **9.6.1**（wrapper）＋ Kotlin DSL ＋ **JDK 17**（`sourceCompatibility=17`）。
- Shadow 插件为 **`com.gradleup.shadow` 9.3.1**（注意不是旧版 `com.github.johnrengelman.shadow`）。
- 版本号由 `HMCL/build.gradle.kts` 生成：`$versionRoot.$buildNumber`；社区版自 v3.16.8 起使用产品版本 **1.0.0**：`config/project.properties` 默认 `versionRoot=1.0`、`buildNumber=0`，后续发布递增 `1.0.1`……；**上游兼容基线仍是 v3.16.4**，不随产品版本变化。`VERSION_ROOT`/`BUILD_NUMBER` 环境变量仍可覆盖默认值。
- 新增依赖需谨慎：**不引入 HMCL 没有的第三方依赖**（合规与体积双重原因）。JNA 已在核心依赖中，可直接用；Rust 守护进程（步骤 17）是唯一例外，需在 17 中显式豁免并说明。

### 4.6 启动引导与属性注入

新增 `org.jackhuang.hmcl.community.CommunityBootstrap`，通过 shadowJar manifest 的 `Main-Class` 指向它；Bootstrap 只复刻 `Main.checkDirectoryPath()`（路径含 `!` 的检查）后直接调用 `org.jackhuang.hmcl.EntryPoint.main`，**不经过 `org.jackhuang.hmcl.Main.main`**（否则会触发 `UpdateHandler.isNestedApplication()` 的嵌套误判，见步骤 05 §4.1）。Java 版本 ≥17 由启动壳 stub 与 class 版本保证。**属性必须在 `HMCL/src/main/java/org/jackhuang/hmcl/EntryPoint.java:48` 之前设置**（该行首次触发 `Metadata` 类初始化）：

| 系统属性 | 作用 | 设置值 |
|---|---|---|
| `hmcl.update_source.override` | 上游自更新源 | `https://www.kerzeftu.top/lmcl/api/update_link`（固定官网；未签名使检查在联网前失败） |
| `hmcl.self_integrity_check.disable` | 自完整性校验开关 | **`false`（强制保持校验开启）**：我们的产物必然校验失败→更新检查在联网前失败，这是禁用自更新的结构性手段（步骤 05）；外部 `-D=true` 会被 Bootstrap 覆盖 |
| `hmcl.home` | 用户级数据目录 | 社区版独立目录 |
| `hmcl.dir` | 本机级数据目录 | 社区版独立目录 |

> `hmcl.bmclapi.override` 自 v3.12 起**不再被读取**：`DownloadProviders` 已删除静态 BMCLAPI/Mojang 源，实际下载源由步骤 07 的 `CommunityDownloadInstaller` 在运行时替换 `DownloadProviderWrapper.setProvider(...)`（v3.13 平级源 + 测速排序）。

> 启动引导层是"零上游源码侵入"的关键：它同时解决自更新、下载源、数据目录、完整性四个问题。

更新提示不走 `hmcl.update_source.override`：上游链路保持"永远失败"，提示由 `community.update.CommunityUpdateNotifier` 独立读取 GitHub/Gitee Releases（只读、只弹窗跳浏览器，不下载）；仓库未创建时两个常量留空，功能静默。见 §13 #19 与[步骤 05](steps/05-禁用自动更新与更新提示.md)。

## 5. 非功能硬约束

### 5.1 绝不阻断启动

所有增强功能必须遵守统一降级模式：

```java
try {
    result = feature.run();
} catch (Throwable t) {
    LOG.warn("Feature failed, skipping", t);
    // 静默降级，绝不阻断
}
```

| 功能 | 失败表现 | 正确行为 |
|---|---|---|
| 启动前体检 | 超时 / 解析异常 | 跳过体检，直接启动 |
| 崩溃还原 | 无 crash-report / 格式变化 | 显示原始日志入口，不给误导性结论 |
| 实例快照 | 磁盘满 / 写失败 | 不记录快照，正常启动 |
| 内存优化 | 无权限 / 守护进程未运行 / 管道超时 | 仅做 L0，正常启动 |
| 首页组件 | 数据源异常 | 组件显示空态，不影响页面 |

### 5.2 隐私与数据

- 崩溃处理链路**不得有任何外发请求**；仅本地日志 + 弹窗。
- 不得向 HMCL 上游服务器发送任何数据（含崩溃、遥测、统计、更新检查）。
- 自更新必须禁用或指向自有源。
- 守护进程（内存优化）不得联网、不得解析外部输入。

### 5.3 权限与安全

- **主程序永远普通权限（asInvoker），绝不主动提权**。
- **绝不静默绕 UAC**：不使用 `__COMPAT_LAYER=RUNASINVOKER`、不关 `EnableLUA`、不改组策略。
- 高权限能力一律通过**用户显式同意 + 只弹一次 UAC** 的独立组件实现（若未来出现），且该组件必须极小化、严格校验调用方、提供明确卸载入口。
- **L2 内存优化采用登录后后台守护（HKCU Run）**：不需要管理员权限、不注册 Windows 服务；安装/卸载即写入/删除当前用户 `Run` 注册表项，失败时静默回退 L0+。
- **下载源地址决定所有下载去向** → 强制 https、URL 格式校验、导入前预览确认、来源提示。

### 5.4 性能与体验

- 首页 / 组件 / 页面：所有 I/O **必须异步**，不得阻塞 FX 线程。
- 监听器必须可解绑，组件销毁时必须 `dispose()`；后台任务必须可取消。
- 不引入明显影响启动耗时（冷启动 > 1s 增量）的检查项；体检有硬超时。
- 中文排版使用我们自己的 `assets/css/community.css` 五档类型层级（尺寸对齐上游在用字号 20/16/14/12），复用 HMCL 既有字体处理（`-Dhmcl.font.override=`）；**不修改**上游 `StyleSheets`/`root.css`/`blue.css`（步骤 19）。

### 5.5 平台要求

| 平台 | 支持等级 | 说明 |
|---|---|---|
| Windows x86/x64 | 完整 | 含内存优化 L2（HKCU 后台守护，默认关闭） |
| Linux x86/ARM | 完整（除 L2） | 无系统级工作集清理，仅 L0+ |
| macOS Intel/Apple Silicon | 完整（除 L2/purge） | `purge` 不作为默认；Apple Silicon 提示收益有限 |
| FreeBSD | 完整（除 L2） | 同上 |
| RISC-V / LoongArch / MIPS | 跟随上游 | 构建产物需自建 runner |

**平台分派必须检测"能力"而非"操作系统"**：同一 OS 下权限、架构、沙箱、杀软差异极大。能力探测结果写入配置缓存，避免每次启动重复探测。

## 7. 开发规范

### 7.1 包结构约定

新增功能一律放新 package，命名见 [4.2](#42-改动策略代码侵入-14-处--分级登记)。**禁止**在既有上游 package 中新增业务类。

### 7.2 侵入点纪律

- **代码侵入当前 17 处**：`Metadata.java`、`MainPage.java`、`LauncherHelper.java`、`DownloadSettingsPage.java`、`RootPage.java`、`DecoratorAnimatedPage.java`、`DecoratorController.java`、`LauncherSettingsPage.java`、`Controllers.java`、`GameSettings.java`、`GameSettingsPage.java`、`PersonalizationPage.java`、`DownloadProviders.java`、`HMCLGameRepository.java`、`ThemePackManagementPage.java`、`CrashReport.java`（#16）、`CrashWindow.java`（#17）；新增或修改功能可继续侵入，但每个新上游文件必须登记，同一文件复用已有入口不新增。
- 构建脚本与资源文件（i18n、图标、about）按 §4.2 的表单独登记，不占代码名额。
- 每次同步上游后，必须核对代码侵入数量与位置是否仍与 §4.2 一致，并在 PR 描述中附核对结果。
- 侵入点继续增长会推高同步成本；能用新增式实现的，仍优先新增式。

> 教训来自 Prism：官方 QML 重写的 Issue #980 关闭原因就是"冲突数量已增长到 impractical"。

### 7.3 错误降级规范

见 [5.1](#51-绝不阻断启动)。补充：

- 降级日志用 `LOG.warn`，不用 `LOG.error`（避免用户误以为严重故障）。
- 面向用户的提示必须说明"已跳过 + 如何手动处理"，不静默吞掉全部信息。
- 关键路径（启动）不得因降级逻辑本身抛出异常。

### 7.4 AI 辅助编码的收益边界

**能省 50–70%**：组件骨架、JSON 持久化与迁移、CSS、数据模型类、JavaFX 布局嵌套、单元测试、文档。

**几乎帮不上甚至添乱**：理解 HMCL 现有架构（`SettingsManager`/`LauncherSettings`/`GameSettings` 配置树、HMCLCore API 边界、`LauncherHelper` 启动链）、侵入点选择、异步与内存泄漏处理、JavaFX DnD 细节、merge 冲突、崩溃分析与三种 mod 元数据规范。

**限制**：JavaFX/JFoenix/MonetFX/Decorator 是小众栈，易产生幻觉 API、Swing/JavaFX 混用、JFoenix 旧写法。

**缓解**：先把相关类源码喂给它 —— `MainPage.java`、`RootPage.java`、`Controllers.java`、`SettingsManager.java`、`TwoLineListItem`、`SVG`、`FXUtils`、`Navigator`。

**合规**：生成后必须 review，别混进 MIT/Apache 片段，别引入 HMCL 没有的第三方依赖。

### 7.5 提交与评审约定

- 每个步骤对应一个或多个 issue，里程碑与步骤编号对应。
- 涉及 `Metadata.java` / `MainPage.java` / `LauncherHelper` 的改动必须单独 commit，便于 patch 策略维护。
- 任何新增 package 必须在 `README` 的步骤总表登记。
- 发布前必须走完 [3.7 分发 Checklist](#37-分发-checklist每次发版逐项确认)。
