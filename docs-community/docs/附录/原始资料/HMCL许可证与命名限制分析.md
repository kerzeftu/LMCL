# HMCL 许可证与命名限制分析

> 面向"基于 HMCL 做社区版"的场景。含条款原文、义务清单、命名边界与风险分级。
> 本文为信息梳理，不构成法律意见；涉及商标与合规判断，建议咨询专业人士。

---

## 一、许可证构成

HMCL 的许可证由两部分组成，**且分处两个文件**：

| 文件 | 内容 |
|---|---|
| `LICENSE` | GPLv3 **全文**（标准文本，35 KB） |
| `README.md` | **附加条款**（Additional terms under GPLv3 Section 7） |

⚠️ **注意这个结构**：附加条款写在 README 里，不在 LICENSE 里。

GPLv3 第 7 条原文要求附加条款应"list, in one central place in the source code"（在源代码中一个集中位置列出）。README 是否算"central place in the source code"存在解释空间。

**对你的实务影响**：分发时必须把这两部分**一起带上**——不能只复制 LICENSE 就以为完成了。建议在你的仓库里把原附加条款单独抄录一份（比如 `LICENSE-ADDITIONAL-TERMS.md`），并在 README 显著位置引用。

## 二、附加条款原文

官方 README（中英双版，内容一致）：

**英文：**

> The software is distributed under GPLv3 license with the following additional terms:
> **Additional terms under GPLv3 Section 7**
> When you distribute a modified version of the software, you must change the software name or the version number in a reasonable way in order to distinguish it from the original version. (Under GPLv3, 7(c))
> The software name and the version number can be edited here.
> You must not remove the copyright declaration displayed in the software. (Under GPLv3, 7(b))

**中文：**

> 该程序在 GPLv3 开源协议下发布，同时附有以下附加条款。
> **附加条款（依据 GPLv3 开源协议第七条）**
> 当你分发该程序的修改版本时，你必须以一种合理的方式修改该程序的名称或版本号，以示其与原始版本不同。（依据 GPLv3, 7(c)）
> 该程序的名称及版本号可在此处修改。
> 你不得移除该程序所显示的版权声明。

拆解下来是**两条义务**：

1. **改名或改版本号**（二选一，需"合理方式"）
2. **不得移除程序中显示的版权声明**

## 三、条款号标注的一处偏差（值得了解）

README 把"必须改名"标注为 7(c)、"保留版权声明"标注为 7(b)。

对照 GPLv3 原文，第 7 条的结构是：

- **7(a) Additional Permissions** —— 附加许可（放宽限制）
- **7(b) Additional Requirements** —— 附加要求（收紧限制），并列举**仅这六类被允许**：
  - (0) 要求保留指定的合理法律声明或作者归属
  - (1) **要求修改版以特定合理方式标记为不同于原版**
  - (2) 不同的担保/责任免责声明
  - (3) 禁止或限制为宣传目的使用许可人/作者的特定名称，或要求特定商标未经明确许可不得用于宣传
  - (4) 网络交互程序需提供对应源码
  - (5) 专利诉讼导致许可终止
  - (6) 与本许可证明确规定的要求等同的条款
- **7(c) Terms Added or Removed by You** —— 讲的是**下游不能再添加新的附加要求**

所以按 GPLv3 的分类：
- "不得移除版权声明" → 7(b) 类型 **(0)** ✅ 标注正确
- "必须改名称或版本号" → 7(b) 类型 **(1)** —— README 标成了 7(c)，**索引有偏差**

**实质影响**：无。7(b)(1) 明确允许"要求修改版以合理方式标记为不同于原版"这类附加要求，所以这条义务是有效的、可执行的。只是引用的条款号不准确。

**对你更重要的推论（来自 7(c)）**：
> 你作为下游分发者，**不能再添加新的附加要求**。

也就是说你的社区版不能加"禁止商用"、"必须额外署名本项目"、"不得再分发"之类的限制性条款。你只能：
- 以 **GPLv3 + 原附加条款** 分发
- 或者**添加附加许可**（放宽），比如允许某些 GPL 本不允许的用法

**不能闭源、不能换许可证、不能加限制。**

## 四、命名限制：边界在哪

### 4.1 明确禁止的

| ❌ 不可为 | 原因 |
|---|---|
| 直接叫 "HMCL" 或 "Hello Minecraft! Launcher" | 名称未改变，违反附加条款 |
| 移除/隐藏程序内显示的版权声明 | 违反附加条款（7(b)(0)） |
| 闭源分发 | 违反 GPLv3 copyleft |
| 更换为其他许可证 | 违反 GPLv3 |
| 添加新的附加要求 | 违反 GPLv3 7(c) |

### 4.2 字面可行但强烈不建议的

**只改版本号、名称不变**（例如 `HMCL 3.13.0-community`）

条款原文是"名称**或**版本号"，所以严格讲字面满足。但：

- 这正是附加条款想避免的情形——用户会以为是官方版本
- 搜索结果、社区讨论会与官方 HMCL 混在一起
- 一旦出现 bug 或争议，伤害的是上游声誉，容易引发纠纷
- 商标混淆风险（见第五节）

**不要用这个方案。**

### 4.3 实际 fork 的命名实践（参考）

公开可见的几个 fork：

| 仓库 | 命名 | 评价 |
|---|---|---|
| `saltedfishclub/HMCL-sfc` | HMCL + 自有后缀 | 较规范，但仍以 HMCL 开头 |
| `XiaoXi/HMCL-iFlute` | HMCL + 自有后缀 | 同上 |
| `InfinityStudio/HMCL` | 仓库名未改 | 不规范（2016 年的老 fork，落后 4057 commits） |

前两个是社区里较常见的做法，`HMCL-<标识>`。缺点：**搜索时仍与官方混在一起**，且容易被认为是官方的一个分支。

### 4.4 命名方案风险分级

| 方案 | 示例 | 附加条款合规 | 商标/混淆风险 | 建议 |
|---|---|---|---|---|
| **完全独立名称** | "Kaleido Launcher" / "Aurora Launcher" | ✅ | **最低** | ⭐ 推荐 |
| 独立名称 + 显著标注来源 | "Nova Launcher —— 基于 HMCL" | ✅ | 低 | ⭐ 推荐 |
| HMCL + 后缀 | "HMCL-Nova" | ✅ | 中 | 可接受 |
| 仅改版本号 | "HMCL 3.13-community" | ⚠️ 字面合规 | 高 | ❌ 不建议 |
| 沿用原名 | "HMCL" | ❌ 违反 | 极高 | ❌ 禁止 |

**推荐方案：独立名称 + 在"关于"页与 README 明确说明来源。**

这样同时满足：
- 附加条款（名称已改变，可区分）
- 版权声明保留（保留程序内的声明）
- 归属清晰（主动说明基于 HMCL，是对上游的尊重，也让用户知道源码在哪）
- 商标与混淆风险最低

## 五、商标风险：GPL 不管这一块

**这是最容易被忽略的一点。**

开源许可证授予的是**版权**，不授予名称权：

| 许可证 | 关于名称/商标的规定 |
|---|---|
| Apache-2.0 | 第 6 条明确：不授予商标许可 |
| MPL-2.0 | 第 2.3 条：不授予贡献者商标权 |
| **GPL-3.0** | **默认不提**。第 7(e) 只是"允许"你添加一条声明放弃商标权的条款 |
| MIT | 不提 |
| BSD-3 | 有"不得用贡献者名背书"条款 |

**HMCL 的附加条款里没有商标条款** —— 它没用 GPLv3 7(b)(3)（该类型允许"禁止为宣传目的使用特定名称"或"要求商标未经许可不得用于宣传"）。也就是说，**上游没有主动主张商标限制**。

但这**不代表你可以随意使用这个名字**，因为：

1. **商标权独立于版权存在**。GPL 没提商标，不等于放弃商标
2. 美国法下商标**因商业使用而产生**（未注册也可主张 ™）；中国是注册制，但未注册的知名商品名称仍可能受《反不正当竞争法》保护
3. 我没有检索到 "HMCL" / "Hello Minecraft! Launcher" 的公开商标注册信息，但**无法排除**其存在或后续主张
4. **混淆本身就是风险** —— 即使法律上能争，被要求改名、下架、社区争议的成本都很高

**结论**：正因为商标状况不明确，**采用独立名称是最稳妥的**。这不只是法律避险，也是产品定位——你的社区版有自己的差异化定位，用独立名称更利于建立独立认知。

## 六、"版权声明"具体指什么

条款说"不得移除该程序所显示的版权声明"（the copyright declaration displayed in the software）。

实务上包括：

| 位置 | 内容 |
|---|---|
| 关于页面 | HMCL 的版权与作者信息 |
| 源码文件头 | `license-header.txt` 对应的版权头 |
| 第三方组件声明 | Log4j（Apache-2.0）、Gson（Apache-2.0）、NimbusLAF（LGPL，在 `org.jackhuang.hmcl.laf.ui`）等 |

⚠️ **一个历史遗留提醒**：旧版 README 有一条
> When you do decide to modify this app, please and you MUST delete `HMCL/org.jackhuang.hmcl.util.CrashReporter`, or errors your code cause will be sent to my server.

意思是修改后**必须删掉 CrashReporter**，否则你代码产生的错误会发到原作者的服务器。

这条在新版 README 里可能已不在（该类在新架构中也可能已移除/改名），但值得确认一下——**无论如何，你的社区版不应把崩溃报告发往上游服务器**。这既是隐私合规问题，也是避免给上游造成噪声。

## 七、分发义务清单（Checklist）

发布你的社区版时，逐项确认：

- [ ] 名称已改变（不使用 "HMCL" / "Hello Minecraft! Launcher" 作为产品名）
- [ ] 版本号或名称其一已改变，且改变方式"合理"（能明确区分于原版）
- [ ] 程序内版权声明**未移除**（关于页、源码头、第三方声明）
- [ ] 随附 **GPLv3 全文**（`LICENSE`）
- [ ] 随附 **HMCL 的附加条款原文**（它在 README 里，不要漏掉）
- [ ] 修改的文件带有**显著声明**：说明你改了什么、修改日期（GPLv3 5(a)）
- [ ] 提供**对应源码**（公开的 GitHub 仓库即可满足）
- [ ] 明确标注"基于 HMCL 开发"及 HMCL 的许可证
- [ ] **未添加**任何新的附加要求（不能加禁止商用、额外署名等）
- [ ] 崩溃报告**未发往上游服务器**
- [ ] 图标/Logo 建议重新设计（避免视觉混淆）

## 八、几个常见疑问

**Q：包名 `org.jackhuang.hmcl` 要不要改？**
GPLv3 不要求改包名。而且**改了会让同步上游变得极其痛苦**（每次 merge 都是全量重命名冲突）。建议保留。

**Q：数据目录 `~/.hmcl`、参数前缀 `-Dhmcl.*` 要不要改？**
同理，建议保留。改了会破坏用户配置迁移，且不影响合规。名称义务针对的是**产品名/版本号**，不是内部标识符。

**Q：能不能收费/商用？**
GPLv3 **允许**商用和收费（"we speak of free software, not of free price"）。但必须同时提供源码，且不得添加"禁止商用"条款。

**Q：能不能不开源，只发布 exe？**
不能。GPLv3 要求提供对应源码。不过你可以**只分发给你自己用**（不构成"convey"）——一旦对外分发就必须给源码。

**Q：我用独立名称，还需要在界面里提 HMCL 吗？**
条款只要求"不移除版权声明"和"改名"，没强制要求署名来源。但**建议主动标注**：
- 符合开源社区惯例与对上游的尊重
- 用户能找到上游源码，也符合 GPL 精神
- 反而降低"抄袭"的争议风险

**Q：图标能沿用吗？**
图标作为程序的一部分受 GPLv3 覆盖（可以修改和再分发）。但若图标具有商标属性，沿用会带来混淆风险。**建议重新设计**——反正你要做 MD3 视觉，正好一起做。

## 九、给本项目的具体建议

基于以上分析，针对你的社区版：

1. **产品名**：起一个完全独立的名字，例如 `<名字> Launcher`。在命名时避开 "HMCL"、"Hello Minecraft" 字样的**开头**（避免搜索混淆）
2. **版本号**：独立版本号体系（如 `1.0.0`），不要沿用 HMCL 的版本号，避免被误认为官方版本
3. **关于页**：保留 HMCL 版权声明，并明确写"基于 HMCL（GPLv3）开发，源码位于 <你的仓库>"
4. **LICENSE 目录**：同时放 `LICENSE`（GPLv3 全文）与 `LICENSE-ADDITIONAL-TERMS.md`（HMCL 附加条款原文）
5. **Metadata.java**：改名称与版本号（README 指明的官方修改位置）
6. **包名 / 数据目录 / 参数前缀**：保留不动，降低同步成本
7. **图标**：重新设计
8. **崩溃上报**：确认不发往上游服务器
