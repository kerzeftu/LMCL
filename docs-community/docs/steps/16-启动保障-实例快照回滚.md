## 1. 目标

每次**成功游玩**后自动记录一份可回滚的实例状态；用户更新模组/改配置导致起不来时，一键回到上一个"能跑"的状态。

完成标志（DoD）：

- [ ] 成功启动（08 判定：进程存活 ≥ 阈值，默认 120 s）退出后，后台自动生成快照，**不阻塞退出、不阻塞下次启动**；
- [ ] 快照包含：模组/配置等"决定能否启动"的文件清单与内容；**不含存档、日志、截图**；
- [ ] 回滚可精确还原被替换/删除的模组与配置；资源不足时降级为 `manifest-only` 并**明确告知哪些文件不能还原**；
- [ ] 回滚前自动拍"回滚前快照"（可逆），且文件逐项执行、失败汇总、不中断；
- [ ] 回滚期间与游戏运行期间互斥（有实例在跑时拒绝回滚）；
- [ ] 共享运行目录（非隔离实例）场景有明确警告与影响面提示；
- [ ] 快照占用可控：默认每作用域保留 3 份、上限 2 GiB，超限自动清理；
- [ ] 断电/强杀后的半成品快照在下次启动时被清理；
- [ ] 全部离线可用；12 个测试用例通过。

## 2. 决策与依据

### 2.1 为什么放弃"拦截写入 + 回收站"方案

原稿设想"在启动器自己的文件写入路径上先把旧文件移入 trash"。核对上游后此路不通：

| 事实 | 位置 |
|---|---|
| 模组下载/更新/启停全部走上游 `ModManager` + 下载任务，直接写目标文件 | `HMCLCore/src/main/java/org/jackhuang/hmcl/addon/mod/ModManager.java` |
| 用户也可能在资源管理器里手动替换 jar | 无法拦截 |

要接住上游每一次写入，必须在上游下载/安装链路上打点（`ModManager`、`HMCLGameRepository` 等多处），远超 `00 §4.2` 的"代码侵入固定 3 处"，且随上游升级持续漂移。**结论：放弃拦截。**

### 2.2 采用的方案：成功退出后"硬链接快照 + 内容寻址 + 校验恢复"

```
快照 S1（成功后）：
  objects/ab/cdef…  ← 硬链接到 mods/A.jar（内容 v1，与游戏文件同一 inode）
  objects/12/3456…  ← 硬链接到 mods/B.jar
  快照目录/manifest.json（路径 → sha256 → object）

用户把 A.jar 更新为 v2（上游用"新文件 + 替换"写入）→ S1 的硬链接仍指向 v1 内容
启动失败 → 回滚 S1：把 objects/… 复制回 mods/A.jar（v2 移入回滚前快照）
```

- **为什么可行**：jar 更新是"写新文件再替换/删除"，旧 inode 被快照硬链接保住；上游自己就这么做（`HMCLCore/src/main/java/org/jackhuang/hmcl/util/CacheRepository.java:166` 用 `Files.createLink` 建缓存硬链接）；
- **空间**：硬链接几乎不占空间，天然去重；同一文件被多个快照引用只存一份内容；
- **小文件例外**：`options.txt`/`config/**`/`instance-game-settings.json`/`servers.dat` 可能被**原地改写**，硬链接会一起变 → 这类文件（单文件 ≤ 256 KiB）一律**真实复制**；
- **不支持硬链接的文件系统**（FAT32/exFAT/部分网络盘）：自动退化为复制；超过预算（默认 2 GiB/作用域）再退化为 `manifest-only`（只记录清单，回滚只能"删除新增文件"，被改/被删文件标注"无法还原"）；
- **失效检测**：回滚前逐个校验 object 的 sha256；不匹配（说明被原地改写破坏）→ 该文件标"快照已失效"，不覆盖当前文件，汇总告知。

### 2.3 作用域：按"运行目录"而不是"实例"

`HMCLGameRepository.getRunDirectory(id)`（`HMCL/src/main/java/org/jackhuang/hmcl/game/HMCLGameRepository.java:165-184`）的语义：

1. 整合包实例 → 版本目录（隔离）；
2. 显式设置"运行目录" → 该目录（可能共享）；
3. 否则 → 仓库根目录（`DefaultGameRepository.getRunDirectory` :114 返回 `getBaseDirectory()`，**多个实例共享**）。

因此快照以 **规范化后的运行目录** 为作用域（scope key = 运行目录绝对路径的 SHA-256 前 16 位）：

- 隔离实例：`scope = version-root`，`instanceIds = [该实例]`；
- 共享目录：`scope = shared`，`instanceIds = 所有 getRunDirectory 指向同一路径的实例`，UI 必须警告"回滚会影响共用该目录的实例"；
- 记录 `runDirectory` 明文路径在 manifest 里（本机数据，不上传）。

### 2.4 成功判定复用 08，不重复实现

| 事件（08 契约） | 16 的动作 |
|---|---|
| `EXITED_NORMAL` / `EXITED_ABNORMAL` 且 `alive >= 阈值` | 会话成功 → 调度快照采集（io） |
| `EXITED_*` 且 `alive < 阈值` | 不采集（失败/未知启动不污染快照） |
| `ABORTED_BY_USER` | 不采集 |
| 手动"标记当前状态为可用" | 采集（用户兜底，UI 二次确认） |

> 采集放在**进程退出之后**而不是存活阈值触发时：游戏刚退出时文件句柄已释放，Windows 上成功率高。

## 4. 数据模型

### 4.1 目录结构

```
<Metadata.HMCL_LOCAL_HOME>/community/snapshots/
├── scopes.json                     # scope key → {runDirectory, instanceIds, lastSnapshotId}
├── <scopeKey>/
│   ├── s-20261021T120400Z/
│   │   └── manifest.json
│   └── s-20261022T090100Z/
│       └── manifest.json
├── objects/                        # 内容寻址（所有 scope 共用）
│   └── ab/cdef0123…（硬链接或复制）
├── hash-cache.json                 # (path,size,mtime) → sha256 缓存
└── snapshot.lock                   # FileLock，防多启动器并发
```

> **为什么不放在实例目录**：共享运行目录/只读实例目录都可能不可写；放 `community/` 下与 06/08/09/15 的数据根一致，卸载/清理边界清晰。

### 4.2 `manifest.json`（schema v1）

```json
{
  "version": 1,
  "snapshotId": "s-20261021T120400Z",
  "scopeKey": "3f2a9c01d4e5b6a7",
  "scope": "version-root",
  "runDirectory": "C:/Games/HMCL/.minecraft/versions/1.20.4-Fabric",
  "instanceIds": ["1.20.4-Fabric"],
  "createdAt": 1761057840000,
  "successfulLaunchAt": 1761057600000,
  "reason": "success",
  "mode": "hardlink",
  "thresholdSeconds": 120,
  "files": [
    {
      "path": "mods/sodium-fabric-0.5.3.jar",
      "size": 1234567,
      "sha256": "9f2c…",
      "object": "9f/2c…",
      "link": "hardlink",
      "mtime": 1761000000000
    },
    {
      "path": "options.txt",
      "size": 4096,
      "sha256": "aa01…",
      "object": "aa/01…",
      "link": "copy",
      "mtime": 1761057000000
    }
  ],
  "excluded": ["saves", "logs", "crash-reports", "screenshots", "backups", "natives-*", ".snapshots"]
}
```

- `reason`：`success` / `manual` / `pre-restore`；
- `mode`：`hardlink` / `copy` / `manifest-only`（不含 `files[].link` 时表示未物化内容）；
- 路径一律相对 `runDirectory`，用 `/` 分隔，禁止 `..` 与绝对路径（读取时校验）；
- 未知字段保留（与 13 配置一致的做法）。

### 4.3 采集范围（白名单，其余一律不碰）

| 包含 | 说明 |
|---|---|
| `mods/**` | 核心：jar / `.disabled` |
| `config/**` | 模组配置（单文件 ≤ 256 KiB 才收录，超出跳过并记日志） |
| `options.txt`、`optionsof.txt`、`servers.dat` | 用户可感知的配置 |
| `instance-game-settings.json` | 上游的实例级设置（存在才收） |
| `resourcepacks/**`、`shaderpacks/**` | 仅当 `snapshots.includeResourcePacks=true`（默认 false，体积大） |
| `datapacks/**` | 同上开关（默认 false） |

**排除**：`saves/`、`logs/`、`crash-reports/`、`screenshots/`、`backups/`、`natives-*`、`libraries/`、`assets/`、`.snapshots/`、任何符号链接/目录联接（防越界）、任何 `*.log`。

### 4.4 与 06 的共享设置（`community-settings.json` 追加段）

```json
"snapshots": {
  "enabled": true,
  "autoCaptureOnSuccess": true,
  "keep": 3,
  "maxBytesPerScope": 2147483648,
  "includeResourcePacks": false,
  "includeDatapacks": false,
  "hashCacheMaxEntries": 5000
}
```

字段缺失按默认值；读取失败不阻断启动（沿用 08 §3.5 规则）。

## 5. 实现

### 5.1 类与职责

```
org.jackhuang.hmcl.community.snapshot
├── SnapshotService        // 门面：capture/rollback/list/diff/delete；只读状态查询给 UI
├── SnapshotCapture        // 枚举 → hash → 物化 → 写 manifest → 清理半成品
├── SnapshotRestore        // diff → 预拍快照 → 逐文件执行 → 校验 → 汇总
├── SnapshotStore          // 路径/锁/原子写/objects 寻址/GC
├── SnapshotManifest       // record + 读写 + 校验
├── SnapshotDiff           // record：added/missing/changed/invalid 四类
├── SnapshotScope          // 运行目录解析 + 共享实例集合
└── ui/SnapshotCard、ui/SnapshotManagerDialog、ui/SnapshotDiffDialog
```

关键签名（14 §2.3 已引用，**回填 14 时以此为准**）：

```java
public final class SnapshotService {
    public static CompletableFuture<SnapshotResult> capture(
            @NotNull String versionId, @NotNull SnapshotReason reason);
    public static CompletableFuture<RestoreResult> restore(
            @NotNull String versionId, @NotNull String snapshotId);
    public static @NotNull List<SnapshotInfo> list(@NotNull String versionId);
    public static CompletableFuture<SnapshotDiff> diff(
            @NotNull String versionId, @NotNull String snapshotId);
    public static CompletableFuture<Void> delete(@NotNull String snapshotId);
    public static boolean isBusy(@NotNull String scopeKey);
}

public record RestoreResult(
        int restored, int deleted, int failed,
        @NotNull List<String> failedPaths,
        @Nullable String preRestoreSnapshotId) { }

public enum SnapshotReason { AUTO_START, PRE_RESTORE, MANUAL }

/// 快照摘要（14 的快照卡列表项；`id` 即目录名，用于 restore/diff/delete）。
public record SnapshotInfo(@NotNull String id, @NotNull Instant at,
                           @NotNull SnapshotReason reason, long files, long bytes,
                           boolean manifestOnly, boolean pinned) { }

/// capture 的结果；`skipped=true` 时 `snapshotId=null` 且 `skipReason` 说明原因。
public record SnapshotResult(@Nullable String snapshotId, boolean skipped,
                             @Nullable String skipReason, @Nullable SnapshotInfo info) { }

/// 四类差异（`invalid` = 路径/文件已不可用，例如被手工删除的目录）。
public record SnapshotDiff(@NotNull List<String> added, @NotNull List<String> missing,
                           @NotNull List<String> changed, @NotNull List<String> invalid) { }
```

### 5.2 采集算法

```
capture(versionId, reason):
 1. scope = resolveScope(versionId)；若 settings.snapshots.enabled=false 且 reason!=manual → 返回 SKIPPED
 2. 若 08 显示该 scope 有活跃会话（游戏运行中）→ SKIPPED（退出后才采集，正常不会发生）
 3. 获得 snapshot.lock（FileLock，超时 3 s 失败即 SKIPPED，不重试）
 4. 检查磁盘：usable < max(512MiB, 预估增量) → 记录日志并 SKIPPED（卡片显示原因）
 5. 枚举白名单文件（见 4.3；跳过符号链接）；
    单文件 hash = hash-cache(path,size,mtime) 命中则复用，否则 sha256（DigestUtils:81）
 6. 与"上一个快照"比对：相同 sha256 的文件直接复用其 object（不重复物化）
 7. 物化：
    - 小文件或需要保护的文件（4.3 小文件规则）→ Files.copy 到 objects/
    - 其他 → Files.createLink(object, source)；抛 UnsupportedOperationException/IOException → 复制
    - 累计物化字节超过 maxBytesPerScope → 停止物化，降级 mode=manifest-only（保留已物化部分，manifest 标降级）
 8. 写临时目录 snapshot.tmp-<uuid>/manifest.json → ATOMIC_MOVE 到最终目录
 9. 更新 scopes.json；执行保留策略（§5.4）
10. 释放锁；结果回 UI（卡片"上次快照"刷新）
```

- 全部在 `Schedulers.io()`；同一 scope 串行（进程内 `Semaphore(1)` + 文件锁）；
- 采集期间不修改任何游戏文件（只读 + 创建链接/副本）；
- 启动时扫描 `*.tmp-*` 目录 → 删除（强杀残留）；
- `reason=pre-restore` 的快照固定保留，不参与自动清理，除非用户手动删除。

### 5.3 回滚算法

```
restore(versionId, snapshotId):
 1. 校验 manifest：路径合法性（相对、无 ..、无绝对路径）、版本号；非法 → 失败并提示"快照损坏"
 2. 08 会话状态：该 scope 任一实例有活跃会话 → 拒绝（"请先退出游戏"）
 3. 预拍当前状态（reason=pre-restore）：失败则中止（"无法创建可逆快照，已取消回滚"）——保证可逆
 4. diff（相对快照）：
    added   = 当前有、快照无 → 删除（先移入 pre-restore 快照，可再恢复）
    missing = 快照有、当前无 → 从 object 还原
    changed = 都有但 sha256 不同 → 从 object 还原（当前内容已在 pre-restore 中）
    invalid = 快照 object 缺失或 sha256 不符 → 不覆盖，计入 failed
 5. 展示清单（数量 + 前 20 条路径 + 展开全部）→ 二次确认
 6. 逐文件执行（每项独立 try/catch）：
    还原 = Files.copy(object → 同目录 tmp) + ATOMIC_MOVE 覆盖（保留原文件名大小写）
    删除 = Files.move 到 pre-restore 快照的 objects（可逆）
 7. manifest-only 快照：只执行删除，missing/changed 全部计入 failed（文案"该快照未保存文件内容"）
 8. 汇总对话框：成功/失败数、失败路径可复制、"建议启动验证"、附"撤销本次回滚（回到 pre-restore）"按钮
 9. 返回 RestoreResult
```

- 执行中禁用"启动"按钮（直接复用 08 §3.1 已提供的 `CommunityLaunchHooks.activeSessionCount(versionId)`；`SnapshotService.isBusy(scopeKey)` 内部也走同一计数，两处同源）；
- 崩溃卡（14）的"回滚到启动前"使用同一 API，传 `preRestoreSnapshotId` 或最近 `success` 快照。

### 5.4 保留与 GC

| 规则 | 默认 |
|---|---|
| 每 scope 保留快照数 | 3（可 1–10），`pre-restore` 不计数、不自动删 |
| 每 scope 物化总字节 | 2 GiB，超限时优先删最旧的 `success` 快照 |
| objects GC | 删除某快照后，扫描全部 manifest 的 object 引用，删除零引用 object（先移入 `trash-objects/`，启动时再清空） |
| hash-cache 上限 | 5000 条，LRU 淘汰 |

清理全部在后台执行，失败只记日志。

### 5.5 UI：`snapshot` 卡片 + 管理对话框

卡片（2×1，0 上游侵入）：

```
┌──────────────────────────────────────────┐
│ 实例快照                       [管理…]    │
│ 上次成功：10-21 12:04 · 1 个文件变更 8 MB │
│ 快捷： [回滚到上次成功]  [标记当前为可用]  │
└──────────────────────────────────────────┘
```

- 数据：`SnapshotService.list(selectedInstanceId)`（io）+ 会话事件刷新；
- [回滚到上次成功]：找最近 `reason=success` 快照 → diff → 二次确认 → restore；
- 无快照：空态"还没有快照，成功启动一次后自动记录"；
- 失败/降级：`manifest-only` 显示黄色标记"该快照未保存文件内容"；
- 共享运行目录：卡片顶部固定黄条"与 N 个实例共享运行目录，回滚会影响它们"；
- 管理对话框（宽 720）：快照列表（时间/原因/模式/文件数/占用）、[对比][回滚][删除]、保留策略调整（写 `community-settings.json`）、"标记当前为可用"。

| 3 | 删除一个模组后启动失败 | 回滚后模组重新出现 |
| 4 | 用户手动替换 jar（资源管理器） | 回滚成功还原旧版（硬链接仍指向旧内容） |
| 5 | 原地改写 jar（模拟破坏） | 回滚时该文件标"快照已失效"，不覆盖，其余正常 |
| 6 | exFAT 盘（不支持硬链接） | 自动 `copy` 模式；回滚成功；日志有降级记录 |
| 7 | 物化超 2 GiB | 降级 `manifest-only`；回滚只删新增，文案明确"未保存内容" |
| 8 | 回滚中途目标被占用（Windows） | 该项失败、其余继续、汇总展示 |
| 9 | 回滚前预拍快照 | 成功后出现 `pre-restore` 快照；"撤销"可用 |
| 10 | 游戏运行中回滚 | 拒绝并提示退出游戏 |
| 11 | 共享运行目录的两个实例 | 卡片黄条提示；回滚后两实例均受影响（符合预期） |
| 12 | 采集时强杀启动器 | 下次启动清理 `*.tmp-*`；无半成品快照出现在列表 |

---

## 7. 风险

| 风险 | 等级 | 应对 |
|---|---|---|
| 原地写文件破坏硬链接内容 | **高** | 小文件强制复制；回滚前 sha256 校验；失效项不覆盖并告知 |
| 共享运行目录回滚影响其它实例 | **高** | scope 按运行目录建模 + 黄条警告 + 确认框列出受影响实例 |
| 磁盘被快照占满 | 中 | 2 GiB/scope 上限 + 采集前可用空间检查 + GC |
| 硬链接/复制性能（几千文件） | 中 | 增量 hash 缓存 + 与上一快照 sha256 比对跳过物化 + 后台线程 |
| 采集/回滚与游戏同时进行 | 中 | 退出后采集；回滚前检查会话；文件锁 + 进程内信号量 |
| 文件系统对大小写/Unicode 处理不同 | 中 | 路径统一 `/`；恢复用原 manifest 路径逐级创建；测试中文/空格路径 |
| 上游改运行目录语义 | 中 | 每次升级跑 `SnapshotScope` 单测（隔离/共享/自定义三态）；解析失败按"共享"保守处理 |
| 与 14 的约定签名漂移 | 中 | §5.1 为准；收尾一致性检查时回填 14 §2.3 |

---

## 8. 回退

1. 关闭 `snapshots.enabled` → 不再采集（保留既有快照可手动管理）；
2. 删除 `community/snapshots/` → 功能回到"无快照"，不影响游戏与其它社区功能；
3. 卡片隐藏：右键"本次隐藏"；从 `descriptors()` 移除 `snapshot` 即彻底下线 UI；
4. 本步未改上游任何文件，回退无构建风险。
