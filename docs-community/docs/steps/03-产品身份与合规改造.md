## 1. 目标

让产物在法务上站得住、在用户眼里是一个独立产品，而不是"伪装成 HMCL 的东西"。

完成标志：

1. 窗口标题、任务栏名、崩溃报告标题全部指向本项目；
2. 版本号独立于上游、可排序、可追溯上游基线；
3. 仓库根目录有 `LICENSE`（GPLv3 全文）+ `LICENSE-ADDITIONAL-TERMS.md`（附录 A 原文）；
4. 所有改动过的上游源文件按 GPLv3 第 5(a) 条加了修改声明；
5. 不存在任何新增的附加要求（不加"禁止商用"、不加额外署名强制）。

> 本文基于 **v3.16.4（release/3.16）实测源码**，与旧版文档假设的 release/3.13 不同。基线信息见[整体要求 §4.1](../00-整体要求.md#41-上游基线锁定)。

## 2. 背景与决策依据

### 2.1 为什么这一步必须先于所有功能开发

GPLv3 第 7 条允许在**保持 GPLv3 全文不变**的前提下附加有限条款；HMCL 的附加条款写在 README 的 `## License` 一节里（**不在 `LICENSE` 文件中**）。这些条款继承到本项目上，其中与身份相关的是：

| 条款 | 要求 | 本项目的落地 |
|---|---|---|
| 7(b)(0)/(1) | 分发修改版时须以合理方式**改名或改版本号** | 独立名称 + 独立版本号 `1.0.0+`（基于 HMCL v3.16.4） |
| 7(b)(1)/(2) | 不得移除程序内的版权声明 | 关于页、源码文件头、崩溃报告全部保留 |
| 7(c) | 下游不得**新增**附加要求 | 本项目对下游零附加要求 |

### 2.2 命名决策

| 方案 | 合规性 | 推荐度 |
|---|---|---|
| 完全独立名 | 完全满足，最干净 | ⭐⭐⭐ |
| 独立名 + 明确标注"基于 HMCL 开发" | 完全满足 | ⭐⭐⭐ **首发采用** |
| `HMCL` + 后缀（如 HMCL Community） | 可接受，但可能触发上游商标顾虑 | ⭐⭐ 备选 |
| 只改版本号、沿用原名 | ❌ 不合规 | 禁止 |

> HMCL 商标注册状态未核实，不要依赖"未注册所以随便用"的假设——独立名是唯一零风险解。

### 2.3 与上游"身份改造"的实现差异（实测要点）

- **`Metadata.VERSION` 不是写死的字符串**：v3.16.4 中它是
  `System.getProperty("hmcl.version.override", JarUtils.getAttribute("hmcl.version", "@develop@"))`，
  值来自构建产物 `assets/hmcl.properties` 的 `hmcl.version`，由 `HMCL/build.gradle.kts` 生成。
  → 因此**不要**像旧文档那样在 `Metadata.java` 里改 `VERSION`；版本号在构建配置里定。
- **`Metadata.TITLE` / `FULL_TITLE` 是派生字段**（`NAME + " " + VERSION`、`FULL_NAME + " v" + VERSION`），改 `NAME`/`FULL_NAME` 即可。
- **关于页（`AboutPage.java`）标题是硬编码的** `"Hello Minecraft! Launcher"`（`:58` 字面量），不是读 `Metadata`。
  本步骤**不修改** `AboutPage.java`（否则突破"6 处代码侵入"预算）：上游关于页保留作为归属展示；
  社区版自己的"关于/许可/源码"信息放在社区设置面板的 `about` 分组（[步骤 13](13-首页组件化A-框架搭建.md) §3.10）。
  如后期确需改关于页，必须先在[整体要求 §4.2](../00-整体要求.md#42-改动策略代码侵入-14-处--分级登记)登记新增侵入点（当前预算 14 处，下一处为第 15 处）。

## 3. 详细实施

### 3.1 版本号命名法：独立产品版本（`1.0.0`）

> **v3.16.8 版本调整（2026-10-22）**：产品版本改为 **1.0.0**（`config/project.properties` 的 `versionRoot=1.0`/`buildNumber=0`，无环境变量时 `HMCL/build.gradle.kts` 读取默认值）；上游基线仍为 **v3.16.4**（`hmcl.community.baseline`）。关于页显示 `Version 1.0.0 · based on HMCL v3.16.4`。下文表格与示例已按当前规则更新；其他步骤中的 `3.16.1000` 构建记录是历史产物，不再代表当前版本。

上游构建脚本 `HMCL/build.gradle.kts:25-53` 的实际逻辑（必须按它来，否则版本号会被解析成别的东西）：

```text
VERSION_ROOT = env VERSION_ROOT ?? config/project.properties 的 versionRoot(=3.16) ?? "3"
BUILD_NUMBER = env BUILD_NUMBER
  有 BUILD_NUMBER → "$VERSION_ROOT.$BUILD_NUMBER"
  无 BUILD_NUMBER → "$VERSION_ROOT.SNAPSHOT" / "$VERSION_ROOT.dev-<sha>" / "$VERSION_ROOT.unofficial-<sha>"
```

本项目定案：

| 项 | 值 | 说明 |
|---|---|---|
| `VERSION_ROOT` | `1.0` | 产品版本主段；**不再与上游 release 号绑定**，上游基线由 `hmcl.community.baseline` 单独记录 |
| `BUILD_NUMBER` | `0 + 发版序号` | 首版 `0` → 产品版本 `1.0.0`；后续 `1.0.1`、`1.0.2`… 单调递增；上游基线仍为 `v3.16.4` |
| 社区标识 | **不进版本号** | "社区版"写在窗口副标题/关于弹窗/发布页，避免 `version` 解析与迁移比较被污染 |

### 3.1.1 构建期注入上游基线（`hmcl.community.baseline`）

关于分组要显示"基于 HMCL v3.16.4（commit fbcc1747…）"，但 `Metadata` 只暴露 `VERSION`/`GITHUB_SHA`（后者来自 CI 的 `GITHUB_SHA`，开发机构建时为 null）。做法：在 `HMCL/build.gradle.kts` 的 `hmclProperties` 里追加 2 行（属 §4.2 的"构建脚本"登记，不占代码 4 处）：

```kotlin
// HMCL/build.gradle.kts:155-166 的 buildList 内
val upstreamBaseline = System.getenv("UPSTREAM_BASELINE") ?: "v3.16.4"
add("hmcl.community.baseline" to upstreamBaseline)
add("hmcl.community.baseline.commit" to (System.getenv("UPSTREAM_BASELINE_COMMIT") ?: "fbcc17472f08e877d60d6b715734e8054e9e61ee"))
```

CI 发版时由 workflow 从 `patches/BASELINE.txt`（步骤 01）读值并通过 env 传入；本地构建落到默认值，仅影响"关于"展示，不影响更新判断。

读取口（03 交付，13 §3.10 的 `about` 分组直接调）：

```java
package org.jackhuang.hmcl.community;

/// 社区版对外展示的元信息；只读、无 IO、无异常。
public final class CommunityMetadata {
    public static String productName();      // Metadata.NAME（03 的代码侵入点）
    public static String version();          // Metadata.VERSION（构建期 hmcl.version）
    public static String baseline();         // hmcl.community.baseline，缺失 → "unknown"
    public static String baselineCommit();   // hmcl.community.baseline.commit，缺失 → "unknown"
    public static String sourceUrl();        // 常量：源码仓库地址（发布前替换为真实 URL）
    public static String licenseUrl();       // 常量：LICENSE-ADDITIONAL-TERMS.md 的仓库内路径
}
```

> 实现用 `JarUtils.getAttribute("hmcl.community.baseline", "unknown")`（与 `Metadata.VERSION` 同源，读 `assets/hmcl.properties`），不要新增配置文件。

理由：

- 上游 `VersionNumber.asVersion` / `compare` 与 `isIntVersionNumber` 会解析、比较版本串（边界已在 §6 核对），纯数字段 `3.16.<构建号>` 最安全；
- 产品版本与上游版本解耦：`1.0.0` 不再需要 `1000+` 段来避免与 `3.16.x` 撞号，上游基线只作为“基于 HMCL v3.16.4”展示；
- 发版脚本从 tag（如 `v1.0.0`）取 `BUILD_NUMBER`，`VERSION_ROOT` 从 `config/project.properties` 或 tag 前缀取，二者都进构建环境变量。

本地验证（无需改任何代码）：

```bash
# 仅改 jar 内版本属性：必须重新构建才能进 assets/hmcl.properties
VERSION_ROOT=1.0 BUILD_NUMBER=0 ./gradlew :HMCL:shadowJar
# 运行期临时覆盖版本（不重构建）：Metadata 读 hmcl.version.override
java -Dhmcl.version.override=1.0.0 -jar HMCL/build/libs/HMCL-1.0.0.jar
```

> `-Dhmcl.version.override` 只影响运行时显示（版本提示/日志），不改变产物文件名与更新判断——用于"身份改造后立刻看标题"的冒烟测试。

### 3.2 身份字段：唯一代码改动 `Metadata.java`

文件：`HMCL/src/main/java/org/jackhuang/hmcl/Metadata.java`。v3.16.4 中需要改的字段（其余保持上游原值）：

| 字段 | 上游值 | 本项目目标值 |
|---|---|---|
| `NAME` | `"HMCL"` | `LMCL`（英文短名，用于窗口标题/崩溃前缀） |
| `FULL_NAME` | `"Hello Minecraft! Launcher"` | `Lumina Minecraft Launcher`（可含 "based on HMCL"） |
| `PUBLISH_URL` | `"https://hmcl.huangyuhui.net"` | `"https://www.kerzeftu.top/lmcl"`（**必改**：关于页、帮助、法务链接都用它；用户确认的官网地址，`DOWNLOAD_URL` 自动派生） |
| `MANUAL_UPDATE_URL` | `"https://github.com/HMCL-dev/HMCL/releases"` | 首发 `= PUBLISH_URL`（仓库未创建，Releases 页暂无；建仓后改为 Releases 页，**必改**） |

不需要改、也不要改：

- `VERSION`（见 3.1，构建期生成）；
- `HMCL_UPDATE_URL`：代码保持上游写法的 `System.getProperty("hmcl.update_source.override", PUBLISH_URL + "/api/update_link")`；运行期由步骤 05 的 `CommunityBootstrap` 固定为官网，**不要**把它改成常量或指向仓库；
- **本步不处理"检查更新"**：上游链路已被 05 结构性禁用；用户可见的更新提示由 `community.update.CommunityUpdateNotifier`（05 §4.3）独立读取 Releases API，仓库未建时 `CommunityMetadata.GITHUB_REPO`/`GITEE_REPO` 留空；
- `BUILD_CHANNEL`（由 `hmcl.version.type` 决定，保持上游构建配置即可）；
- `MINIMUM_REQUIRED_JAVA_VERSION=17`、`RECOMMENDED_JAVA_VERSION=21` 等运行约束。

改完后的派生值应满足：

```text
TITLE      = LMCL 1.0.0
FULL_TITLE = Lumina Minecraft Launcher v1.0.0
```

> 说明：`NAME` 决定崩溃报告标题、日志中的产品标识、窗口标题；`PUBLISH_URL` 决定帮助/关于/法务跳转。两者必须一起改，否则会出现"标题是新的、点关于跳到上游"的割裂。

### 3.5 崩溃报告标题

崩溃报告里出现产品名的地方（`CrashReport` / `CrashReporter` 的标题常量、游戏崩溃窗口标题）：

```bash
grep -rn "Hello Minecraft\|Crash Report" --include=*.java HMCL HMCLCore | grep -v build
```

处理原则：**只改字符串常量，不重写崩溃处理链**（崩溃上报逻辑在步骤 05 被整体关闭）。改后必须实测一次人为崩溃：能弹窗、能写出日志、标题正确。若涉及的字符串来自 i18n（`crash.*`），改 `assets/lang/I18N*.properties` 对应值（资源改动，不占代码侵入）。

### 3.6 许可证文件

仓库根目录（沿用上游 `LICENSE` 不动，新增我们自己的附加条款记录）：

```text
LICENSE                     # GPLv3 全文，一字不改（上游已提供）
LICENSE-ADDITIONAL-TERMS.md # 附录 A 条款原文，一字不改地上抄
```

`LICENSE-ADDITIONAL-TERMS.md` 必须**原样**抄录开发包附录 A 的条款文本（条款标题、编号、生效条件全部保留），**不要改写/精简/重新编号**——改写可能被解释为"新增附加要求"。

### 3.7 修改声明（GPLv3 第 5(a) 条）

只对**实际改过的上游文件**加声明（本步骤只有 `Metadata.java`；后续步骤会改 `MainPage.java`、`LauncherHelper.java`）：

```java
/*
 * Modified by <Project> team on 2026-10-21:
 *   - product name and publish URLs changed to <Project>
 * See https://github.com/<org>/<repo>/commits for full history.
 */
```

识别改动文件的脚本（基线分支固定 `release/3.16`）：

```bash
git diff --name-status upstream/release/3.16..main -- HMCL HMCLCore HMCLBoot
```

> 不要给所有文件批量加头：会让后续同步 diff 噪音爆炸，也会破坏"只改必要文件"的合规叙事。

## 5. 风险与应对

| 风险 | 等级 | 应对 |
|---|---|---|
| 版本号写成 `1.0.0-community.N` 被上游解析/迁移逻辑拒绝 | **中高** | 坚持纯数字段 `1.0.<构建号>`（如 `1.0.0`）；上线前跑 `VersionNumber.isIntVersionNumber`/`compare` 单测（§6 已核对事实） |

## 6. 版本号相关事实（v3.16.4 已核对，无需再等实测）

1. **解析 API**：上游没有 `VersionNumber.parse`，公开入口是 `VersionNumber.asVersion(String)` / `VersionNumber.compare(String, String)`，另有 `isIntVersionNumber(String)`（`HMCLCore/src/main/java/org/jackhuang/hmcl/util/versioning/VersionNumber.java:38-70`）。`"1.0.0"` 由纯数字段组成，`isIntVersionNumber` 为 true，`asVersion` 可解析；`compareTo` 见同类 :106-126，逐段数值比较，`1.0.1 > 1.0.0`。写代码时补一个 JUnit：`assertTrue(VersionNumber.compare("1.0.1", "1.0.0") > 0)` 与 `isIntVersionNumber("1.0.0")`。
2. **配置迁移不看启动器版本**：`LegacyConfigMigrator.java:60-61` 只认旧文件的整数 `_version`（`LEGACY_CURRENT_CONFIG_VERSION = 2`），并在 :184-192 明确"新设置格式另用版本方案、不得依赖该数值"；`SettingsManager.java:1202` 才触发迁移。全仓没有用 `Metadata.VERSION` 与旧配置版本做比较的迁移逻辑 → **改版本号不会触发/阻断迁移**。
3. **更新检查确实读 `Metadata.VERSION`**：`UpdateChecker.java:50-52` 对 remote 版本做 `VersionNumber.compare(Metadata.VERSION, latest.version()) < 0`，`:44` 还会对 dev 通道特判 → 若忘了禁用更新，`1.0.0` 可能被判"低于上游最新"而提示，也可能因 `isDevelopmentVersion` 走夜间通道分支。步骤 05 的"更新源指向自有 JSON + 强制完整性校验"必须在上线前验证 `UpdateChecker` 不会访问上游（抓包断言，见 05 §6）。
