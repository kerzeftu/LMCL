## 1. 目标

用户需求：m03806（默认不内置下载源，允许自定义）、m12016（把内置源删干净）、m12351（确保设置里的源真正生效，打包附样例）、m12994（不再分主源/镜像，最多 5 个平级源，下载时自动测速排序，样例至少 3 个源）、m15125（Modrinth/CurseForge 官方端地址必须内置）。

1. **零内置**：全新安装、未配置任何源时，Minecraft 版本列表与游戏文件下载都**不能**访问 Mojang/BMCLAPI 或任何第三方源；必须由用户添加至少一个源。例外是 Modrinth/CurseForge 插件 API/CDN（协议端点，见 §3.2.1），它们不参与游戏下载源选择。
2. **平级源**：配置里最多 5 个源，**没有主源/镜像概念**，顺序只表示“用户添加顺序”；写出 schema 2 的 `sources` 数组，并兼容读取 v1 的 `primary`+`mirrors`。
3. **自动测速**：进入下载入口（侧栏 [下载]、管理页“新建实例”、主页启动卡空态“新建实例”）时，如果测速缓存超过 5 分钟，就在 `Schedulers.io()` 上并行探测全部源的 `/mc/game/version_manifest.json`，按“可用优先、延迟升序”重建 provider 候选链；失败的源排最后。
4. **手动测速排序**：设置 → 下载提供 [测速排序] 按钮，显示每个源的毫秒延迟，并按同一规则重排界面行；该操作只改 UI，点 [保存并应用] 才落盘。
5. **前置拦截**：未配置时进入下载入口先弹“先配置下载源”，提供 [去设置]，不让后台任务抛异常堆栈。
6. **保存即生效**：保存后写盘、重建 provider，并断言 `CommunityDownloadGuard.isConfigured() == !sources.isEmpty()`；不一致直接报保存失败。
7. **零侵入上游下载枚举的语义**：上游 `versionListSource` / `fileDownloadSource` 字段保留以兼容旧配置，但**不再影响实际 provider**；下载设置页不再暴露这两个三档下拉框。
8. UI 复用 HMCL 原生控件（`ComponentList`/`LinePane`/`JFXTextField`/`MessageDialogPane`），不引入新框架。

### 2.3 为什么需要 `MissingDownloadProvider`

`AutoDownloadProvider` 在构造时对空候选列表抛 `IllegalArgumentException`；而版本列表入口 `GameVersionList` 直接取 `downloadProvider.getVersionListURLs()`。所以“零内置”不能靠传空列表，必须有一个**明确失败**的 provider：

```java
static DownloadProvider build(CommunityDownloadSources sources) {
    if (sources.isEmpty()) return new MissingDownloadProvider();
    List<DownloadProvider> providers = ...;   // 只含用户配置的源，无官方
    return new AutoDownloadProvider(providers, List.copyOf(providers));
}
```

`MissingDownloadProvider`：`getVersionListURLs()` 返回 `List.of()`，`getVersionListById(...)` 返回 `MissingVersionList`，`injectURL`/`injectURLWithCandidates` 对普通地址抛 `CommunityDownloadSourceMissingException`，`getConcurrency()` 返回 1。v3.16.2 起，这两个入口先检查 `CommunityAddonSources.isBuiltinAddonUrl(url)`：Modrinth/CurseForge 的 4 个官方 HTTPS 主机直接返回原地址/候选，其余（包括 Mojang、BMCLAPI、第三方）仍失败。

### 2.4 安装时机

| 时机 | 代码 | 说明 |
|---|---|---|
| 侧栏构造 | `CommunitySideBar` 构造 `try { CommunityDownloadInstaller.install(); }` | 早于用户点“下载/设置” |
| 首页挂载 | `CommunityDashboard.mount()` 最前 `install()` | 兜底；早于 `community.dashboard.enabled` 判断 |
| 下载入口 | `CommunityDownloadGuard.requireConfigured()` 在缓存 false 时再试 `install()` | 防止设置初始化顺序或异常导致未安装 |

`install()` 幂等：把上游两个 source 属性监听注册在自己身上，然后 `apply()`；`apply()` 读取 `CommunityDownloadSources.load()`、`wrapper.setProvider(...)`、`CommunityDownloadGuard.refresh(!sources.isEmpty())`，并触发一次受 TTL 限制的 `CommunityDownloadRanker.refreshAsync(false)`。

### 2.5 上游设置页的处置

`DownloadSettingsPage` 顶部嵌入社区编辑器，删除三档 `LineSelectButton`，保留 `defaultAddonSource` 卡片（第 4 处代码侵入，2026-10-22 批准）。`LauncherSettingsPage` 的“下载”tab 仍指向上游页面，因此用户从设置进入即可看到社区编辑器；缓存目录、下载线程、代理等其它上游设置保持不变。

## 3. 方案设计

### 3.1 需求 → 实现映射

| 需求 | 实现 |
|---|---|
| 零内置 | `DownloadProviders` 删除静态源，初始 `MissingDownloadProvider`；`CommunityDownloadProvider.of(empty)` 返回 Missing；仅放行插件 API/CDN（§3.2.1） |
| 最多 5 个平级源 | `CommunityDownloadSources(List<CommunityDownloadSource>)`；`MAX_SOURCES=5`；解析与保存双重校验 |
| 自动测速排序 | `CommunityDownloadRanker.refreshAsync` 并行探测；`order(sources)` 应用缓存顺序；实际 provider 重建后立即生效 |
| 无兜底 | 不构造 `MojangDownloadProvider`；空配置返回 Missing |
| 未配置提前拦截 | `CommunityDownloadGuard.requireConfigured(owner)`：三处入口 + “去设置” |
| 保存立即生效 | `save()` → IO 写盘 → `apply()` → 断言 → 回 FX 显示 |
| 持久化 | `community-settings.json` 的 `downloadSources` 段（`CommunitySettings.section/putSection`） |
| UI | `CommunityDownloadSettingsPane` 嵌入上游下载设置页；社区设置面板 `download` 分组复用同一编辑器 |
| 迁移 | 读取 v1 `primary`/`mirrors` 时合并为平级列表；写出统一 schema 2 |

### 3.2 候选链构建

```java
static DownloadProvider build(CommunityDownloadSources sources) {
    return CommunityDownloadProvider.of(CommunityDownloadRanker.order(sources.sources()));
}
```

`CommunityDownloadProvider.of` 对每个源构造 `BMCLAPIDownloadProvider`，再构造 `AutoDownloadProvider(providers, List.copyOf(providers))`。`AutoDownloadProvider` 的版本列表候选取并集（去重、保序），`injectURL` 取首个候选；因此“第一个源”是当前测速最快的源。**没有任何官方源可回退**，所有候选失败时任务失败并显示缺源/下载错误。

### 3.3 自动测速排序

| 项 | 规则 |
|---|---|
| 触发点 | `CommunityDownloadInstaller.apply()`（安装/保存/上游设置变化）、`CommunityDownloadGuard.requireConfigured()` 已配置分支 |
| TTL | `CommunityDownloadRanker.TTL_MILLIS = 5 分钟`；TTL 内重复调用直接返回 |
| 单飞 | 同一时刻只允许一个测速任务；`running=true` 时后续调用直接返回 |
| 探测 | 并行 `GET <url>/mc/game/version_manifest.json`；连接/请求超时 5 秒；2xx 视为可用；丢弃响应体 |
| 排序 | 可用源按延迟升序；失败源按原配置下标排在最后；`rank(probes)` 为纯函数，可单测 |
| 缓存 | 只存内存 `rankedUrls`；应用重启后重新测速；配置顺序是永久兜底 |
| 生效 | 测速完成后 `CommunityDownloadInstaller.applyRanked()` 重建 provider；正在进行的下载继续使用旧实例，不受影响 |
| 线程 | 探测在 `Schedulers.io()`；UI 回调在 `Schedulers.javafx()`；不阻塞 FX |

**已知时序边界**：自动测速是异步的。如果用户在测速完成前立刻开始下载，本次下载会使用“上一次排序/配置顺序”；测速完成后只影响后续下载。文档接受该偏差，因为阻塞下载入口等待测速会明显拖慢弱网启动。手动 [测速排序] 可让用户立即看到结果。

### 3.4 拦截与生效校验

```java
// 入口
if (!CommunityDownloadGuard.requireConfigured(owner)) return;

// 保存（IO 线程）
sources.save();
CommunityDownloadInstaller.apply();
if (CommunityDownloadGuard.isConfigured() != !sources.isEmpty()) {
    throw new IllegalStateException("Configured download sources were not applied");
}
```

- `requireConfigured` 弹 `MessageDialogPane`：说明“LMCL 不内置任何下载源”，[去设置] 打开 `CommunitySettingsPanel.open(owner, "download")`，[取消] 关闭；
- 已配置时，`requireConfigured` 还会调用 `CommunityDownloadRanker.refreshAsync(false)`，实现“进入下载入口自动测速”；
- 保存失败时 UI 显示 `save_failed`，不显示成功文案；日志带 `[CommunityDownload]` 上下文；
- 未配置时 `DownloadProviders.localizeErrorMessage` 把缺源异常转为可读文案，避免 `IllegalStateException` 堆栈。

### 3.5 存储 schema（`community-settings.json`）

```json
{
  "downloadSources": {
    "schema": 2,
    "sources": [
      { "name": "BMCLAPI", "url": "https://bmclapi2.bangbang93.com" },
      { "name": "BMCLAPI 主控", "url": "https://openbmclapi.bangbang93.com" },
      { "name": "BMCLAPI 备用", "url": "https://bmclapi.bangbang93.com" }
    ]
  }
}
```

解析规则：

- 优先读 `sources` 数组；缺失时按 v1 的 `primary` + `mirrors` 顺序合并，迁移为平级源；
- 非法条目丢弃；重复地址保留第一次；超过 5 个丢弃并 WARNING；
- 未知字段忽略；`schema` 仅记录；
- `name` 可缺省（默认主机名）；UI 不单独提供名称输入，保存时按 URL 复用旧名称。

### 3.6 校验规则

| 规则 | 行为 |
|---|---|
| 空地址 | 该行跳过；全部为空 = 保存“0 个下载源”，下次下载被守卫拦截 |
| 无协议 | 自动补 `https://` |
| 非 `http(s)` / 无主机名 | 拒绝：`community.settings.download.error.invalid` |
| 超长 | 地址截断 2048、名称截断 64 |
| 重复 | 拒绝：`community.settings.download.error.duplicate` |
| 超过 5 个 | 拒绝 + [添加源] 禁用：`error.too_many` |

### 3.10 失败降级

| 场景 | 行为 |
|---|---|
| `getDownloadProvider()` 不是 wrapper（上游改结构） | 记 WARNING，不安装；下载入口守卫仍会提示未配置 |
| 配置损坏/不可写 | `load()` 返回空 → Missing；保存失败只提示，不影响当前已生效 provider |
| 测速全部失败 | 排序结果按原配置顺序，仍会尝试所有源；首源失败由 `AutoDownloadProvider` 继续下一个 |
| 测速期间再次请求 | `running=true`，直接返回；不叠加任务 |
| 自定义源 5xx/超时 | `AutoDownloadProvider` 按候选顺序尝试下一个；全部失败则任务失败，**不回退官方** |
| 第三方源证书错误 | JVM 默认 TLS 拒绝；不绕过 |
| 安装异常 | 侧栏/首页/守卫都只 WARNING，不阻塞启动 |

### 3.11 线程与并发

- `CommunityDownloadRanker.refreshAsync` 可在任意线程调用；探测在 `Schedulers.io()`；
- 结果写回使用 `synchronized(LOCK)`；`rankedUrls`/`testedAt` 为 `volatile`；
- 排序完成后 `applyRanked()` 在测速完成线程重建 provider，`DownloadProviderWrapper.setProvider` 是引用替换，不阻塞下载；
- UI 的测速结果与消息通过 `Schedulers.javafx()` 回 UI 线程。

### 10.3 运行时序

1. 用户进入下载入口（侧栏下载 / 管理页新建实例 / 主页启动卡新建实例）；
2. `CommunityDownloadGuard.requireConfigured()` → `markDownloadEntry()` + `refreshAsync(true)`；
3. 页面/任务继续构造请求；一旦 `RankingDownloadProvider` 的任一方法被 IO 线程调用，`awaitBeforeDownload()` 看到 pending 或 running，等待本轮测速（最多 12 s）；
4. `CommunityDownloadRanker` 完成探测 → 计算顺序 → **若设置页不可见**写回 `downloadSources` → `applyRanked()` 重建 provider；
5. 等待方返回，真正的文件 GET 开始。

TTL/会话规则：

- 测速结果 5 分钟内有效；进入下载入口强制刷新；
- provider 空闲 ≥2 分钟后，第一次调用视为新会话，同样等待一轮；
- 设置页正开着时，后台排序只改内存顺序，不写盘，避免覆盖用户正在编辑的地址；
- 12 秒超时后按当前顺序继续，不永久阻塞下载。

### 10.4 自动保存规则与防误删

- 地址修改、增删源、单项 [测试]、导入都触发；停止输入 0.7 s 后保存；
- 只要还有空白输入行（刚点 [添加源] 尚未填），自动保存静默跳过，避免把“待填写”当作删除；
- 手动 [保存并应用] 仍可立即保存并强制测速；[清除所有源] 仍可清空；
- 保存顺序用 `saveSequence` 单调递增，旧快照晚到不会覆盖新配置；旧快照只复位忙碌标记。

### 10.6 手工验收（需 Windows 桌面）

1. 设置 → 下载：改一个源地址，等约 1 s，出现“已自动保存并应用 (N 个下载源)”；
2. 点某行 [测试]，成功后该行自动保存；再点 [保存并应用] 仍可强制测速；
3. [添加源] 出空行时不保存；填入 URL 后自动保存；删除一行自动保存；
4. 点 [测速排序]：滚动位置基本不变，排序完成后自动保存并提示；
5. 清空所有源保存，点侧栏 [下载]：仍弹“尚未配置下载源”，[去设置] 落到 设置 → 下载；

### 10.7 偏差与风险

- 未在 Windows GUI 实机验证；防抖手感、输入法/粘贴、12 s 超时和滚动恢复都依赖真实桌面；
- 自动保存是“尽力而为”：空白行跳过、非法 URL 跳过，用户可能看不到失败提示；手动保存仍会显示校验错误；
- 后台测速写回顺序会改变 `downloadSources.sources` 顺序；设置页打开时跳过写盘，是“避免覆盖编辑”的折中；
- `RankingDownloadProvider` 在 FX 线程只触发不阻塞，因此“构造 URL”类调用不会卡 UI，但也不会保证该次构造使用最新排序；
- 若上游重构 `DownloadProvider` 接口，需同步 `RankingDownloadProvider` 的委托方法。

### 10.8 回退

1. 删除 `RankingDownloadProvider` 的包装（`CommunityDownloadInstaller.applyInternal` 不再包一层），下载恢复为立即开始；
2. 删除 `CommunityDownloadSettingsPane` 的 `autoSaveTimer`/`onSourcesEdited`/`persist` 自动分支，恢复手动保存；
3. 删除 `CommunityDownloadRanker.persistRanking`，排序只影响内存；
4. 删除 `speedTestAndSort` 的滚动捕获/恢复与原地 `Collections.swap`，恢复 v3.14 行为；
5. 以上回退都不影响已落盘的 `downloadSources` schema 2 数据。

## 11. v3.16.2 内置插件端点例外（实现记录）

### 11.1 问题

用户 m15125 指出：进度条风格可以继续，但 Modrinth / CurseForge 的地址必须内置。此前 v3.12 的“零内置”把 `MissingDownloadProvider` 的所有 `injectURL` 都改成抛异常；插件仓库（Modrinth/CurseForge）在未配置游戏下载源时也会走同一个 provider，因此搜索、项目详情和文件下载全部失败。

### 11.2 边界

- 零内置仍然只针对 **Minecraft 游戏下载**：版本清单、游戏 jar、libraries、assets、加载器；
- Modrinth/CurseForge 是**插件协议端点**，不属于用户可替换的 BMCLAPI 兼容镜像；
- 只按主机白名单放行，不按 URL 前缀，避免 `api.modrinth.com.evil.example` 之类后缀欺骗。

### 11.3 实现

新增 `HMCL/src/main/java/org/jackhuang/hmcl/community/download/CommunityAddonSources.java`：

```java
public static final String MODRINTH_API = "https://api.modrinth.com";
public static final String MODRINTH_CDN = "https://cdn.modrinth.com";
public static final String CURSEFORGE_API = "https://api.curseforge.com";
public static final String CURSEFORGE_CDN = "https://edge.forgecdn.net";

private static final Set<String> BUILTIN_HOSTS = Set.of(
        "api.modrinth.com", "cdn.modrinth.com",
        "api.curseforge.com", "edge.forgecdn.net");

public static boolean isBuiltinAddonUrl(String url) {
    // 只接受 https + 精确 host；URI 解析失败返回 false
}
```

`MissingDownloadProvider.injectURL` / `injectURLWithCandidates` 先调用该判断；命中时返回原地址或 `List.of(URI.create(baseURL))`，未命中继续抛缺源异常。`CommunityDownloadGuard` 仍按“有没有游戏下载源”拦截下载入口；插件页不在守卫范围内，因此这里只恢复端点可达性，不改变未配置源的提示。
