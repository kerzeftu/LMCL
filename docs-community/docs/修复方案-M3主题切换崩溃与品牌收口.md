## 1. 结论摘要

### 1.1 崩溃不是 M3 主题或 m3fx 的问题

崩溃发生在 `DecoratorController.applyVisualTheme()` 切换外壳内容时：

```text
java.lang.IndexOutOfBoundsException: toIndex = 1
  at javafx.collections.ModifiableObservableListBase.subList(...)
  at com.sun.javafx.binding.ContentBinding$ListContentBinding.onChanged(ContentBinding.java:123)
  at javafx.beans.binding.ContentBinding$ListContentBinding...
  at org.jackhuang.hmcl.ui.decorator.DecoratorController.applyVisualTheme(DecoratorController.java:163)
  at org.jackhuang.hmcl.ui.main.PersonalizationPage.applyVisualTheme(PersonalizationPage.java:356)
```

根因是 **先把 `shell` 从 `Decorator` 的绑定目标中“意外”摘掉，再对绑定源执行 `setAll`**，导致 JavaFX 的 `Bindings.bindContent` 在“源仍报告移除 1 个元素、目标已经为空”时越界。M3 主题只是触发了这次外壳替换；即使点击「M3（关闭玻璃）」，从 Classic 首次切换也会走同一条路径。

### 1.2 品牌收口这次只做两个直接可见点

| 位置 | 现状 | 目标 |
|---|---|---|
| 崩溃报告头 | `---- Hello Minecraft! Crash Report ----` | `---- Lumina Minecraft Launcher Crash Report ----` |

范围说明：

- 全称统一取 `Metadata.FULL_NAME`，当前值就是 `Lumina Minecraft Launcher`；不再散落新的字面量。
- 英文、简体中文、繁体中文、日文四份翻译中**已经出现的** `Hello Minecraft! Launcher` / `Hello Minecraft！ランチャー` 一并替换。

## 2. 崩溃根因

### 2.1 关键代码

`HMCL/src/main/java/org/jackhuang/hmcl/ui/decorator/DecoratorController.java:152-167`：

```java
public void applyVisualTheme() {
    if (m3Host != null) {
        m3Host.setContent(null);
        m3Host.dispose();
        m3Host = null;
    }

    if (M3Settings.isM3Enabled()) {
        m3Host = new M3Host(shell);                 // ← 先把 shell 放进新 M3Host
        decorator.getContent().setAll(m3Host);      // ← 再改绑定源；崩溃点
    } else {
        decorator.getContent().setAll(shell);
    }
}
```

`HMCL/src/main/java/org/jackhuang/hmcl/community/ui/m3/M3Host.java:56-70`：

```java
public M3Host(@Nullable Node content) {
    ...
    setContent(content);
    ...
}

public void setContent(@Nullable Node content) {
    if (content == null) {
        getChildren().clear();
    } else {
        getChildren().setAll(content);              // ← 把 shell 从旧父节点移走
    }
}
```

`HMCL/src/main/java/org/jackhuang/hmcl/ui/decorator/DecoratorSkin.java:177`：

```java
Bindings.bindContent(contentPlaceHolder.getChildren(), skinnable.contentProperty());
```

`Decorator.getContent()` 返回的是 `content.get()`，也就是 `ListProperty` 当前持有的 `ObservableList<Node>`；`contentPlaceHolder.getChildren()` 是绑定目标。

### 2.2 实际状态变化

初始 Classic 启动时，`DecoratorController` 构造里先调用一次 `applyVisualTheme()`，此时 `Decorator` 还没装 skin，绑定尚未建立，所以这条路径安全：

| 对象 | 状态 |
|---|---|
| `decorator.getContent()` | `[shell]` |
| `contentPlaceHolder.getChildren()` | `[shell]`（skin 安装后绑定建立） |

用户点击 M3 Expressive 后：

1. `new M3Host(shell)` 的 `getChildren().setAll(shell)` 把 `shell` 从 `contentPlaceHolder.getChildren()` 摘走。JavaFX 自动改父节点，这一步不会经过 `Decorator` 的绑定源。
2. 此时绑定目标变成 `[]`，但绑定源仍是 `[shell]`。
3. `decorator.getContent().setAll(m3Host)` 对绑定源发出“移除 `shell`”的变更；`ContentBinding.ListContentBinding` 执行 `dest.subList(0, 0 + 1).clear()`，而 `dest` 已经是空列表，于是 `toIndex = 1` 越界。
4. 崩溃发生在 JavaFX 事件线程，启动器弹出错误窗口。

### 2.3 为什么不是每次切换都崩

| 切换 | 是否崩 | 原因 |
|---|---|---|
| Classic → M3 Expressive | 崩 | `shell` 先被 `M3Host` 摘走，绑定目标先空，再 `setAll` |
| Classic → M3（关闭玻璃） | 崩 | 同上，`isM3Enabled()` 同样为 true |
| M3 Expressive → Classic | 不崩 | `m3Host.setContent(null)` 只把 shell 从 M3Host 摘走；绑定源/目标仍是 `[m3Host]`，`setAll(shell)` 时目标大小仍为 1 |
| M3 Expressive → M3（关闭玻璃） | 不崩 | 旧 M3Host 仍在绑定源/目标；新 host 没有先摘走 shell，目标大小仍为 1 |
| 重启后直接进入 M3 | 不崩 | 构造函数里的 `applyVisualTheme()` 发生在 skin 绑定建立之前 |

所以用户从默认 Classic 首次点 M3 时必现；点 M3 → Classic 再点 M3 也会再次必现。

### 2.4 为什么之前没测出来

- 之前的验证只做到 `:HMCL:compileJava`、单测、打包，WSL2 没有 Windows GUI，没有做过“Classic 首次切 M3”的点击验证。
- 没有覆盖 `Bindings.bindContent` 与 `Parent.getChildren()` 改父节点交互的回归测试。
- 这说明缺口不只是代码，还包括“主题切换”这项验收没有进入 Windows 手工清单。修复方案里会同时补测试矩阵。

## 3. 修复方案

### 3.1 推荐方案：先换宿主，再放入 shell

不先构造带内容的 `M3Host`，而是：

1. 创建一个空的 `M3Host`；
2. 在 `shell` 仍属于旧绑定目标时，对绑定源 `setAll(emptyHost)`；此时目标大小仍为 1，移除 `shell`、加入空宿主都安全；
3. 再把 `shell` 放进新宿主；这时 `shell` 的旧父节点已被第 2 步移除，不会再触发绑定事件。

示意代码（最终以实现为准）：

```java
public void applyVisualTheme() {
    if (m3Host != null) {
        m3Host.setContent(null);
        m3Host.dispose();
        m3Host = null;
    }

    if (M3Settings.isM3Enabled()) {
        M3Host next = new M3Host();                 // 空宿主，不碰 shell
        decorator.getContent().setAll(next);        // shell 仍在旧目标中，安全移除
        next.setContent(shell);                     // 此时 shell 已无父节点
        m3Host = next;
    } else {
        decorator.getContent().setAll(shell);
    }
}
```

要点：

- `next` 先不赋给 `m3Host`，等 `setContent(shell)` 成功后再赋值；`setContent` 抛异常时不会留下“半切换”的字段状态。
- 如果希望增加恢复能力，可在 `try/catch` 中失败后 `decorator.getContent().setAll(shell)` 并 `next.dispose()`；但第一阶段先用最小改动，避免把异常吞掉。
- 不采用“先 `m3Host.setContent(null)` + `decorator.getContent().clear()` + 再 `new M3Host(shell)`”的变体：它能避免崩溃，但会短暂把内容清空，且多一次无意义布局；推荐方案不需要清空。

### 3.2 需要覆盖的回归矩阵

| # | 操作 | 预期 |
|---|---|---|
| 1 | 默认 Classic 启动，点 M3 Expressive | 不崩溃；M3 玻璃生效；当前页面保留 |
| 2 | Classic → M3（关闭玻璃） | 不崩溃；无玻璃；当前页面保留 |
| 3 | Classic → M3 Expressive → Classic → M3 Expressive，连续 10 次 | 不崩溃；无空壳、无重复侧栏 |
| 4 | 在设置页、下载页、其他页分别切换 | 页面不重建；滚动位置尽量保留 |
| 5 | 已保存 M3，重启 | 直接进入 M3；不崩溃 |
| 6 | 切换后打开模态框/对话框，再关闭 | 对话框层级正常；无 `shell` 双父节点异常 |
| 7 | 切换后最小化/恢复、改变窗口大小 | 布局/玻璃不闪烁；侧栏选中态正常 |
| 8 | 自定义主题包选中时切换视觉主题 | 自定义主题包选择不被清掉 |

### 3.3 测试与静态检查

- `:HMCL:compileJava`、`:HMCL:checkTranslations`。
- community 测试与全量测试；本次没有合适的无头 JavaFX 绑定测试，先不虚报新增 UI 单测。
- Windows 实机按 3.2 手工执行；这是本次唯一能覆盖真实 `Parent`/`Scene` 行为的验收。
- 若后续要加自动化：可把“内容交换”抽成不依赖 `Decorator` 的纯列表/绑定辅助类，用 `ObservableList` + `Bindings.bindContent` 做无 GUI 单元测试，模拟“先改父节点、再 setAll”的顺序，断言不越界。该测试只能证明绑定层，不替代 Windows 点击验收。
