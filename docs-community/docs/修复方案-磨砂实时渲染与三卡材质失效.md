# 磨砂材质实时渲染与三卡材质失效：纵览与修复方案

> 文档版本：v1.0（已落地 R1，待 Windows 实机验收）
> 编写日期：2026-11-01（同日实现修订）
> 基线：LMCL 1.0.0 / HMCL v3.16.4；当前代码与文档状态 **v3.17.25（m3expressive26）**
> 触发：用户反馈“模糊依然不是实时渲染，问题也都没有修好，先纵览写md”
> 结论先行：**v3.17.24 的“真实背景节点快照 + 16ms 合并刷新”仍是静态快照，不是实时渲染；三卡失效的根因是 1×1 卡内容根铺满后由主题实色背景盖住玻璃，不是 CSS 选择器优先级。v3.17.25 已按 R1（壁纸层实时模糊）落地五层实时 ImageView，并用 MaterialCardSurface 透明守卫修复三卡；最终视觉效果仍待 Windows 实机确认。**

---

## 0. 一句话结论

当前磨砂管线是：

```text
壁纸/背景节点 ──snapshot（一次性）──> 5 张模糊图片 ──viewport 切片──> 每张卡片的 5 个 ImageView
```

它不是“实时渲染”，而是“**缓存快照 + 视口平移**”。视口平移能让卡片滚动时看起来贴着壁纸，但背景内容、壁纸动画、窗口缩放、主题或标题栏变化都不会自动变成实时模糊；`PauseTransition(16ms)` 只是把多次重建合并，不是持续渲染。

三张卡（Java 推荐、下载源、启动健康）目前只能确认：

1. 它们和其他 6 张卡一样经过 `BuiltinWidgets.materialCard(...)`；
2. 它们的根节点都带 `.card`；
3. CSS 里存在“卡片透明”规则，且 `m3-community.css:222` 的 4 类规则已比 `.lmcl-m3 .community-home .card` 更具体；但 `community.css:322` 仍有冗余 3 类规则，运行时是否命中仍需日志确认；
4. `GlassSurface` 是否真的进入 `shown` 状态、视口是否有效、层级是否被遮挡，**没有运行时日志证据**，v3.17.24 也没有在 Windows 实机验收。

因此本轮不再直接堆代码，而是先给出可验证的纵览方案。

## 1. 问题复述与验收口径

### 1.1 用户可见问题

- **P1 实时性**：拖动/缩放窗口、壁纸变化、主题切换时，磨砂层不能像“真正的玻璃”一样持续跟随；当前最多是 16ms 后换一张快照。
- **P2 三卡失效**：主页右栏的“Java 推荐”“下载源”“启动健康”三张 1×1 卡没有磨砂效果，和其余卡片视觉不一致。
- **P3 历史遗留（必须一并回归）**：实例快照框的材质曾出现模糊层位置错位；v3.17.24 改为真实背景节点后仍不能宣称修好，需要在本轮验收矩阵中重新覆盖。

### 1.2 本轮验收口径

| 编号 | 验收项 | 通过标准 |
|---|---|---|
| A1 | 窗口缩放实时性 | 连续拖动窗口边缘时，玻璃层与壁纸边缘不出现 >1 帧的可见错位/黑边；日志显示背景层按帧更新，而不是只在松手后更新 |
| A2 | 滚动/卡片移动 | 滚动主页、拖动组件时，卡片玻璃始终与壁纸对齐；允许视口平移，不允许整块变回不透明兜底 |
| A3 | 三卡可见性 | 三张卡在玻璃主题下均显示五层材质；`-Dlmcl.visual.debug=true` 日志中三卡均为 `shown`，不是 `fallback` |
| A4 | 关闭玻璃/Classic | `visual.glass=off` 与 Classic 主题下卡片恢复实色，不出现透明穿透 |
| A5 | 性能 | 1080p、9 卡、5 层目标 ≥50 FPS；低于阈值自动降级到 3 层或快照兜底，并有日志 |
| A6 | 实机 | Windows 10/11 x64 实机截图 + 日志；WSL2 编译通过不等于验收 |

> 说明：A1 的“实时”只要求**壁纸/背景节点的几何与内容实时**。如果期望“卡片底下正在滚动的 UI 内容也被实时模糊”，那是另一种架构（见 §5 方案 C），成本与风险高一个量级，必须先确认。

### 2.2 当前渲染时序

1. `DecoratorController.applyVisualTheme()` 在 M3 开启时创建 `M3Host`，把 shell 放进去，然后把 `GlassBackdrop` 附着到整个 `Decorator`。
2. `GlassBackdrop.attach()` 查找 `DecoratorSkin` 的 `.lmcl-launcher-background` 节点；监听它的 `layoutBounds` 与 `localToSceneTransform`，并监听窗口宽高、`Themes.background`、场景。
3. 任一触发 → `schedule()` → `PauseTransition(16ms)` → `refresh()`。
4. `refresh()` 计算宿主尺寸，最多 960×640 缩放，调用 `render()`：
   - 先把背景节点按 `localToScene` 偏移画到离屏 Canvas；
   - 对 Canvas 做 5 次 `/3/3/2/2/2` 迭代的 `BoxBlur`（半径 96/64/40/24/12 场景像素，按快照缩放）；
   - 生成 `GlassSnapshot(5 images, scale, origin, padding)`。
5. `GlassSurface.update()` 只做：
   - 取快照；
   - `localToScene` 求视口；
   - 把 5 张图设置给 5 个 `ImageView` 的 `viewport`；
   - 设置 `visible=true`。
6. 滚动卡片时 `localToSceneTransform` 变化，`update()` 重新算 viewport；**不会重建图片**。

这条链路解释了为什么“看起来像贴图”：卡片移动只是换视口，背景本身是冻结的。

### 2.3 当前 CSS 的层级风险（已部分排除）

现有三条相关规则：

```css
/* community.css:322，3 个类；旧规则，仍保留 */
.lmcl-m3-glass .community-material-card > .card {
    -fx-background-color: transparent;
    -fx-border-color: transparent;
}

/* m3-community.css:215，3 个类 */
.lmcl-m3 .community-home .card {
    -fx-background-color: -m3-color-surface-container-low;
    -fx-border-color: -m3-color-outline-variant;
}

/* m3-community.css:222，4 个类；当前真正生效的透明规则 */
.lmcl-m3-glass .community-home .community-material-card > .card {
    -fx-background-color: transparent;
    -fx-border-color: transparent;
}
```

因此 v3.17.24 的 CSS 并不是“只有 3 类、会被同特异度覆盖”：m3-community.css 里的 4 类规则特异度 `(0,4,0)`，高于 `.lmcl-m3 .community-home .card` 的 `(0,3,0)`，且位于其后。**三卡失效不能再用“CSS 只有 3 类选择器”解释。**

仍保留的 CSS 风险：

- `community.css:322` 的旧 3 类规则是冗余的，若有人误删 m3 CSS 的 4 类规则，会退回到同特异度竞争；
- 如果 `.card` 不在 `.community-home` 子树内（或 `.lmcl-m3-glass` 类没有加到 `M3Host`），4 类规则不会命中；
- JavaFX 主题包可能通过行内样式/其他样式表覆盖，需运行时读取 `Region.getBackground()` 验证。

静态审查的结论应改为：**CSS 透明规则在源码层面是正确且更具体的；三卡仍失效时，优先怀疑 `GlassSurface` 的可见性、层级、尺寸/视口，而不是继续加选择器类数。**

### 2.4 为什么三卡可能“独独没有效果”的候选原因

按优先级排列，全部需要日志确认，不能先入为主：

| 编号 | 假设 | 证据/检查点 | 可能修复 |
|---|---|---|---|
| H1 | CSS 透明未命中（低概率） | 4 类规则已存在且比 `.lmcl-m3 .community-home .card` 更具体；仍需运行时打印三卡 `.card` 的 `getBackground().getFills()` 确认 | 删除冗余 3 类规则；若命中的是行内/主题样式，改为更高层作用域 |
| H2 | 三卡 `GlassSurface` 走了 fallback（`NO_SNAPSHOT` / `OUT_OF_BOUNDS` / `NO_SCENE`） | `-Dlmcl.visual.debug=true` 日志；三卡是否出现 `[glass-material] java-recommend fallback=...` | 修宿主生命周期/视口计算 |
| H3 | 三卡 `GlassSurface` 尺寸为 0 或 1×1 布局未稳定 | 日志 `hidden: size WxH`；`getWidth/getHeight` | 让 wrapper 先布局；延迟到 `layoutChildren` 后 update |
| H4 | 玻璃层被内容节点遮挡（层序错误） | 临时给 `GlassSurface` 加红色边框；或看 `getChildren()` 顺序 | `glass.toBack()` / 调整 wrapper 构造顺序 |
| H5 | 三卡内容自身有不透明背景 | 遍历三卡 `region.getBackground()`；检查 `community-source-empty` 等 | 只保留卡片根的透明，内容背景改透明 |
| H6 | 五层 opacity/compact 规则未命中（类名不在同一子树） | 打印 `getStyleClass()`；查 `.lmcl-m3-glass-compact` 是否在 `GlassSurface` 上 | 修选择器或把 compact 类加到 wrapper |
| H7 | 快照/视口坐标偏移，三卡恰好落在图片外或边缘 | 日志 `viewport=null` / `OUT_OF_BOUNDS`；比较 card scene bounds 与 snapshot bounds | 修 `GlassSnapshot.viewport()` 或 padding |

> 当前 H1 已被源码层面部分排除（4 类规则存在且更具体），H2/H3 的嫌疑反而更大；**不能只改 CSS 就宣布三卡修好**。

## 3. 为什么 v3.17.24 仍然不是实时

### 3.1 静态性来自数据模型，不是刷新间隔

`GlassSnapshot` 是 `record(List<Image> layers, ...)`，图片一旦生成就是不可变的。`GlassSurface` 的 5 个 `ImageView` 只是同一批图片的视口切片。即使把 `16ms` 改成 `1ms`，也只是更频繁地生成新图片，仍然是“快照替换”，不是场景级实时合成。

### 3.2 只有背景节点变化会触发重拍

`GlassBackdrop` 监听的是：

- 宿主宽高；
- `backgroundNode.layoutBoundsProperty()`；
- `backgroundNode.localToSceneTransformProperty()`；
- `Themes.backgroundProperty()`；
- 场景变化。

如果背景节点内部有动画、视频、canvas 或 UI 内容变化，但布局/变换没变，`snapshot` 不会更新。这是“看起来静止”的根因之一。

### 3.3 快照包含的是背景，不是“玻璃下面的内容”

当前设计只采样 `DecoratorSkin` 的背景 Region，不采样卡片下方正在滚动的 UI。若用户期望“毛玻璃应模糊其背后的卡片/列表”，当前架构永远做不到；这需要另一条技术路线，成本更高。

### 3.4 16ms 合并可能反而造成“拖影”

`PauseTransition` 在窗口连续缩放时可能不断重新开始；如果 `refresh()` 本身耗时超过 16ms，实际刷新率会低于屏幕刷新率，表现为“松手才清晰”。需要测 `refresh()` 耗时与帧时间，而不是只看代码里的 16ms。

### 3.5 快照上限 960×640 会放大对齐误差

1080p 窗口下 `snapshotScale < 1`；视口是缩放后的像素矩形。`ImageView` 再把小图放大到卡片尺寸，边缘会出现半像素/模糊偏移。v3.17.24 的标题栏/窗口对齐问题虽然修了，但在缩放比例变化时仍可能复现。

## 4. 目标语义：先定义“实时”

建议把需求拆成三个等级，避免“实时”一词歧义：

| 等级 | 含义 | 技术含义 | 建议 |
|---|---|---|---|
| R0 | 静态壁纸贴图 | 当前快照 + 视口 | 不满足 |
| R1 | 背景实时 | 背景节点/壁纸变化、窗口缩放、滚动时，玻璃层随场景实时更新；不采样卡片下方 UI | **本轮目标**，可行性与风险可控 |
| R2 | 场景实时 | 卡片下方任何 UI 内容都实时模糊 | 需要场景快照/着色器，递归与性能风险高 |

**建议本轮锁定 R1**；R2 单独立项，不在本轮承诺。

## 5. 方案对比

| 方案 | 做法 | 实时性 | 性能 | 侵入/风险 | 结论 |
|---|---|---|---|---|---|
| A. 加大快照频率 | 30/60Hz 重建 5 层快照 | 伪实时，受快照耗时限制 | 高（每帧 5 次大图模糊） | 低 | 不推荐作为主方案 |
| B. 实时背景复制（推荐） | 每个 `GlassSurface` 放 5 个实时背景 Region，直接绑 `Background`，每层加 `BoxBlur` effect；几何随场景更新，不做快照 | **R1 真实时** | 中高（5 effect/卡，可降级） | 中（替换 GlassBackdrop 数据模型） | **主方案** |
| C. 场景快照实时模糊 | 每帧抓取卡片下方 scene 区域再模糊 | R2 | 很高，递归/闪烁 | 很高 | 本轮不采用 |
| D. 全局共享玻璃层 | 整页 5 层模糊壁纸垫在所有卡片下，卡片透明 | R1 | 低 | 中（所有卡共用模糊，难以每卡不同权重） | 备选优化 |
| E. 自定义 shader/Effect | 采样场景纹理做高斯 | R2/R1 | 取决于 GPU | 很高 | 长期探索 |

### 为什么推荐 B

- 背景节点本身就是 `Region`，`backgroundProperty()` 是实时数据源；复制 5 个 `Region` 并绑定同一个 `Background`，不需要 snapshot；
- `BoxBlur` 是 JavaFX 原生 effect，窗口缩放/滚动时由渲染管线实时处理；
- 每层 opacity 仍可由现有 CSS 控制，compact 规则可保留；
- 不采样卡片下方 UI，避免递归快照；
- 可在性能不足时降级到当前快照（保留 `visual.glass.mode=live|snapshot`）。

### B 的关键设计

```text
DecoratorSkin.backgroundNode (Region, background bound to Themes.background)
        │
        ├─ GlassBackdrop 只暴露 "背景数据源 + 几何"（不再 snapshot）
        │
GlassSurface
  ├─ LiveLayer[0..4] : Region
  │     background := backdrop.background
  │     effect     := BoxBlur(radius[i], radius[i], iterations[i])
  │     opacity    := CSS 层权重
  │     clip       := 父 GlassSurface 的圆角 clip
  └─ fallback/tint（保留）
```

几何更新：

- `backgroundNode` 的 `localToScene(0,0)` 与 `layoutBounds` 变化时，更新 5 个 Region 的 `translateX/Y`、`resize`；
- `GlassSurface.localToScene` 变化时，只更新自身 viewport/offset，不重建图片；
- 背景节点尺寸变化时，Region 尺寸跟着变；
- 每层 effect 的半径使用**屏幕像素**（96/64/40/24/12），不再乘 snapshot scale。

需要特别处理的点：

1. **Region 尺寸**：要复制背景节点的完整尺寸，而不是卡片尺寸，否则 `Background` 的 `COVER` 会按卡片重新缩放，纹理错位。
2. **裁切**：Region 放在 `GlassSurface` 的子树里，由父级圆角 clip 裁切；Region 自身不 clip，否则 effect 边缘会被切掉。
3. **坐标**：Region 使用未托管布局（`setManaged(false)`），在 `GlassSurface.layoutChildren()` 中按 `backgroundNode` 的 scene 矩形相对卡片定位；避免 StackPane 居中导致偏移。
4. **性能**：9 卡 × 5 层 = 45 个全尺寸背景 Region + effect；先做单卡 spike，测 1080p/1440p 帧时间；若 >16ms，降为 3 层或对 1×1 卡使用 2 层。
5. **降级**：`visual.glass.mode=live`（默认）/`snapshot`/`off`；`auto` 在首次布局后测帧，超预算切 snapshot。
6. **兼容**：保留 `GlassSnapshot`/`GlassSurface` 的 fallback 路径，Classic/glass off 完全不走 live 分支。

### 如果 B 的性能不可接受

- 方案 D：全局 5 层背景垫在所有卡下，卡片透明；视觉上五层仍在，但所有卡共用同一组层权重，1×1 compact 无法独立降权；可作为 B 的低成本降级。
- 方案 A：30Hz 快照 + 降低快照上限到 720×480；作为兜底，不再宣称“实时”。

## 6. 三卡修复策略：先证据，后改动

### 6.1 第一步：加诊断，不改视觉

在 `GlassSurface` 现有 `debug()` 之外增加（仅 `-Dlmcl.visual.debug=true`）：

- `node` 的 `getStyleClass()`、父链到 `.community-home` 的类名；
- `getWidth()/getHeight()`、`isVisible()`、`getOpacity()`；
- `snapshot == null`、`viewport == null` 的具体原因；
- 卡片根 `.card` 的 `Background` fills（JavaFX CSS 应用后读取）；
- `GlassSurface` 在 wrapper 中的 child index；
- `GlassBackdrop` 的 host 类名/尺寸/背景节点类名。

输出示例：

```text
[glass-material] java-recommend|234x120|NONE|shown: ... compact=false
[glass-card] java-recommend wrapper=community-material-card
  cardFills=[0x...] cardIndex=1 glassIndex=0
[glass-css] java-recommend styleClasses=[card, ...]
```

如果三卡日志显示 `shown` 且 `cardFills` 为空，问题在层级/可见性；如果 `fallback=NO_SNAPSHOT`，问题在宿主生命周期；如果 `cardFills` 有实色，问题在 CSS 级联。

### 6.2 第二步：CSS 只做清理，不再当主修复

当前 `m3-community.css:222` 的 4 类规则已经是正确的透明规则；`community.css:322` 的 3 类规则是冗余历史。建议：

- 删除 `community.css:322` 的旧规则，避免未来被误认为“透明规则只有 3 类”；
- 保留 `m3-community.css:222` 的 4 类规则，并把它放在 `.lmcl-m3 .community-home .card` 之后（当前已在之后）；
- `CommunityCssTest` 的断言改为验证 **4 类规则存在且位于 3 类实色规则之后**，而不是只验证字符串存在；
- 如果 D0 日志显示 `.card` 的 `getBackground()` 仍不透明，再检查是否是主题包/行内样式覆盖，而不是继续加选择器类数。

### 6.3 第三步：布局/层级修复

若 H3/H4 命中：

- `materialCard()` 创建后先 `glass.toBack()`；
- `GlassSurface` 在 `layoutChildren()` 后调用 `update()`（避免首次 0 尺寸被跳过）；
- 给 wrapper 设置 `setPickOnBounds(false)`？只影响命中，不影响绘制；不要用它替代层级修复；
- 检查三卡是否被 `ScrollPane` 的 viewport clip 误裁：打印 `localToScene` 与 `ScrollPane` viewport bounds。

### 6.4 第四步：几何/视口修复

若 H7 命中：

- 为三卡打印 snapshot 的 `originX/Y/scale` 与 card scene bounds；
- 检查 `GlassSnapshot.viewport()` 的钳制是否把 1×1 卡压到 <1px；
- 检查 `padding` 是否小于背景节点偏移（标题栏高度）；
- 用可复现的卡片尺寸写单测（不依赖 Windows）。

### 6.5 不应做的事

- 不要用 `!important`（JavaFX 不支持）；
- 不要把 `.card` 全局设透明（会破坏 Classic/glass off）；
- 不要用“把三卡换成别的控件”绕过问题；
- 不要在没有日志的情况下继续修改 `GlassBackdrop`。

## 12. 实现记录（v3.17.25 / m3expressive26）

### 12.1 文件与职责

- `HMCL/src/main/java/org/jackhuang/hmcl/community/ui/m3/GlassLiveViewport.java`（新增）：纯几何 helper，负责卡片场景矩形 → 背景图 cover 视口、采样外扩、场景/本地缩放换算；不依赖 JavaFX 场景生命周期，可单测。
- `GlassBackdrop.java`：新增 `ReadOnlyIntegerProperty liveRevisionProperty()`、`record LiveSource(Node, Image, double)`、`liveSource()`、`liveImage(Background)`；live 可用时停止 `PauseTransition` 快照刷新；背景节点/主题/图片/布局/变换/透明度/场景变化都推进 revision。
- `GlassSurface.java`：`Group liveGroup` 内五个未托管 `ImageView`，复用五档 `BoxBlur`；视口按背景图 cover 缩放与居中偏移换算，外扩部分由圆角 `clip` 裁掉；live 不可用依次退快照、tint。
- `MaterialCardSurface.java`（新增）：在 `BuiltinWidgets.materialCard` 中对内容 Region 安装/卸载透明守卫；监听 `backgroundProperty`、`parent`、`scene`、祖先 `styleClass`，仅在玻璃开启时把非透明 `Background` 替换为 `Background.EMPTY` 并记住原值，玻璃关闭/Classic 恢复同一实例。
- `BuiltinWidgets.java`：`materialCard` 显式 `glass.toBack()`，让玻璃层位于内容层下方；不改变 9 卡 ID、`colSpan/rowSpan` 或 `WidgetProvider` 契约。
- `m3-community.css` / `community.css`：4 类 `.lmcl-m3-glass .community-home .community-material-card > .card` 透明规则保留；旧 3 类冗余规则删除。

### 12.2 三卡根因（已确认）

不是选择器优先级：4 类规则 specificity 高于 3 类实色规则，且运行时已命中。真正原因是 1×1 卡的 `DashboardWidget` 内容根铺满整张卡（`HomePane.addWidget` 设 `maxHeight=USE_PREF_SIZE`），主题给内容根加了实色 `.card` 背景，把下方玻璃完全盖住；2×1 卡因内容有 padding 仍能露出边缘玻璃。因此 B 线最终采用 Java 透明守卫，而不是继续加 CSS。

### 12.3 验证与已知风险

- 全量测试 **336 / 0 / 2 skipped**（跳过的是既有 FX toolkit 门控用例）；新测试覆盖视口映射、live 图片选择、透明守卫与 CSS 规则。
- jar/exe/包校验值见 §11；`jre-x64` 127 MB、`dependencies/windows-x86_64/openjfx` 8.9 MB 保留。
- **风险 1**：未在 Windows 实机运行，视觉层数、对齐、对比度与 GPU 性能均未验收；WSL2 无 X11/Xvfb，不能以编译通过代替 GUI 验收。
- **风险 2**：9 卡 × 5 层 + 侧栏约 50 个 `BoxBlur`，1080p 高 DPI 可能掉帧；需要实机数据决定是否 compact/降层。
- **风险 3**：采样外扩用 `1.5×半径+2` 经验值；旋转/斜切按轴对齐矩形近似，当前 UI 无此场景。
- **风险 4**：`MaterialCardSurface` 会临时改写内容根 Background；若第三方插件持有同一 Background 实例并在玻璃开启时写回，可能被再次清空，需要实机观察。
- **风险 5**：R1 只模糊壁纸，卡片下方滚动内容不会进入模糊；若用户期望 R2，需要另立方案。

### 12.4 上游侵入

本轮**无新增侵入点**。#18 `DecoratorSkin` 的 `lmcl-launcher-background` 样式类仍保留，但从“逐帧快照来源”改为“实时背景几何来源”；侵入登记见 `docs/00-整体要求.md` §13 与 `docs/审查记录-v3.16.4源码核对.md` 对应条目。
