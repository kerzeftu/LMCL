## 1. 目标与边界

### 1.1 要解决的问题

启动器（HMCL）是**常驻进程**：用户开一次，然后一直开着启动游戏、装模组、看日志。上游只在**启动游戏前**做一次 `System.gc()`（`HMCL/src/main/java/org/jackhuang/hmcl/game/LauncherHelper.java:919`），此后启动器堆里积累的已提交内存（committed）不会在长时间挂机时主动归还，任务管理器里表现为"启动器也占几百 MB"。

本步骤在**零提权、全平台**前提下做两件事：

1. **启动器侧**：游戏运行、启动器空闲时，周期性归还未使用的已提交堆（`System.gc()` + 指标观测 + 自适应降频）；
2. **游戏侧**：定义 JEP 346 参数的语义与验收口径；生成器 `JvmMemoryOptions` 由 [步骤 11](11-性能策略-JVM参数预设向导.md) 交付（11 §3.2.1），本步在 11 之后复用其实现做验收，不重复实现。

### 1.2 明确不做

| 不做 | 原因 |
|---|---|
| 跨进程 `EmptyWorkingSet` | 需 `SeDebugPrivilege`，仅 Windows 且要提权 → 属步骤 17 的 L2 方案 |
| Linux `malloc_trim` / `drop_caches` | 前者只作用于自身进程；后者需 root 且清的是 page cache，不是"工作集"（内核文档明确不是内存回收手段） |
| macOS `purge` | 需 root、会整机冻结数秒；Apple Silicon 统一内存下不可靠 |
| 读游戏进程堆数据 | 跨平台没有安全的进程内省手段（Windows 需 P/Invoke + 提权；Linux 需 `ptrace`）；**改为展示已下发的参数 + 可选 GC 日志指引** |
| 改上游 `LauncherHelper:919` 的既有 `System.gc()` | 已存在且行为正确，不动 |

### 1.3 完成标志（DoD）

- [ ] 回收器在游戏运行、启动器空闲 ≥ 5 分钟且"未使用已提交 ≥ 128 MiB"时触发，默认 10 分钟一次；
- [ ] 触发前后记录 `used/committed/max`，日志可查；单次耗时 > 500 ms 自动降频（10min→30min），连续两次 > 1s 自动关闭并提示；

- [ ] 按本步 §3.3 的语义验收 11 交付的 `JvmMemoryOptions.generate(...)`（Java ≥ 12 且 GC=G1 才生成，否则返回空 + 原因）；
- [ ] 游戏侧参数默认**不生成**（用户显式勾选才写），与步骤 11 的 `jvmWizard` 状态互通；

## 2. 上游与 JDK 事实

### 2.1 启动器 JVM

| 事实 | 出处 |
|---|---|
| 启动器最低/推荐 Java = **17 / 21** | `HMCL/src/main/java/org/jackhuang/hmcl/Metadata.java:43-45`（`MINIMUM_REQUIRED_JAVA_VERSION=17`、`MINIMUM_SUPPORTED_JAVA_VERSION=17`、`RECOMMENDED_JAVA_VERSION=21`） |
| 启动游戏前已有一次 `System.gc()` | `HMCL/src/main/java/org/jackhuang/hmcl/game/LauncherHelper.java:919` |
| 启动器自身的 JVM 参数由启动脚本/stub 决定 | 运行期无法追加 JVM 参数 → **不能依赖 `-XX:+ExplicitGC...` 类参数**，回收器必须自适应 |

`System.gc()` 是否走并发取决于当前 GC 与 JVM 配置：G1 在多数发行版默认会尽量走并发，但不能假设；因此回收器**测量每次调用耗时并自适应**，而不是写死"并发、无停顿"。

### 2.2 游戏进程的 JEP 346（唯一权威语义）

来源：[JEP 346: Promptly Return Unused Committed Memory from G1](https://openjdk.org/jeps/346)（Release 12 交付）。

G1 在**同时满足**以下两条时触发一次周期回收：

1. 距**上一次 GC 停顿**已超过 `G1PeriodicGCInterval` 毫秒，且当前没有进行中的并发周期；**数值 0 = 关闭该功能（默认）**；
2. 系统 1 分钟平均负载（`getloadavg()`，Windows 为模拟实现）低于 `G1PeriodicGCSystemLoadThreshold`；**该值为 0 时忽略负载检查**。

`G1PeriodicGCInvokesConcurrent`：为 `true`（默认）时周期回收走"继续/发起并发周期"，为 `false` 时做一次 full GC。周期回收的日志带 `(G1 Periodic Collection)` 标记。回收后堆大小按现有 `MinHeapFreeRatio` / `MaxHeapFreeRatio` / `-Xms`/`-Xmx` 决定；若已到最小堆，就不再收缩。

**由此得到三条必须写进文档的结论**：

- 周期回收**不是按墙钟触发**：游戏一直在分配、频繁停顿时不触发；只有"接近空闲"（距上次 GC 超过 interval）才触发 → 对帧率影响小；
- `G1PeriodicGCSystemLoadThreshold` **不是百分比**，是 1 分钟平均负载（`getloadavg`）；写 `30` 等于永不触发。默认 0 = 不检查负载；机器差异大，**我们默认不写这个参数**；
- `G1PeriodicGCInvokesConcurrent` 默认已为并发，**不必写**（写了也不改变默认行为）。

| GC | 是否归还已提交堆 |
|---|---|
| G1（+ JEP 346 参数） | ✅ 空闲时归还 |
| ZGC / Shenandoah | ✅ 自动归还（无需参数；ZGC 另有 `-XX:+ZUncommit` 等，非本步骤范围） |
| Parallel / Serial / CMS | ❌ 不归还（CMS 已在 JDK 14 移除） |

|---|---|

| 步骤 11 向导 | 通过其 `JvmMemoryOptions`（11 §3.2.1）生成"高级选项"参数片段；12 只读该实现做验收 |

### 3.2 启动器侧回收器

**触发条件（全部满足才执行）**：

1. `memoryBase.enabled = true`；
2. 至少一个游戏进程处于运行中，且已运行 ≥ 120 秒（复用步骤 08 的 `SURVIVED_THRESHOLD` 判定，避免启动瞬间）；
3. 距上次回收 ≥ `intervalMinutes`（默认 10 分钟）；
4. `committed - used ≥ minReclaimMiB`（默认 128 MiB）且 `committed ≥ 256 MiB`；
5. 当前没有 `-XX:+DisableExplicitGC`（检查 `RuntimeMXBean.getInputArguments()`；若存在则面板显示"你的 JVM 禁止显式 GC，回收器已停用"）；
6. 距上次"启动游戏"请求 ≥ 60 秒（复用步骤 08 的 `REQUESTED` 事件，避免与启动流程里的 `System.gc()` 叠加）。

**执行**：

```
long t0 = System.nanoTime();
MemoryUsage before = ManagementFactory.getMemoryMXBean().getHeapMemoryUsage();
System.gc();
MemoryUsage after  = ManagementFactory.getMemoryMXBean().getHeapMemoryUsage();
long elapsedMs = (System.nanoTime() - t0) / 1_000_000;
```

- 记录 `before/after/committed/max/elapsed`；
- 若 `elapsedMs > 500` → `intervalMinutes *= 3`（上限 60 分钟），日志 WARNING；
- 若连续两次 `elapsedMs > 1000` → `enabled=false` 并写 `disabledReason="pause_too_long"`，面板提示（用户可重新开启）；
- `System.gc()` 只是**建议**，JVM 可忽略；文档与 UI 都不承诺"一定归还"。

**线程模型**：单守护线程 `CommunityMemoryReclaimer`，`ScheduledExecutorService`（daemon），每 30 秒"检查一次是否满足条件"（不是每 30 秒 GC）。JVM 退出时 `shutdownNow()`。

**对外 API（步骤 14 内存卡的唯一依赖面，签名固定）**：

```java
public final class MemoryReclaimer {
    public static MemoryReclaimer instance();
    public MemoryMetrics metrics();           // 只读快照，不触发回收
    public boolean reclaimNow();              // 手动归还；60s 冷却内返回 false（卡片显示冷却中）
    public void setEnabled(boolean enabled);  // 写 memoryBase.enabled，立即生效
    public boolean isEnabled();
}
```

> 14 只允许调这 4 个方法；不得直接读 `MemoryBaseSettings`、不得自己 `System.gc()`、不得起线程轮询。

**为什么选 `System.gc()` 而不是 `jcmd GC.run`**：

- 不依赖 `jcmd` 可执行文件与 attach 权限（Windows 下 attach 行为受安全软件影响）；
- 不引入子进程与端口；
- 缺点是无法强制并发，已用自适应兜底。

### 3.3 游戏侧参数语义（JEP 346；生成器在步骤 11）

> **归属（v1.2 收口）**：`JvmMemoryOptions` 随 `org.jackhuang.hmcl.community.jvm` 包由**步骤 11**交付（11 §3.2.1），因为写入方是 11 的向导、且 11 在前；本步不新增该类，只定义语义与验收（避免 11↔12 循环依赖）。

`JvmMemoryOptions.generate(int javaMajor, String gcName, boolean userOptIn)`（签名以 11 §3.2.1 为准）：

| 条件 | 结果 |
|---|---|
| `userOptIn=false` | 空（默认不打扰） |
| `javaMajor < 12` | 空 + 原因 `java_too_old`（JEP 346 是 12+） |
| GC 非 G1（ZGC/Shenandoah 等） | 空 + 原因 `gc_not_g1`（ZGC 自动归还） |
| 否则 | 见下 |

生成片段（只写三项，全部有 JEP 依据）：

```
-XX:G1PeriodicGCInterval=600000
-XX:MinHeapFreeRatio=5
-XX:MaxHeapFreeRatio=25
```

- `G1PeriodicGCInterval=600000`（10 分钟）：远大于正常 GC 间隔，只有游戏接近空闲才会触发；
- `MinHeapFreeRatio=5` / `MaxHeapFreeRatio=25`（默认 40/70）：让"回收后目标堆"更接近实际使用量，避免刚收缩又被撑回去；不写 `MaxHeapFreeRatio=10` 那么激进，减少"收缩→再扩堆"的抖动；
- **不写** `G1PeriodicGCSystemLoadThreshold`（默认 0 = 忽略负载检查；写负载阈值在 Windows 的 `getloadavg` 模拟下不可移植）；
- **不写** `G1PeriodicGCInvokesConcurrent`（默认并发）；
- **不写** `ShrinkHeapInSteps`（默认行为已是分步收缩，写死反而在低版本有兼容风险）。

**与步骤 11 的交互**：

- 向导"大内存（ZGC）"档不显示该选项（原因 `gc_not_g1`）；
- 向导"跟随上游"档可选（生成参数写进 `jvmOptions`；该片段不含 `-XX:+Use*GC`，所以**不会**触发上游 `DefaultLauncher:216-217` 的"跳过 G1 块"判断）；
- 复选框状态存 `jvmWizard.<id>.periodicGc`，`jvmOptions` 由向导统一重算（避免与手填参数混在一起无法撤销）。

**如何让用户验证真的归还了**（写进帮助文案）：

- 游戏内按 `F3` 看不到堆归还；正确做法是启动参数临时加 `-Xlog:gc*:file=gc.log`（JDK 9+），日志出现 `(G1 Periodic Collection)` 且 capacity 下降即生效；
- 任务管理器/`ps` 观察 RSS 下降可能滞后（页回收由 OS 决定）。

### 3.4 指标 API（供步骤 14 内存卡）

```java
public record MemoryMetrics(
        long heapUsed, long heapCommitted, long heapMax,
        long reclaimableEstimate,     // max(0, committed - used)
        @Nullable Instant lastReclaimAt,
        long lastReclaimFreed,        // 上次回收减少的 committed（字节，可为 0）
        long totalReclaimed,          // 累计减少的 committed
        int intervalMinutes,
        boolean enabled,
        @Nullable String disabledReason,
        boolean gameRunning) { }
```

- 采集：`MemoryMXBean.getHeapMemoryUsage()` + 回收器状态；UI 每次显示时拉取一次，**不做后台高频轮询**；
- `reclaimableEstimate` 是"已提交但未使用"的保守估计，不等于一定能归还那么多（文案写"理论可归还"）。

## 7. 风险

| 风险 | 等级 | 应对 |
|---|---|---|
| `System.gc()` 在某些 JVM 上造成明显停顿 | 中 | 条件收紧（仅游戏运行 120s 后）、间隔 10 分钟、计时自适应降频/自动关闭 |
| 用户/安全软件把启动器 JVM 配置为 `-XX:+DisableExplicitGC` | 低 | 启动时检测 `RuntimeMXBean` 输入参数并停用 + 提示 |
| `System.gc()` 被 JVM 忽略，用户认为"功能无效" | 中 | 文案写"是否归还由 JVM 决定"，面板展示实际 `committed` 变化 |
| JEP 346 参数在特定发行版不识别 | 低 | 只对 G1 + Java ≥ 12 生成；G1PeriodicGC* 自 JDK 12 起存在；测试矩阵含 Zulu/Temurin/Corretto |
| `MaxHeapFreeRatio` 导致收缩后又扩堆抖动 | 中 | 用 25 而非 10；周期 10 分钟；不做默认开启 |
| 用户把 JEP 346 参数与自定义 `-Xms=-Xmx` 同用 | 低 | 步骤 11 冲突检测提示"固定堆大小时周期回收收益有限" |
| 指标 API 被高频轮询拖慢 UI | 低 | 只在面板可见时拉取；`MemoryMXBean` 调用本身轻量 |

4. 完全回退：不启动 `MemoryReclaimer`（Bootstrap 不注册），代码保留，行为与上游一致。
