# 步骤 09 · 启动保障（Ⅱ）· 崩溃现场留存与还原

> **阶段**：阶段二 · 启动保障 ｜ **优先级**：P0 ｜ **工期**：2 周
> **前置**：[步骤 08](08-启动保障-启动前体检.md)（消费其启动钩子事件）｜ **后续**：[步骤 16](16-启动保障-实例快照回滚.md)
> **代码侵入**：0（只新增 `org.jackhuang.hmcl.community.crash` 包 + 仪表盘卡片，由 [步骤 13](13-首页组件化A-框架搭建.md) 挂载）
> **边界（先读）**：上游 `GameCrashWindow` **已经**做崩溃原因分析并自动弹出；本步骤**不重写分析器、不弹第二个崩溃窗**，只做"现场留存 + 崩溃历史 + 诊断导出 + 与快照回滚的联动"。

---

## 1. 目标

1. 崩溃发生后，**现场不丢**：把游戏日志、crash-report、启动命令、Java/内存/版本信息、模组清单、启动耗时固化成一份可离线查看的归档；
2. 崩溃原因**可复用**上游 `CrashReportAnalyzer` 的结论（含规则命中与关键词），不自己写第二套规则；
3. 崩溃**有历史**：首页仪表盘可看"最近崩溃"，支持查看详情、打开归档、导出诊断包；
4. 崩溃**可回退**：与步骤 16 的快照联动，提供"回滚到本次启动前"入口（快照存在时才显示）；
5. 归档、历史、清理**全部异步且容错**：任何失败只记日志，绝不影响启动/游戏/上游崩溃窗。

完成标志（DoD）：

- [ ] 崩溃退出后 ≤2s 归档目录生成（文件锁/磁盘满场景允许失败但不阻塞）；
- [ ] `meta.json` 字段齐全且可被 v1 schema 校验（含 `quickCrash`、`exitType`、`snapshotId`）；
- [ ] `accessToken` 等敏感串被 `Logger.filterForbiddenToken` 过滤（构造用例断言归档内无 token 原文）；
- [ ] `INTERRUPTED`（用户主动停止）与 `NORMAL` 退出**不产生**崩溃归档；
- [ ] 崩溃历史损坏/缺字段/归档目录被删时，UI 降级不崩；
- [ ] 保留策略生效：超过 10 份或 90 天自动清理最旧，且清理不影响当前归档；
- [ ] 回滚按钮只在 16 返回快照存在时出现，点击行为由 16 提供。

## 2. 上游现状与可复用件（v3.16.4 实测）

### 2.1 崩溃时上游做了什么

`HMCL/src/main/java/org/jackhuang/hmcl/game/LauncherHelper.java`：

| 行 | 行为 |
|---|---|
| 970 | `HMCLProcessListener.onExit(int exitCode, ExitType exitType)` 被调用 |
| 981 | `launchingLatch.countDown()`（我们的 `onProcessExit` 在**这行之前**，见步骤 08） |
| 982–983 | `if (exitType == ExitType.INTERRUPTED) return;` —— 用户主动停止**不算崩溃** |
| 997–1000 | `if (exitType != ExitType.NORMAL) { repository.markVersionLaunchedAbnormally(version.getId()); runLater(() -> new GameCrashWindow(...).show()); }` |

结论：**上游的"崩溃"判据 = `exitType != NORMAL && exitType != INTERRUPTED`**。我们的事件语义（步骤 08）与之一致，直接复用，不再另立判据。

### 2.2 上游崩溃分析器（不要重写）

`HMCLCore/src/main/java/org/jackhuang/hmcl/game/CrashReportAnalyzer.java`：

| API | 签名 | 用途 |
|---|---|---|
| `analyze` | `public static Set<Result> analyze(String log)` | 对"crash-report 文本或日志文本"跑规则，返回命中集合 |
| `Result` | `public record Result(Rule rule, String log, Matcher matcher)` | `rule` 决定文案，`matcher` 提供 `expected` 等分组 |
| `findCrashReport` | `public static String findCrashReport(String log) throws IOException, InvalidPathException` | 从日志里找 crash-report 路径并读出来 |
| `extractCrashReport` | `public static String extractCrashReport(String rawLog)` | 从原始日志截取 crash-report 段 |
| `findKeywordsFromCrashReport` | `public static Set<String> findKeywordsFromCrashReport(String crashReport)` | 未命中规则时的关键词兜底 |
| `getJavaVersionFromMajorVersion` | `public static int getJavaVersionFromMajorVersion(int majorVersion)` | `TOO_OLD_JAVA` 文案用 |

`Rule` 覆盖（`CrashReportAnalyzer.java:36` 起）：`TOO_OLD_JAVA`、`MOD_RESOLUTION_CONFLICT`、`MOD_RESOLUTION_MISSING`、`MOD_RESOLUTION_COLLECTION`、`MOD_RESOLUTION_MISSING_MINECRAFT`、森林系 OptiFine 组合等。文案 key 形态为 `game.crash.reason.<rule 小写>`，另有 `game.crash.reason.multiple / unknown / stacktrace / mod`。

### 2.3 其他可复用件

| 用途 | API | 位置 |
|---|---|---|
| 敏感 token 过滤 | `Logger.filterForbiddenToken(String)`；token 由上游登录流程注册 | `HMCLCore/src/main/java/org/jackhuang/hmcl/util/logging/Logger.java:64` |
| 启动器内存日志 | `Logger.LOG.getLogs()` | 同上（`LogExporter.java:73` 有用法） |
| 打 zip | `new Zipper(Path)` / `putFile` / `putTextFile` / `putLines` | `HMCLCore/src/main/java/org/jackhuang/hmcl/util/io/Zipper.java` |
| 命令/类路径/未落盘日志 | `ManagedProcess.getCommands()`、`getClasspath()`、`getLines(...)`、`getExitCode()` | `HMCLCore/src/main/java/org/jackhuang/hmcl/util/platform/ManagedProcess.java:88/97/114/178` |
| 启动器日志目录 | `<Metadata.HMCL_LOCAL_HOME>/logs` | `HMCL/src/main/java/org/jackhuang/hmcl/EntryPoint.java:51` |
| 实例运行目录 | `repository.getRunDirectory(versionId)`（`logs/`、`crash-reports/` 在它下面） | `HMCLGameRepository` |

> `LogExporter.exportLogs(...)`（`HMCL/src/main/java/org/jackhuang/hmcl/game/LogExporter.java`）是上游"导出崩溃信息"的实现：打包 `logs/`、`crash-reports/`、`hmcl.log`、`minecraft.log`、`launch.bat`、版本 json，并用 `Logger.filterForbiddenToken` 过滤。**结论：导出内容直接复用其清单与过滤方式；但它的 zip 内容固定、不便追加 `meta.json`，因此我们自己用 `Zipper` 组织，规则与其对齐。**

## 3. 设计

### 3.1 事件接线（只消费步骤 08 的契约）

在启动器初始化（与步骤 05 的 Bootstrap 同处）注册：

```java
CommunityLaunchHooks.addListener(new CrashArchiveListener());
```

`CrashArchiveListener`：

- `PROCESS_CREATED`：把 `ManagedProcess`、`versionId`、`LaunchContext`（步骤 08 在 `TASKS_COMPLETED` 事件里携带/缓存）存入本次会话上下文；**不读文件、不落盘**；
- `EXITED_ABNORMAL`：异步执行归档（`Schedulers.io()`），事件回调立即返回；
- `EXITED_NORMAL` / `ABORTED_BY_USER` / `SURVIVED_THRESHOLD`：忽略（`SURVIVED_THRESHOLD` 可作为 `quickCrash=false` 的判据，避免重复读时钟）。

> 上游 `GameCrashWindow` 在 `runLater` 里弹出，我们的归档与之并行；**归档绝不弹窗**，完成后面板更新一个"最近崩溃"红点（`Platform.runLater`）。

### 3.2 归档目录结构

根：`<Metadata.HMCL_LOCAL_HOME>/community/crash-reports/`（本地根，步骤 06 已定；**不写用户根、不写实例目录**）

```
crash-20261021-134500-a1b2c3/          # crash-<yyyyMMdd-HHmmss>-<短 id>
├── meta.json
├── hmcl.log                           # 启动器日志（LOG.getLogs()，过滤 token，最多 1 MiB 尾部）
├── minecraft.log                      # runDir/logs/latest.log（存在时，过滤）
├── crash-report.txt                   # runDir/crash-reports/ 最新一份客户端报告（存在时，过滤）
├── command.txt                        # 启动命令（getCommands()，逐行过滤 token）
├── mods.txt                           # mods/ 文件名 + sha1（存在时；.disabled 也列）
└── snapshot.txt                       # 16 返回的快照 id（存在时，一行）
```

`meta.json`（schema **v1**，字段缺失按默认值处理）：

```json
{
  "schema": 1,
  "archiveId": "crash-20261021-134500-a1b2c3",
  "createdAt": "2026-10-21T13:45:00+08:00",
  "versionId": "1.20.4-Fabric",
  "gameVersion": "1.20.4",
  "launcherVersion": "3.16.1000",
  "exitCode": 1,
  "exitType": "APPLICATION_ERROR",
  "aliveSeconds": 47,
  "quickCrash": true,
  "java": { "version": "21.0.5", "vendor": "Eclipse Adoptium", "path": "C:\\...\\java.exe" },
  "memory": { "minMb": 512, "maxMb": 4096, "physicalMb": 16384 },
  "os": { "name": "Windows 11", "arch": "x86_64" },
  "modCount": 128,
  "snapshotId": "snap-20261021-134412",
  "analysis": {
    "rules": ["TOO_OLD_JAVA"],
    "keywords": [],
    "summary": "game.crash.reason.too_old_java"
  }
}
```

- `exitType` 取值直接来自上游 `ExitType` 枚举名（`NORMAL` 不会进入归档）；
- `quickCrash = aliveSeconds < 阈值`（阈值取步骤 08 的 `launchTracker.successThresholdSeconds`，默认 120）；"启动期崩溃"与"运行期崩溃"由它区分，**不另存时间戳做二次判断**；
- `analysis.summary` 只存 **i18n key**（+ 参数），不存成品中文，避免语言混杂与文案过期；渲染时用当前语言。

### 3.3 归档实现（全部容错）

```java
// 伪代码：CrashArchiver.archive(context, event)
try {
    Path dir = crashRoot.resolve(nextArchiveName(event));     // 冲突时追加 -2、-3
    Files.createDirectories(dir);
    writeText(dir.resolve("meta.json"), GSON.toJson(meta));    // 先写 meta，再补文件
    copyFiltered(runDir.resolve("logs/latest.log"), dir.resolve("minecraft.log"));
    copyLatestCrashReport(runDir.resolve("crash-reports"), dir.resolve("crash-report.txt"));
    writeText(dir.resolve("command.txt"), filterLines(process.getCommands()));
    writeText(dir.resolve("hmcl.log"), tail(LOG.getLogs(), 1 << 20));
    writeModsList(...);                                       // 失败只记日志
    writeSnapshotPointer(...);                                // 16 未启用则跳过
    CrashHistory.append(dir, meta);                           // 索引原子更新
    prune(crashRoot);                                         // 保留策略
} catch (Throwable e) {
    LOG.warning("Community crash archive failed", e);         // 绝不上抛
}
```

- 所有读写用 `Files.copy(..., StandardCopyOption.COPY_ATTRIBUTES)` + `StandardOpenOption`，**不修改源文件**；
- 大文件保护：单个文件 >8 MiB 时截断（保留头 2 MiB + 尾 2 MiB，中间插 `...[truncated]...` 标记）；
- 磁盘满/权限不足：只记 warning，`crash-history.json` 不追加，下次启动不重试（避免循环失败）。

### 3.4 原因摘录（离线、复用上游规则）

归档时同步 `analysis`：

1. 优先 `crash-reports/` 最新 `.txt` 原文；
2. 否则 `runDir/logs/latest.log`，先 `CrashReportAnalyzer.findCrashReport(log)`/`extractCrashReport(rawLog)` 尝试抽报告段；
3. `Set<Result> results = CrashReportAnalyzer.analyze(text)`：
   - 命中 1 条 → `rules=[rule]`、`summary=game.crash.reason.<rule 小写>`；
   - 命中多条 → `summary=game.crash.reason.multiple`，`rules` 全存；
   - 未命中 → 关键词兜底 `findKeywordsFromCrashReport(...)`，存 `keywords`，`summary=game.crash.reason.stacktrace`（无关键词则 `unknown`）；
4. 任何异常 → `analysis=null`（UI 显示"未识别"）。

> 这段逻辑与 `GameCrashWindow.analyzeCrashReport()` 的判定一致；如果上游改了规则/文案，我们**只跟 key，不复制文案**，升级无感。

### 3.5 崩溃历史索引

`<本地根>/community/crash-history.json`（与 `community-settings.json` 同目录，**不合并**：历史是数据、设置是配置，分别原子写）：

```json
{ "schema": 1, "entries": [
  { "archiveId": "crash-20261021-134500-a1b2c3", "createdAt": "...", "versionId": "...",
    "quickCrash": true, "summary": "game.crash.reason.too_old_java",
    "rules": ["TOO_OLD_JAVA"], "snapshotId": "snap-...", "exported": false }
] }
```

- 只保留最近 **20** 条（与归档保留 10 份独立：归档被清理后历史条目仍可"详情不可用"降级）；
- 每次归档后重写（临时文件 + `ATOMIC_MOVE`）；读到损坏 JSON → 备份为 `crash-history.json.bak-<时间戳>` 并重建空索引；
- 崩溃历史**不参与启动决策**，任何 IO 失败只影响 UI。

### 3.6 UI（容器与卡片壳由 13/14 提供，本步只交付 pane）

**本步交付的 API（14 的 `crash-history` 卡片按此调用，签名固定）**：

```java
/// 写入归档 `meta.json` 的摘要（§3.4 的结果）；`quickCrash` = STARTUP 且未存活阈值。
public record CrashMeta(@NotNull String versionId, @NotNull String gameVersion,
                        @NotNull LaunchPhase phase, boolean quickCrash,
                        @NotNull String summary, @NotNull List<String> rules,
                        @NotNull List<String> keywords, @Nullable String snapshotId,
                        boolean exported, @NotNull Instant at) {}

public final class org.jackhuang.hmcl.community.crash.CrashHistory {
    public static List<CrashEntry> load();        // 读索引；损坏→备份 + 空列表（不抛）
    /// 归档完成后追加一条；`reasonRule` 取 `rules` 的第一条（多条时 summary 为 multiple）。
    public static void append(@NotNull Path archiveDir, @NotNull CrashMeta meta);
    public static int unseenCount();             // 本次会话内新增条数（红点）
    public static void markAllSeen();
}

/// 崩溃发生的阶段：以 08 的 `SURVIVED_THRESHOLD` 为分界。
/// STARTUP = 未发过存活阈值就退出；RUNTIME = 存活阈值之后退出。
public enum LaunchPhase { STARTUP, RUNTIME }

/// 索引条目（与 crash-history.json 的 entries[] 一一对应）
public record CrashEntry(
        String archiveId, Instant at, String versionId, String gameVersion,
        LaunchPhase phase,                    // STARTUP / RUNTIME
        @Nullable String reasonRule,          // 命中的上游 Rule 名
        List<String> keywords,
        @Nullable String snapshotId,          // 16 的快照指针；未启用为 null
        boolean exported,
        String dirName) {}                    // 归档目录名（详情/导出用）
```

新增 `community.ui.crash.CrashHistoryPane`（**无参构造**；`setCompact(true)` 时只渲染列表行，供 14 卡片内嵌）：

```
最近崩溃 (3)

  10-20 22:10  1.20.1-Forge    运行期 · 未识别（含关键词）  [详情]
  10-19 09:31  1.19.2-Vanilla  启动期 · 日志未找到           [详情]
```

> 卡片壳（标题/空态/角标/展开）**由 14 的 `crash-history` 组件提供**；09 不新增 `CrashHistoryCard` 类（避免两处维护）。

- **详情**：打开归档目录（`FXUtils.openFolder` 等上游工具）+ 展示 `meta.json` 摘要 + "导出诊断包"；

- 全部文案走 i18n（key 见 §3.7）。

### 3.8 保留与配额

| 项 | 值 | 说明 |
|---|---|---|
| 归档保留份数 | 10 | 超出删最旧（先删目录，再删历史条目 -- 历史条目保留到 20 条） |
| 归档保留天数 | 90 | 与份数先到先删 |
| 目录总配额 | 200 MiB | 超配额从最旧开始删，直到低于配额或只剩 3 份 |
| 单文件上限 | 8 MiB | 超出截断（头 2 MiB + 尾 2 MiB） |
| 清理时机 | 归档成功后 | **启动时绝不清理**，避免启动变慢与误删 |

### 3.9 隐私与合规

- 归档/导出前统一过 `Logger.filterForbiddenToken`（上游登录流程已把 accessToken 注册进去，`Logger.java:64`）；
- `command.txt` 逐行过滤；`meta.json` 不含用户名以外的个人信息（路径可能含用户名，导出时提示）；
- 不联网、不上传；"上传到社区"若未来要做，必须显式勾选 + 展示内容清单（本步骤不做）；
- 归档内容属于用户本机数据，删除入口在详情面板（"删除此归档"）。

### 3.10 边界：启动器自身崩溃/强杀

事件只在启动器进程内有效。若启动器被强杀：

- 游戏进程可能仍在运行（上游 `LauncherVisibility` 决定），本步骤不处理；
- 下次启动时步骤 08 发出 `PREVIOUS_ABNORMAL`：若该实例 24h 内无对应归档，则生成一条 `quickCrash=unknown` 的"补档"（只含 `logs/latest.log` 与 crash-report，`meta.json` 标注 `"recovered": true`），面板显示"上次会话已异常结束"；
- 补档**不猜测原因**（`analysis=null`），避免误导。

## 5. 测试计划

| 用例 | 期望 |
|---|---|
| 游戏启动 30s 崩溃 | 归档生成、`quickCrash=true`、`analysis` 有结论 |
| 游戏运行 3h 后崩溃 | `quickCrash=false`、`aliveSeconds` 正确 |
| 用户点停止（INTERRUPTED） | 不生成归档、历史不新增 |
| 正常退出 | 不生成归档 |
| 启动器强杀后重启 | 生成 `recovered=true` 补档，无原因结论 |
| 归档目录被手动删除 | 历史详情提示"归档已丢失"，不崩 |
| `crash-history.json` 损坏 | 备份并重建，UI 显示空 |
| accessToken 出现在命令/日志 | 归档内为 `<access token>` |
| 磁盘只读 | 归档失败仅 warning，游戏不受影响 |
| 第 11 次崩溃 | 最旧归档被删，历史条目在（详情降级） |
