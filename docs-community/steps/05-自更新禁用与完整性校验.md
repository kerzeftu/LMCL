# 步骤 05 · 自更新禁用与完整性校验

> **阶段**：阶段一 · 工程底座 ｜ **优先级**：P0（最不容出错的一步） ｜ **工期**：2–3 天
> **前置**：[步骤 03](03-产品身份与合规改造.md) ｜ **后续**：[步骤 06](06-数据目录与用户迁移.md)
> **侵入点**：0（新增 `community.CommunityBootstrap` 类 + `HMCL/build.gradle.kts` manifest 1 行，均属"新增/构建"登记，不改上游逻辑文件）

---

## 1. 目标

**结构性地保证：社区版产物永远无法通过上游的自完整性校验，因此自更新链路在发起任何网络请求之前就必然失败。**

这不是"把更新按钮藏起来"，而是"让恢复官方自更新在密码学上不可能"：官方校验用的是 HMCL 官方 RSA 私钥签出的 `META-INF/hmcl_signature`，我们既没有该私钥，也没有官方公钥对应的签名，`isSelfVerified()` 恒为 `false`。

完成标志（DoD）：

1. 发行产物（jar / exe）不含 `META-INF/hmcl_signature`，`isSelfVerified() == false`；
2. `UpdateChecker.checkUpdate()` 在**联网前**抛 `IOException("Self verification failed")`，被上层捕获后只记 WARNING 日志，不弹错误框、不阻断启动；
3. 启动、切更新渠道、崩溃、退出全过程**无任何发往 `huangyuhui.net` / 官方 CI / 官方统计服务的请求**（mitmproxy 证据）；
4. Bootstrap 在 `Metadata` 静态初始化之前钉住两个属性：更新源指向本项目域名；`hmcl.self_integrity_check.disable` 在发行版中被强制为 `false`（外部 `-D` 覆盖无效）；
5. 发行渠道值固定为 `stable`（不得出现上游 `nightly` 行为：公告卡、官方身份判定）；
6. 已知 UX 债务有书面记录（设置页"检查更新"显示"已是最新"、按钮永不出现），不在本步用侵入换取修复。

> 本步**不修改**任何上游逻辑文件：`UpdateChecker` / `UpdateHandler` / `IntegrityChecker` / `SettingsPage` / `MainPage` / `CrashReporter` 全部保持原样。这是我们能把侵入预算压回"固定 3 处"的关键。

## 2. 依据：v3.16.4 源码实测（先看这 6 个事实）

| # | 位置 | 事实 |
|---|---|---|
| 1 | `IntegrityChecker.java:48` | `DISABLE_SELF_INTEGRITY_CHECK = "true".equals(System.getProperty("hmcl.self_integrity_check.disable"))`，类加载时读一次 |
| 2 | `IntegrityChecker.java:114` | `isSelfVerified()`：用内置公钥 `assets/hmcl_signature_publickey.der` 验证自身 jar/exe 的 `META-INF/hmcl_signature`；未签名 → `false` |
| 3 | `UpdateChecker.java:87-88` | `checkUpdate()` 的**第一段代码**就是 `if (!DISABLE && !isSelfVerified()) throw new IOException("Self verification failed");` —— 在构造 `URL`、发 HTTP 之前 |
| 4 | `UpdateHandler.java:177-178` | `applyUpdate(Path)`（`--apply-to` 自替换）同样先过该校验 |
| 5 | `UpdateHandler.java:126` / `197-200` | `updateFrom()` 下载完成后再次校验；`requestUpdate()` 在 `DISABLE == false` 时 `verifyJar(updateTo)` |
| 6 | `Metadata.java`（静态字段 `HMCL_UPDATE_URL`） | `System.getProperty("hmcl.update_source.override", PUBLISH_URL + "/api/update_link")`，**在 `Metadata` 类初始化时读取一次**；而 `Metadata` 的初始化由 `EntryPoint.main` 第 48 行 `http.agent` 赋值触发 |

推论（本步方案的全部依据）：

- **不设置** `hmcl.self_integrity_check.disable` 时，守卫拦截发生在网络之前，官方更新源根本不会被连接；`UpdateChecker.checkUpdate()` 的异常被 `UpdateChecker.requestCheckUpdate` 捕获并 `LOG.warning`，UI 侧 `SettingsPage` 的监听器只会把副标题设为 `update.latest`（"已是最新"），**不弹错误框**；
- 因此"禁用自更新"的正确姿势不是 `-Ddisable=true`（那会把更新检查放行到网络层），而是**保持/强化校验**；
- 唯一必须在网络发生前钉住的是**更新源**：默认值 `https://hmcl.huangyuhui.net/api/update_link` 是官方地址。虽然守卫会先失败，但 `update_source.override` 是我们的第二道防线（若未来某次同步改了守卫位置、或我们启用自己的签名，更新源必须是本项目域名）；
- `hmcl.update_source.override` 必须在 `EntryPoint.main`（第 48 行）之前写入 → 用 Bootstrap 类在 `EntryPoint` 之前执行（见 §4.1、§4.2）。

### 2.1 渠道值的副作用（容易踩，务必按 §4.5 设置）

上游 `Metadata`：

```java
public static final String BUILD_CHANNEL = JarUtils.getAttribute("hmcl.version.type", "nightly");
public static boolean isStable()   { return "stable".equals(BUILD_CHANNEL); }
public static boolean isDev()      { return "dev".equals(BUILD_CHANNEL); }
public static boolean isNightly()  { return !isStable() && !isDev(); }   // ← 注意：任何其它值都算 nightly
```

- `isNightly()` 为真时，`MainPage` 会显示"nightly 构建"公告卡（`MainPage.java:128-171`，内容来自本地 i18n，不联网，但会误导用户）；
- `IntegrityChecker.isOfficial()`（`IntegrityChecker.java:142-143`）在 `BUILD_CHANNEL.equals("nightly") && GITHUB_SHA != null` 时为 `true` —— 我们的 CI 一定有 `GITHUB_SHA`，所以**发行物绝对不能用 `hmcl.version.type=nightly`**；
- 结论：发行构建 `VERSION_TYPE=stable`；开发/每夜包用 `VERSION_TYPE=dev`；**禁止 nightly**（写入步骤 02、18 的构建脚本约束）。

### 2.2 与步骤 04 的关系（默认 No-Go 时的叠加影响）

步骤 04 结论：relocate 会让 `CrashReport.shouldBeReport()` 的 `stackTrace.contains("org.jackhuang")` 恒为 false，崩溃窗口静默失效；默认结论为 **No-Go**。因此本步在"不 relocate"的基线上实施，`CommunityBootstrap` 引用 `org.jackhuang.hmcl.EntryPoint` 的字面类名不受影响。若未来改为 Go，Bootstrap 的字节码引用会被 Shadow 自动改写，但 manifest 的 `Main-Class` 需人工同步（§4.2 已要求回归）。

## 3. 方案选择

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| **A. 保持校验 + 钉住属性（推荐）** | 不设 disable=true；Bootstrap 把更新源指到本项目、把 disable 钉为 false | 零逻辑侵入；密码学上不可恢复；官方请求在联网前失败 | 设置页显示"已是最新"；无法一键更新 | ✅ 采用 |
| B. `-Dhmcl.self_integrity_check.disable=true` | 启动脚本/参数关闭校验 | 实现最省事 | 更新检查被放行到网络层，只剩更新源一道防线；参数可被用户/绿色包改写；等于把安全建立在字符串上 | ❌ 否 |
| C. 删除 `upgrade/` 包 | 删 7 个类 | 表面"干净" | 与上游同步冲突巨大；`CrashWindow`/`Controllers`/`RootPage` 都有引用，易 `NoClassDefFoundError` | ❌ 否 |
| D. 自建签名更新通道 | 换公钥 → CI 私钥签名 → 自家 update JSON | 可一键更新 | 需替换 `assets/hmcl_signature_publickey.der` + 保管私钥 + 服务端 JSON，工作量 1–2 周 | ⏸ 后置到步骤 18 backlog（P3） |

**A 案的本质**：把"我们发的是未签名修改版"这个事实，从"麻烦"变成"安全闸门"。

## 4. 详细实施

### 4.1 新增 `CommunityBootstrap`

位置（新增包，已在 `00-整体要求.md` §4.2 登记）：`HMCL/src/main/java/org/jackhuang/hmcl/community/CommunityBootstrap.java`

先明确上游真实的启动链（v3.16.4，三个模块的类同名覆盖关系，容易搞错）：

```
HMCLBoot/src/main/java/.../Main.java            ← shadowJar manifest 的 Main-Class（原有）
  └─ checkDirectoryPath() → Java 版本检查（MINIMUM_JAVA_VERSION = 17）
       └─ org.jackhuang.hmcl.EntryPoint.main(args)
HMCLBoot/src/main/java/.../EntryPoint.java      ← dummy，shadowJar 合并时被
HMCL/src/main/java/org/jackhuang/hmcl/EntryPoint.java   ← 同名类覆盖，这才是真入口
  └─ EntryPoint（第 48 行触发 Metadata 初始化）→ Launcher.main(args)
```

因此 Bootstrap **不能直接调用 `EntryPoint`**，否则会跳过 HMCLBoot 的 Java 版本检查与"exclamation mark 路径"检查（`HMCLBoot/.../Main.java:63-95,144-152`）。正确做法是转交 `org.jackhuang.hmcl.Main.main(args)`：

```java
package org.jackhuang.hmcl.community;

import org.jackhuang.hmcl.Main;
import org.jetbrains.annotations.NotNull;
import org.jetbrains.annotations.NotNullByDefault;

/// 社区版启动入口：在任何上游类初始化（尤其是 `Metadata`）之前钉住进程级属性。
/// 这是 shadowJar 的 `Main-Class`，属性写完后原样转交上游 [Main]（保留 Java 版本检查）。
@NotNullByDefault
public final class CommunityBootstrap {

    /// 更新源属性名；上游 `Metadata` 静态初始化时读取并缓存。
    private static final String PROP_UPDATE_SOURCE = "hmcl.update_source.override";

    /// 自完整性校验开关属性名；上游 `IntegrityChecker` 类初始化时读取并缓存。
    private static final String PROP_DISABLE_INTEGRITY = "hmcl.self_integrity_check.disable";

    /// 开发逃生口：本地需要测试"更新检查真的会发请求"时才允许外部覆盖上述属性。
    private static final String PROP_DEV = "hmcl.community.dev";

    /// 社区版更新源占位域名（RFC 2606 保留域，发布阶段替换为真实域名，见步骤 18）。
    private static final String COMMUNITY_UPDATE_SOURCE = "https://lmcl.example/api/update_link";

    private CommunityBootstrap() {
    }

    /// 程序入口：先钉属性，再原样转交上游 [Main]。
    public static void main(String @NotNull [] args) throws Throwable {
        boolean dev = Boolean.getBoolean(PROP_DEV);

        // 第二道防线：即使外部传了官方 update_link，也只会指向本项目域名。
        if (!dev) {
            System.setProperty(PROP_UPDATE_SOURCE, COMMUNITY_UPDATE_SOURCE);
            // 第一道防线：发行版强制保持校验开启，使未签名产物在联网前失败。
            System.setProperty(PROP_DISABLE_INTEGRITY, "false");
        }

        Main.main(args);
    }
}
```

> 注意：`Main.main` 声明为 `throws Throwable`（`HMCLBoot/.../Main.java:144`），Bootstrap 的 `main` 必须同样声明，否则编译失败。
>
> 本步只写两个属性；[步骤 06](06-数据目录与用户迁移.md) §4.2 会在同一 `main` 里、`Main.main` 之前追加 `CommunityPaths.applySystemProperties()`（显式属性已存在则跳过）。实现 06 时直接改本类并同步回填 §4.1 的代码片段，不要另建第二个 Bootstrap。

要点：

- **为什么是类级属性而不是启动脚本**：属性在 `Main-Class` 的第一行代码写入，早于 `Metadata`（`HMCL/src/main/java/org/jackhuang/hmcl/EntryPoint.java:48`）与 `IntegrityChecker` 的类初始化；用户/绿色包附加的 `-Dhmcl.self_integrity_check.disable=true` 会被覆盖。禁止把这两个属性写进发行启动脚本或 `HMCL_JAVA_OPTS` 默认值（步骤 20 的 stub 默认参数也不加）。
- **`hmcl.community.dev` 只用于开发**：本地调试更新链路时 `-Dhmcl.community.dev=true`，此时允许外部属性覆盖；CI 的发行构建不得设置该属性（步骤 02/18 加检查：`grep -r "hmcl.community.dev" 发行脚本` 必须为空）。
- **异常处理**：本方法不做 `try/catch`。属性设置是纯内存操作，不会失败；`EntryPoint.main` 的异常由上游崩溃处理接管（保持 `CrashReporter` 行为）。

### 4.2 把 manifest 的 `Main-Class` 指向 Bootstrap

在 `HMCL/build.gradle.kts` 的 `shadowJar` 配置中（当前实读为）：

```kotlin
manifest {
    attributes(
        "Created-By" to "Copyright(c) 2013-2025 huangyuhui.",
        "Implementation-Version" to project.version,
        "Main-Class" to "org.jackhuang.hmcl.Main",     // ← 改为 org.jackhuang.hmcl.community.CommunityBootstrap
        ...
    )
}
```

- 只改 `Main-Class` 一行；`HMCLBoot` 的 `EntryPoint` 覆盖机制（shadowJar 合并时用 HMCL 模块同名类覆盖 `HMCLBoot` 的 dummy 类）不受影响；
- 改完构建产物的验证：

```bash
unzip -p HMCL/build/libs/HMCL-*.jar META-INF/MANIFEST.MF | grep -i "Main-Class"
# 期望：Main-Class: org.jackhuang.hmcl.community.CommunityBootstrap
```

- **exe 也要验证**：`makeExecutables` 把 stub + jar 拼成 `HMCL-<version>.exe`（发行时改名 `LMCL-<version>-win-x86.exe`），`Main-Class` 决定 JVM 入口；步骤 20 的验收包含"裸机双击 exe 启动成功"，本步先在开发机执行 `java -jar LMCL-*.exe` 做等价验证。

### 4.3 更新源占位与发布切换

- 首发固定 `https://lmcl.example/api/update_link`（保留域，永不解析）；官方更新源从此不会出现在任何代码路径中；
- 发布前（步骤 18）替换为真实域名，若暂无更新接口，**允许保留占位域**：`UpdateChecker` 会在守卫处失败，根本走不到 DNS 解析；
- 预留更新 JSON 契约（仅日后启用 D 案时需要）：

```json
{
  "version": "3.16.1001",
  "jar": "https://<community-domain>/api/artifacts/LMCL-3.16.1001.exe",
  "jarsha1": "<sha1>",
  "force": false,
  "preview": false
}
```

字段依据：`RemoteVersion.java:31-47` —— `version` 必填；`jar` 与 `jarsha1` 必须同时存在，否则抛 `IOException("No download url is available")`；`force`/`preview` 可选。**首发不托管此文件**。

### 4.5 构建渠道值与相关约束（与步骤 02/18 联动）

- 发行构建：`VERSION_TYPE=stable`（version type 进入 `assets/hmcl.properties` 的 `hmcl.version.type`）；
- 开发/预览包：`VERSION_TYPE=dev`；
- **禁止 `nightly`**：会触发 `isNightly()` 公告卡，且 `IntegrityChecker.isOfficial()` 在 `GITHUB_SHA` 非空时把构建视为官方（`IntegrityChecker.java:142-143`）；
- CI 构建脚本增加断言：`assets/hmcl.properties` 中 `hmcl.version.type` ∈ {stable, dev}，否则构建失败。

### 4.6 顺带记录的产品事实（不属本步范围，避免后踩）

- 非官方构建在账号部分会显示 `unofficial.hint` 警告（`CreateAccountPane.java:355`、`MicrosoftAccountLoginPane.java:153`）；文案位于 `assets/lang/I18N*.properties`（已登记的资源侵入），可在步骤 03 统一改写为社区版声明；
- Microsoft 登录的 OAuth client id 来自构建期 `MICROSOFT_AUTH_ID`（官方 CI secret）；我们没有该 id 时 `Accounts.OAUTH_CALLBACK.getClientId().isEmpty()` 为真，登录按钮直接禁用（`MicrosoftAccountLoginPane.java:144-152`）。**这是"账号体系"的产品决策**（自建 OAuth 应用 / 只支持离线与第三方认证），写入 `00-整体要求.md` §12 开放问题，不在本步解决。

### 5.2 抓包证明（唯一可信证据）

```bash
mitmproxy -p 8888
HMCL_JAVA_OPTS="-Dhttp.proxyHost=127.0.0.1 -Dhttp.proxyPort=8888 -Dhttps.proxyHost=127.0.0.1 -Dhttps.proxyPort=8888" \
  java -jar LMCL-*.jar
```

操作序列：启动 → 设置页切换更新渠道（stable↔dev）→ 开关"预览更新" → 打开"关于" → 触发一次崩溃（临时抛异常）→ 退出。

判定：

- **必须无**：`*.huangyuhui.net`、`ci.huangyuhui.net`、`hmcl.huangyuhui.net`；
- 允许出现：BMCLAPI（若点击下载游戏）、Mojang、`lmcl.example`（更新检查不会走到，预期也无）；
- 有其它未知域名 → 记录并回到 §2 对照（可能来自 JavaFX WebView、账号、公告），登记后再决定。

### 5.3 强制参数覆盖测试（证明"钉住"有效）

```bash
HMCL_JAVA_OPTS="-Dhmcl.self_integrity_check.disable=true" java -jar LMCL-*.jar
```

期望日志仍出现 `Failed to check for update`（根因 `Self verification failed`），即外部参数被 Bootstrap 覆盖。若该构建设置了 `-Dhmcl.community.dev=true`，则此测试不适用（属预期）。

### 5.4 `--apply-to` 篡改路径测试

```bash
cp LMCL-*.jar /tmp/evil.jar
java -jar LMCL-*.jar --apply-to /tmp/evil.jar
```

期望：进程在 `UpdateHandler.applyUpdate` 抛 `IOException("Self verification failed")`（终端/日志可见），`/tmp/evil.jar` 未被修改。**不允许**出现静默替换成功。

### 5.5 渠道值测试

- `VERSION_TYPE=stable` 构建启动 → 主界面无 "nightly/dev" 公告卡；
- `VERSION_TYPE=dev` 构建 → 出现 dev 提示卡（且 `isOffical()` 为 false）；
- 记录 `assets/hmcl.properties` 里的 `hmcl.version.type` 值作为验收证据。

### 5.6 崩溃链路回归

- 触发崩溃 → 崩溃窗口弹出 + 日志文件写出 + 抓包无网络；
- 若步骤 04 的 relocate 最终为 Go，则本项必须重测（`CrashReport.shouldBeReport()` 依赖包名字符串的动态）。

## 7. 回退方案

- 删除 `CommunityBootstrap` 两行 `System.setProperty(...)`（或整个类）→ 恢复上游默认行为；
- `HMCL/build.gradle.kts` 的 `Main-Class` 改回 `org.jackhuang.hmcl.Main`；
- **任何情况下都不得把更新源改回 `https://hmcl.huangyuhui.net/api/update_link`**：守卫虽然仍会拦截，但"官方源"一旦写死，未来任何一次校验开关误置都会把用户带去官方版。
