# 步骤 02 · CI 三工作流落地

> **阶段**：阶段一 · 工程底座 ｜ **优先级**：P0 ｜ **工期**：5 天（含跑通与踩坑）
> **前置**：[步骤 01](01-仓库建立与上游同步机制.md) ｜ **后续**：无
> **侵入点**：0

---

## 1. 目标

建立"同步上游 → 验证编译 → 构建发布"的全链路 CI，使每次上游同步和每次发布都有机器验证，而不是靠人肉操作。

三份工作流（**原文已随包提供**，本仓库内位于 [`docs/附录/CI工作流/`](../附录/CI工作流/)）：

```
.github/workflows/
├── sync-upstream.yml   定时拉上游，自动合并；成功开 PR，冲突开 issue
├── ci.yml              每次 push / PR 验证编译
└── build-release.yml   打标签后构建并发布 GitHub Release
```

| 工作流 | 触发 | 产出 |
|---|---|---|
| `sync-upstream.yml` | 每天 UTC 18:17（北京时间次日 02:17）+ 手动 | 同步分支 + PR，或冲突 issue |
| `ci.yml` | push 到 `main` 与 `build/*`（发版分支）、任意 PR、手动 | 4 类构建产物 artifact |
| `build-release.yml` | 推送 `v*` 标签 + 手动 | GitHub Release + 每文件 `.sha256`；加签/SBOM/人工放行由[步骤 18](18-内存优化P2-发布准备.md) 扩展 |

---

## 2. 背景与决策依据

| 决策 | 内容 | 理由 |
|---|---|---|
| 只用 `ubuntu-latest` | 单 runner 出全部产物 | HMCL 的 `makeExecutables` 是**纯字节拼接**：把 jar 追加到 `assets/HMCLauncher.exe` / `.sh` stub 之后，不依赖目标平台。我们的 stub 由[步骤 20](20-HMCLauncher启动壳重建.md) 从 HMCLauncher fork 编译产出，以 `HMCL_LAUNCHER_EXE` 注入（文件 basename 必须为 `HMCLauncher.exe`，否则 `makeExecutables` 找不到 `assets/HMCLauncher.exe`）；sha 固定后随仓库提交 |
| 计费 | ubuntu 1x，Windows 2x，macOS 10x | 单 ubuntu 可省掉 2–10 倍 Actions 分钟数 |
| 定时同步而非手动 | 每天一次 | 上游活跃，手动同步容易积压；冲突时会开 issue 提醒 |
| 版本号来自标签 | `v3.16.1000` → `-Pversion=3.16.1000` | 一眼看出基于哪个上游版本；构建号从 1000 起，**不再使用 `-community.N` 后缀**（避免污染上游版本解析/配置迁移，GPLv3 第 7 条的可区分性由产品名 + 数字段共同满足；定案见步骤 18 §2） |

## 3. 详细实施

### 3.1 落地四步

1. **复制 `.github` 整个目录到 fork 仓库根目录**
   ```bash
   mkdir -p .github/workflows
   cp docs/附录/CI工作流/*.yml .github/workflows/
   ```
   > 注意：首次同步上游时，上游自带的 `gradle.yml` 会与我们的 CI 并存并重复运行。**第一次合并后删除上游原来的 `gradle.yml`**（保留 `ci.yml` 作为唯一编译验证）。

2. **开启写权限**：仓库 `Settings → Actions → General → Workflow permissions` 设为 **Read and write**（`sync-upstream.yml` 需要推分支、开 PR、开 issue）。

3. **配置 Secrets**（见 3.3）。

4. **手动跑一次验证**：`Actions → Sync Upstream → Run workflow`，输入 `upstream_ref`（如 `release/3.16`），确认能正常合并或正确报冲突。

> fork 仓库的 Actions 默认可能是关闭的，首次需到 Actions 页面手动启用。

### 3.2 三个工作流的关键配置（易错点）

| 配置 | 值 | 为什么不能省/不能错 |
|---|---|---|
| JDK | `distribution: zulu`、`java-version: 17` | 与官方 CI 一致；Zulu 的 `jdk+fx` 包最省事 |
| `java-package` | **`jdk+fx`** | **不能省**：普通 JDK 不带 JavaFX，构建直接失败 |
| 虚拟显示 | `xvfb-run --auto-servernum ./gradlew ...` | **不能省**：无头 Linux 上 JavaFX 相关任务需要虚拟显示 |
| JVM 参数 | `JAVA_TOOL_OPTIONS: -Djava.awt.headless=true` | 避免 AWT 在无显示环境下抛错 |
| Gradle 缓存 | `gradle/actions/setup-gradle@v5` + `cache-cleanup: never` | 保证缓存不被自动清理，冷启 5–10 分钟 → 有缓存 3–5 分钟 |
| `--no-daemon --parallel` | 构建参数 | CI 环境一次性进程，daemon 无益且可能残留 |
| 产物上传 | `actions/upload-artifact@v7` + `archive: false` | 产物本身已是压缩包，再打 zip 无意义且慢 |
| Release | `softprops/action-gh-release@v2` + `generate_release_notes: true` | 省掉手写 changelog |
| stub 注入（步骤 20 完成后回填） | 发布工作流设 `HMCL_LAUNCHER_EXE: ${{ github.workspace }}/lib/stub/HMCLauncher.exe` | 不设 = 内嵌**上游官方 stub**（HMCL 品牌与版权资源）；basename 不是 `HMCLauncher.exe` 时会被静默忽略、同样回落到官方 stub |

### 3.3 Secrets

| Secret | 必需性 | 说明 |
|---|---|---|
| `MICROSOFT_AUTH_ID` | 视构建要求 | Microsoft OAuth App ID，官方 CI 即在使用 |
| `MICROSOFT_AUTH_SECRET` | 视构建要求 | 配套密钥 |
| `CURSEFORGE_API_KEY` | 否 | 可用 `-Dhmcl.curseforge.apikey=` 替代 |
| `SIGNING_PFX_BASE64` | **发布必需** | OV 代码签名证书（PFX）的 base64；`osslsigncode` 在 ubuntu runner 上使用（步骤 18 §4） |
| `SIGNING_PFX_PASSWORD` | **发布必需** | PFX 密码 |
| `SIGNING_TIMESTAMP_URL` | 否 | RFC3161 时间戳服务；缺省用证书默认/`http://timestamp.digicert.com` |
| `GITHUB_TOKEN` | 不用配 | Actions 自动注入 |

> 若不想自建 OAuth 应用，先确认上游是否有默认可沿用的值（`-Dhmcl.microsoft.auth.id=` / `.secret=` 可覆盖）。
> 签名私钥只放 GitHub Secrets（production 环境限定），**不得**进入仓库、构建缓存或 artifact；详见步骤 18。

### 3.4 版本号与标签规则

```bash
# 打标签（构建号从 1000 起，每次发布递增）
git tag v3.16.1000
git push --tags
```

`build-release.yml` 的解析逻辑：

```bash
TAG="${github.ref_name}"              # v3.16.1000
VERSION="${TAG#v}"                    # 3.16.1000
VERSION_ROOT="${VERSION%.*}"          # 3.16
BUILD_NUMBER="${VERSION##*.}"         # 1000
UPSTREAM_BASELINE=$(sed -n 's/^baseline_tag=//p' patches/BASELINE.txt)        # v3.16.4
UPSTREAM_BASELINE_COMMIT=$(sed -n 's/^upstream_sha=//p' patches/BASELINE.txt) # fbcc1747…
VERSION_ROOT="$VERSION_ROOT" BUILD_NUMBER="$BUILD_NUMBER" \
  UPSTREAM_BASELINE="$UPSTREAM_BASELINE" UPSTREAM_BASELINE_COMMIT="$UPSTREAM_BASELINE_COMMIT" \
  ./gradlew build
```

> **不要用 `-Pversion=`**：上游 `HMCL/build.gradle.kts:30/37` 只用环境变量 `VERSION_ROOT` + `BUILD_NUMBER` 拼版本；`-Pversion` 会被忽略。未设 `BUILD_NUMBER` 时产物是 `3.16.SNAPSHOT`（CI 分支构建即如此）。

**命名法：`v<上游基线的 major.minor>.<构建号>`**（例：上游 `3.16.4` → 我们 `3.16.1000`，下一次 `3.16.1001`；上游升到 `3.17` 后改为 `3.17.1000`）。好处：

- 一眼看出基于哪个上游版本线，便于用户和 issue 排查；
- **纯数字段**，`VersionNumber.asVersion`（HMCLCore `VersionNumber.java:38`）、配置迁移比较、Gradle 版本注入都不会遇到非数字后缀；
- 与上游官方版本号明确不同 → 满足 GPLv3 第 7 条"合理方式区分"的要求（产品名同时不同，见步骤 03）；
- 排序天然正确（同上游线内按构建号递增）。

> **禁止**再使用 `-community.N` / `-SNAPSHOT` 等后缀；`v3.13.0-community.1` 是旧稿口径，仅作历史对照。
> 产物命名分两层：Gradle 内部产物保持上游 `HMCL-<version>.*`（工程名与 `archiveBaseName` 都不改）；`build-release.yml` 在 `dist/` 重命名为发行名 `LMCL-<version>-<arch>.<ext>`，`arch` 取值 `win-x86`（exe，32 位壳）/`any`（jar、sh）/`all`（deb）。产品名已于 2026-10-21 定为 LMCL（00 §13 #18）。

### 3.5 同步工作流的行为细节

`sync-upstream.yml` 的实际行为（实现已随包提供）：

1. `fetch-depth: 0` 拿完整历史；
2. `git merge-base` 判断是否已是最新（相同则输出 `uptodate` 并退出）；
3. 新建 `sync/upstream-<UTC时间戳>` 分支，尝试 `git merge`；
4. 干净 → 推分支 + `gh pr create`（base `main`）；
5. 冲突 → 先 `git diff --name-only --diff-filter=U` 记录冲突文件，再 `git merge --abort`，**仍然推送分支**（方便人工接手），然后开 issue 并附冲突文件清单；
6. issue 打 `upstream-sync` 标签，若标签不存在则退化为无标签创建（脚本里做了 `||` 兜底）。

人工处理冲突的标准动作：

```bash
git fetch origin
git switch sync/upstream-<timestamp>
git merge upstream/<ref>        # 重新触发冲突，逐个解决
# 解决后
git add -A && git commit
git push
```

### 3.6 成本与配额

| 项目 | 说明 |
|---|---|
| Runner | 只用 `ubuntu-latest`（1x 计费） |
| 免费额度 | 私有仓库 2000 分钟/月；**公开仓库免费无限** |
| 单次构建 | 冷启约 5–10 分钟，有 Gradle 缓存后约 3–5 分钟 |
| 定时任务 | GitHub 会停用 **60 天无任何提交** 的仓库的 schedule → 需保持仓库活跃 |

**省额度技巧**：`ci.yml` 只对 `main`/`build/*` 的 push 和 PR 触发，且 `paths-ignore: '**.md'`；日常开发在 `feature/*` 分支（不触发），别频繁 push 到 main。

## 4. 验收 Checklist

- [ ] `.github/workflows/` 下三个文件已就位，且 `gradle.yml`（上游自带）已删除
- [ ] Workflow permissions 已设为 Read and write
- [ ] 必要 Secrets 已配置（含 `SIGNING_PFX_BASE64`/`SIGNING_PFX_PASSWORD`，**仅 production 环境可读**）
- [ ] 手动运行 `Sync Upstream` 成功（或正确报冲突并开 issue）
- [ ] `ci.yml` 在 PR 上跑绿，4 个 artifact（jar/exe/sh/deb）均上传
- [ ] 打预发布标签 `v3.16.1000-rc.1`（或 workflow_dispatch + `prerelease=true`），产出 Release 且附每文件 `.sha256`
- [ ] 产物 exe 已在 ubuntu 上 `osslsigncode` 签名，Windows 侧 `signtool verify /pa` 通过（步骤 18）
- [ ] SBOM（CycloneDX）已随 Release 上传，签名后的 SHA-256 已重算
- [ ] 计时记录：冷启动构建时长、有缓存构建时长（写入 CI-使用说明或本文备注）
- [ ] 确认 `v*` 标签不会越过人工放行直接进正式发布（production 环境审批 + `prerelease` 默认开）

> 本步骤只落地"基础三工作流"；签名、SBOM、灰度、撤回等发布治理在[步骤 18](18-内存优化P2-发布准备.md) 中增补，两处口径以 18 为准。

## 5. 风险与应对

| 风险 | 等级 | 应对 |
|---|---|---|
| `java-package: jdk+fx` 漏配 → 构建失败 | 中 | 已写入本节易错点表；模板中已固化 |
| 无 `xvfb-run` → JavaFX 任务失败 | 中 | 同上 |
| 上游 `gradle.yml` 与本项目 CI 并存 → 重复构建 | 低 | 首次合并后删除上游 workflow |
| 定时任务被 GitHub 停用（60 天无提交） | 中 | 保持仓库活跃；冲突 issue 也是活动；必要时手动 dispatch |
| `gh pr create` 因默认分支名不同失败 | 低 | 确认 `main` 是仓库默认分支；脚本里 base 为 `main` |
| 签名私钥泄露 / 滥用 | **高** | PFX 只放 production 环境 Secrets；workflow 不 `echo`；PR 构建**禁止**使用签名密钥（只有 tag 触发的 release job 能读）；轮换证书按步骤 18 §4.7 |
| Secrets 泄露 | **高** | 只在 repo Secrets 中保存，不在 workflow 里回显；`CURSEFORGE_API_KEY` 用 JVM 参数注入 |
| macOS 产物缺失 | 低 | 首发不做 `.dmg`；需要时再单独加 `macos-latest` job（10x 计费） |

## 6. 可选扩展（首发不做）

- **多架构产物**：LoongArch / RISC-V 需 self-hosted runner（GitHub 官方不提供）。
- **同步到自有存储**：`build-release.yml` 里已预留 COS 上传注释示例，可换 rclone / 任意对象存储。
- **自动更新源**：`-Dhmcl.update_source.override=` 指向自己的更新接口 —— **但首发阶段自更新是禁用的**（见[步骤 05](05-自更新禁用与完整性校验.md)）。
