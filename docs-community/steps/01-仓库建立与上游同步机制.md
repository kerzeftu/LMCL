# 步骤 01 · 仓库建立与上游同步机制

> **阶段**：阶段一 · 工程底座 ｜ **优先级**：P0（一切工作的前提） ｜ **工期**：3–5 天
> **前置**：无 ｜ **后续**：[步骤 02 · CI 三工作流落地](02-CI三工作流落地.md)
> **侵入点**：0（本步骤不改任何产品代码）

---

## 1. 目标

建立一个可持续跟随上游的 fork 仓库，并把"如何同步上游"固化成可重复执行的流程，而不是每次临时决策。

完成标志：

1. 仓库可从上游 `release` 分支拉取更新；
2. 有明确的开发分支模型；
3. 有一个可执行的同步脚本/命令（patch 或 merge 二选一，并说明理由）；
4. 记录了**本次实施所基于的上游基线 SHA**。

---

## 2. 背景与决策依据

| 决策 | 内容 | 理由 |
|---|---|---|
| 跟哪个分支 | **跟 release 分支（如 `release/3.16`），不跟 `main`** | `main` 是 beta 开发分支，官方 README 明确说明含额外测试功能、可能不稳定 |
| 同步策略 | **首选 patch 策略** | 本项目侵入点压到 3 处且长期固定，patch 冲突点明确、历史干净、可独立审查 |
| 何时改 merge | 改动超过 **20 处**或高度分散时 | patch 维护成本会超过 merge 的收益 |
| 仓库形态 | 公开仓库 | GPLv3 要求对外分发时提供对应源码，公开仓库一次满足 |

> 上游处于活跃开发中，release 分支号会变化（`release/3.16` → 后续版本）。实施时以 `git branch -r` 实际结果为准，不要写死。

---

## 3. 详细实施

### 3.1 创建 fork 并配置远端

```bash
# 1. 在 GitHub 上 fork HMCL-dev/HMCL 到自己的账号/组织

# 2. 克隆自己的 fork
git clone git@github.com:<your-org>/<your-repo>.git hmcl-community
cd hmcl-community

# 3. 上游远端指向官方仓库（不要只留 origin）
git remote add upstream https://github.com/HMCL-dev/HMCL.git
git remote -v          # 应看到 origin=<你的 fork>，upstream=<官方>

# 4. 拉取全部分支与标签（同步需要完整历史才能算 merge-base）
git fetch upstream --prune --tags --force
```

### 3.2 选择上游基线

```bash
# 列出上游分支，确认当前 release 分支号
git branch -r | grep upstream/release

# 锁定基线（本文档口径：v3.16.4 = release/3.16 线的最新稳定发行）
# 用 tag 而不是 release/3.16 分支头，保证日后重建仓库仍落在同一提交
git rev-parse v3.16.4                     # 实测：fbcc17472f08e877d60d6b715734e8054e9e61ee
git switch -c main v3.16.4
git push -u origin main

# 记录基线（写进 patches/BASELINE.txt，便于日后追溯）
git rev-parse v3.16.4 > patches/BASELINE.txt
```

`patches/BASELINE.txt` 内容示例（每次同步后更新）：

```
upstream_ref=release/3.16
baseline_tag=v3.16.4
upstream_sha=fbcc17472f08e877d60d6b715734e8054e9e61ee
synced_at=2026-10-21
```

> 注意区分：**基线**固定在 tag `v3.16.4`（可复现）；**同步源**是分支 `release/3.16`（会前进）。每次同步用 `git diff upstream/release/3.16..main` 的语义是"相对上游最新"，而 `patches/BASELINE.txt` 记录的是**我们上次实际验证过的提交**，两者都要写。上游发布 `v3.16.5`/`release/3.17` 后，先改 `upstream_ref`/`baseline_tag`，再按 §3.4 重建 patch 与出包分支。

### 3.3 分支模型

| 分支 | 用途 | 生命周期 |
|---|---|---|
| `main` | 我们的稳定线，所有交付都合入这里 | 长期 |
| `feature/<step>-<name>` | 单个步骤的开发分支（如 `feature/07-source-import`） | 每步骤一条，合后删除 |
| `build/<version>` | patch 策略下，从干净上游起的分支，用于 apply patch 后出包 | 每版本一条 |
| `sync/upstream-<timestamp>` | CI 自动同步产生的分支（见步骤 02） | 合并或放弃后删除 |

**约定：`main` 只在 CI 绿的状态下推进。** 上游同步必须经 PR 验证后合并，不允许本地直接 push。

### 3.4 同步机制 A —— patch 策略（推荐，首发采用）

一次性导出本项目相对上游的全部改动：

```bash
# 导出：只含我们自己的改动
git diff upstream/release/3.16..main > patches/community.patch
```

上游更新后重建：

```bash
git fetch upstream --prune --tags --force
git switch -c build/3.16.1000 upstream/release/3.16
git apply --3way patches/community.patch     # 冲突点明确、逐个 review
./gradlew build                              # 先验证能编译
git switch main
# 通过后将 build/3.16.1000 合并回 main；或以 build 分支为发布基线（02 的 ci.yml 已对 build/* push 触发）
```

要点：

- `--3way` 让冲突以 diff3 形式呈现，比纯 `git apply` 好排查。
- patch 冲突**集中在固定几处**（3 处侵入点），这正是它优于 merge 的原因。
- 若 patch 已失效（上游大改），重新从当前 `main` 生成，不要堆积多个 patch 文件。
- 生成 patch 前确认工作区干净：`git status` 无未提交改动。

### 3.5 同步机制 B —— merge 策略（改动扩大后的退路）

```bash
git switch main
git fetch upstream --prune --tags --force
git merge --no-edit upstream/release/3.16
# 冲突解决后
git push origin main
```

CI 的 `sync-upstream.yml`（步骤 02）即按此策略自动执行：干净合并 → 开 PR；有冲突 → 记录冲突文件后中止并开 issue。

### 3.6 目录与文件约定

```
<repo>/
├── patches/
│   ├── community.patch      # 我们相对上游的改动（patch 策略下维护）
│   └── BASELINE.txt         # 当前基线 ref + SHA + 同步日期
├── docs-community/          # 本套开发文档（**不能放 docs/**，见下）
├── docs/                    # ⚠️ 上游自带目录（Contributing/Localization/PLATFORM/schemas），不要覆盖
├── HMCL/                    # 上游模块（尽量不改）
├── HMCLCore/                # 上游模块（尽量不改）
└── HMCLBoot/                # 上游模块（尽量不改）
```

补充约定：

- `patches/` 与 `docs-community/` 属于本项目自有文件，**永远不会与上游冲突**（上游没有这两个路径）。
- **上游已经有 `docs/`**（`Contributing*.md`、`Localization*.md`、`PLATFORM*.md`、`schemas/` 等），本套文档必须放 `docs-community/`；早期草案误写为 `docs/`，按本文执行。18 引用的主题包 schema 仍在**上游** `docs/schemas/theme-pack/1.0.0.json`。
- 不使用 git submodule 引入上游，保持单仓库、单历史。
- 不在 `main` 上保留实验性提交；实验走 `feature/*`。

### 3.7 首次基线检查（动手前必须做）

在写第一行业务代码前，先确认这几件事与文档假设一致：

```bash
# 1. 确认上游分支名与基线
git branch -r | grep upstream/

# 2. 确认三模块结构存在
ls -d HMCL HMCLCore HMCLBoot

# 3. 确认 Metadata 位置（步骤 03 要改）
find . -name Metadata.java -not -path "*/build/*"

# 4. 确认自更新链路存在（步骤 05 要处理）
ls HMCL/src/main/java/org/jackhuang/hmcl/upgrade/ 2>/dev/null || \
  find . -path "*/upgrade/UpdateChecker.java" -not -path "*/build/*"

# 5. 确认无 .fxml 文件（步骤 04 的前提假设）
find . -name "*.fxml" -not -path "*/build/*" | wc -l    # 期望 0
```

任一项与文档不符 → 先更新对应步骤文档，再动手。

## 4. 验收 Checklist

- [ ] `git remote -v` 同时存在 `origin`（自己的 fork）与 `upstream`（官方）
- [ ] 本地 `main` 基于选定 release 分支，且已推送到 `origin`
- [ ] `patches/BASELINE.txt` 已记录 ref + SHA + 日期
- [ ] 同步机制二选一已定案，并在本文/README 留痕
- [ ] 已执行 3.7 的 5 项基线检查，结论与文档假设一致
- [ ] `./gradlew build` 在本地可跑通（作为后续所有步骤的基线）

---

## 5. 风险与应对

| 风险 | 等级 | 应对 |
|---|---|---|
| 误跟 `main` 导致基线不稳定 | 中 | 分支模型写死 release；CI 的 `upstream_ref` 默认值同步修改 |
| release 分支改名/消失 | 中 | 每次同步前 `git branch -r` 确认；CI 里对不存在分支明确报错（见 sync-upstream.yml 的 `git rev-parse --verify` 检查） |
| patch 长期不更新导致 apply 失败 | 中 | 每次同步后立即重新生成 patch，并更新 BASELINE |
| 误把构建产物提交进仓库 | 低 | 依赖上游 `.gitignore`；提交前 `git status` 复核 |
