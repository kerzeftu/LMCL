# 步骤 06 · 数据目录与用户迁移

> **阶段**：阶段一 · 工程底座 ｜ **优先级**：P1 ｜ **工期**：3–5 天
> **前置**：[步骤 03](03-产品身份与合规改造.md)、[步骤 05](05-自更新禁用与完整性校验.md) ｜ **后续**：[步骤 07](07-下载源配置.md)
> **侵入点**：0（新增 `community.env` / `community.migration` 包 + Bootstrap 两行属性）
> **基线依赖**：本章所有路径/文件结论来自 v3.16.4 源码实读（`Metadata.java`、`SettingsManager.java`、`LegacyConfigMigrator.java`），**不是** old HMCL 的 `config.json` 单体模型。

---

## 1. 目标

让社区版与官方 HMCL **各自独立持有启动器数据**（设置/状态/账号缓存），同时让用户可以安全、可控地把官方 HMCL 的配置"带过来"，且带过来之后两边互不踩踏。

完成标志（DoD）：

1. 首次运行即落在社区版自己的两个根目录（本地工作区目录 + 用户共享目录），不读写官方目录；
2. `-Dhmcl.dir` / `-Dhmcl.home` 及对应环境变量的覆盖仍然有效（便于测试、便携部署）；
3. 启动器目录不可写时（Program Files、只读介质）自动降级到用户目录，**不崩溃、不静默丢设置**；
4. 官方数据导入是**用户显式触发的动作**（[步骤 13](13-首页组件化A-框架搭建.md) 首页提示条 + 设置面板 `data` 分组），启动时不自动复制、不弹模态框；
5. 导入有清单（哪些文件、哪些字段被丢弃/净化）、有 receipt（幂等，可重复点不重复导入）、失败可回滚；
6. 凭据（账号 token）默认**不导入**；导入后账号列表可重建但需重新登录；
7. 所有结论有 JUnit 测试（jimfs 或临时目录），三平台路径在 CI 至少各跑一次（Windows 必跑）。

## 2. 上游目录与设置模型（v3.16.4 实测）

### 2.1 两个根目录，职责不同

| 根 | 源码常量 | 覆盖属性 | 覆盖环境变量 | 默认值（无覆盖时） | 内容 |
|---|---|---|---|---|---|
| **本地/工作区** | `Metadata.HMCL_LOCAL_HOME` | **`hmcl.dir`** | `HMCL_LOCAL_HOME` | `CURRENT_DIRECTORY/.hmcl`（即启动器所在工作目录下的 `.hmcl`） | `config/`、`state/`、`cache/`、`private/`、`logs/`、`dependencies/` |
| **用户/共享** | `Metadata.HMCL_USER_HOME` | **`hmcl.home`** | `HMCL_USER_HOME` | Linux/BSD：`$XDG_DATA_HOME/hmcl` 或 `~/.local/share/hmcl`；其它系统：`OperatingSystem.getWorkingDirectory("hmcl")`（Windows 即 `%APPDATA%/hmcl`） | `config/`、`state/`、`private/`（跨工作区共享的设置/账号） |

> ⚠️ 旧版本文档把两个属性写反了：**`hmcl.home` 是"用户共享目录"，`hmcl.dir` 才是"启动器本地目录"**。以本表为准。
> 另外 `Metadata.DEPENDENCIES_DIRECTORY` 可用 `hmcl.dependencies.dir` / `HMCL_DEPENDENCIES_DIR` 覆盖，默认 `<本地目录>/dependencies`；`Metadata.MINECRAFT_DIRECTORY`（默认游戏目录）由 `OperatingSystem.getWorkingDirectory("minecraft")` 决定，**不属于启动器数据**。

**为什么必须同时覆盖两个根**：只覆盖 `hmcl.dir` 时，账号、`user-settings.json` 仍写在官方 `%APPDATA%/hmcl` 下 → 与官方共享同一份账号/全局设置，仍会互相覆盖。独立目录的判定标准是"两个根都不在官方默认位置"。

### 2.2 文件清单（`SettingsManager.java:59-140` 实测）

| 相对路径 | 用途 | 备注 |
|---|---|---|
| `<本地>/config/launcher-settings.json` | 启动器设置（下载源、Java、主题、语言…） | `LauncherSettings`，含 `versionListSource` / `fileDownloadSource` |
| `<本地>/state/launcher-state.json` | 本地状态（窗口、最近选中、提示记录） | `LauncherState` |
| `<本地>/config/game-directories.json` | 游戏目录列表 | `GameDirectories` |
| `<本地>/config/game-settings.json` | 各实例设置（以路径为键） | `GameSettings.Instance` 容器 |
| `<本地>/config/accounts.json` | 账号元数据（本地） | 不含私密 token |
| `<本地>/private/account-private-data.json` | 账号私密数据（token 等） | **敏感** |
| `<本地>/config/authlib-injector-servers.json` | 第三方认证服务器列表 | |
| `<本地>/cache/authlib-injector-server-metadata.json` | 上述服务器元数据缓存 | 可重建 |
| `<用户>/config/user-settings.json` | 跨工作区共享设置 | `UserSettings` |
| `<用户>/state/user-state.json` | 跨工作区共享状态 | `UserState` |
| `<用户>/config/user-game-directories.json` | 用户级游戏目录 | |
| `<用户>/config/user-accounts.json` | 用户级账号元数据 | |
| `<用户>/private/user-account-private-data.json` | 用户级账号私密数据 | **敏感** |
| `<本地>/settings.json` | **旧版迁移输入**（`LEGACY_SETTINGS_LOCATION`） | 上游会迁移到新格式并写 receipt |

补充事实：

- 每个文件由 `JsonSettingFile<T extends ObservableSetting & JsonSchemaSetting>` 托管，带 `schema` 字段与"读/写权限"状态（`READ_WRITE`、`READ_ONLY`、`READ_ONLY_PRESERVE_SCHEMA`、`UNREADABLE`），加载时通过 `JsonSchema.check` 校验；
- 上游自带旧格式迁移器 `LegacyConfigMigrator`（1431 行）：识别 `hmcl.json` / `.hmcl.json` / `settings.json`（`LEGACY_CURRENT_CONFIG_VERSION = 2`），迁移下载源字符串（`default/balanced/official/mojang/mirror/bmclapi` → `DownloadSource` 枚举名，`LegacyConfigMigrator.java:942-958`），并写 `MigrationReceipt` 防重复迁移；
- 迁移有测试：`HMCL/src/test/java/org/jackhuang/hmcl/setting/{LauncherSettingsMigrationTest,UserSettingsTest,MigrationReceiptTest,GameDirectoriesTest}.java`，可作为我们导入器的行为基准。

## 3. 决策

| 决策点 | 结论 | 理由 |
|---|---|---|
| 独立程度 | **两个根目录都独立** | 只独立本地目录仍会与官方共享账号/用户设置（§2.1） |
| 命名 | 本地：`<启动器目录>/.lmcl`；用户：Windows `%APPDATA%/LMCL`、Linux `$XDG_DATA_HOME/LMCL` 或 `~/.local/share/LMCL`、macOS `~/Library/Application Support/LMCL` | 与产品身份（步骤 03）一致；`LMCL` 全大写避免与官方 `hmcl` 混淆 |
| 注入方式 | Bootstrap 计算绝对路径后写 `hmcl.dir` / `hmcl.home`，**早于 `Metadata` 类初始化** | 两个属性都在 `Metadata` 静态字段初始化时读取一次，错过时机无效 |
| 是否自动导入官方数据 | **否**，只检测 + 记录；导入是用户显式动作（13 的首页提示条 / 设置面板入口） | 启动期复制几十 MB/含凭据的文件 = 不可控、不可回滚；且违反"绝不阻断启动" |
| 导入范围 | 设置/状态/游戏目录/认证服务器列表；账号元数据可选，**私密数据不导入** | 凭据迁移=安全责任；设置迁移才是用户痛点 |
| 旧格式 | 交给上游 `LegacyConfigMigrator`：把旧文件放到**我们的本地目录**根下再让上游迁移 | 不重写迁移逻辑，复用上游 1431 行迁移器与 receipt 机制 |
| 实例目录（`versions/`、`mods/`） | 不复制、不迁移 | 属于游戏目录，用户可让两个启动器共用游戏目录（并发运行风险见 §6） |

## 4. 详细实施

### 4.1 新增 `community.env.CommunityPaths`

位置：`HMCL/src/main/java/org/jackhuang/hmcl/community/env/CommunityPaths.java`（新增包，已在 `00-整体要求.md` §4.2 登记）

职责：**纯计算 + 纯 IO 探测**，不依赖 JavaFX，可在单元测试里直接调用。

```java
package org.jackhuang.hmcl.community.env;

/// 计算社区版的两个数据根目录（本地工作区 / 用户共享），并写入上游可识别的系统属性。
/// 所有方法都允许在无 UI 环境下调用，便于测试。
public final class CommunityPaths {
    /// 产品目录名；改它等于改用户数据位置，发布后不要动。
    public static final String PRODUCT_DIR_NAME = "LMCL";

    /// 本地目录名（放在启动器目录下，保持便携语义）。
    public static final String LOCAL_DIR_NAME = ".lmcl";

    /// 计算本地根：优先显式属性/环境变量，其次 `<启动器目录>/.lmcl`，不可写时降级到
    /// `<用户根>/local`。返回值一定是绝对路径。
    public static Path localHome() { ... }

    /// 计算用户根：优先显式属性/环境变量，其次各平台标准目录下的 `LMCL`。
    public static Path userHome() { ... }

    /// 把两个根写入 `hmcl.dir` / `hmcl.home`；幂等，可重复调用。
    /// 必须在 `Metadata` 类初始化之前调用（由 `CommunityBootstrap` 保证）。
    public static void applySystemProperties() { ... }
}
```

实现要点：

1. **启动器目录怎么取**：jar 场景取 `ProtectionDomain.getCodeSource().getLocation()` 的父目录；exe（stub+jar）场景同样可得（`java -jar LMCL.exe` 时 location 是 exe 路径）。取不到时退化为 `user.dir`；
2. **可写探测**：`Files.createDirectories(localHome)` + 写一个临时文件后删除；失败（`AccessDeniedException`、`ReadOnlyFileSystemException`）→ 降级到 `<userHome>/local` 并 `LOG.warning`；
3. **显式覆盖优先**：`-Dhmcl.dir` / `HMCL_LOCAL_HOME` / `-Dhmcl.home` / `HMCL_USER_HOME` 存在时**完全不改**（这是测试/绿色部署的逃生口），只在日志打印实际生效路径；
4. **绝不读取官方目录**：本类只做路径计算，不做检测（检测在 4.3）；
5. **测试**：用 `jimfs` 注入不可写文件系统验证降级；用临时目录验证三平台分支（通过可注入的 OS 枚举或包级可见方法，避免依赖真实 `%APPDATA%`）。

### 4.2 Bootstrap 注入顺序

**本步直接修改步骤 05 §4.1 交付的 `CommunityBootstrap.main`**（不新建第二个入口类），属性设置顺序升级为：

```java
if (!dev) {
    System.setProperty("hmcl.update_source.override", COMMUNITY_UPDATE_SOURCE);
    System.setProperty("hmcl.self_integrity_check.disable", "false");
}
if (!Boolean.getBoolean("hmcl.community.paths.explicit")) {   // 显式覆盖时不再计算
    CommunityPaths.applySystemProperties();
}
Main.main(args);
```

- `applySystemProperties()` 内部再次判断显式属性是否已存在（双保险），存在则跳过；
- 该方法只做路径计算与目录创建，**不做任何官方数据读取**（4.3 的检测在 `SettingsManager.init()` 之后由 UI 触发，见 4.5）；
- 若路径计算抛出 `IOException`（磁盘满、权限异常）→ 捕获后 `LOG.warning` 并回退到上游默认（共享官方目录），同时写 `community.paths.fallback=true` 的属性供后续 UI 提示；**不允许抛出到 `Main`**（违反"绝不阻断启动"）。

### 4.3 官方数据检测（只读，不复制）

新增 `community.migration.OfficialDataLocator`：给定当前平台，返回**可能**存在的官方数据根列表（按优先级）：

| 平台 | 候选（本地根 / 用户根） |
|---|---|
| Windows | `%APPDATA%/hmcl`（用户根）；`<启动器目录>/.hmcl`、`<安装目录>/.hmcl`（本地根候选）；`%APPDATA%/HMCL`（大小写容错） |
| Linux | `$XDG_DATA_HOME/hmcl` / `~/.local/share/hmcl`（用户）；`~/.hmcl`（本地/旧默认） |
| macOS | `~/Library/Application Support/hmcl`（用户）；`~/.hmcl`（旧默认） |

检测逻辑只做三件事：

1. `Files.isDirectory(...)` + 关键文件存在性（`config/launcher-settings.json` 或旧版 `settings.json`/`hmcl.json`/`.hmcl.json`）；
2. 统计"可导入项"数量（设置文件数、游戏目录数——**不统计实例数与体积**，避免遍历大目录）；
3. 结果写入 `<用户根>/state/community-import-scan.json`（`{"detected":true,"sources":[...],"scannedAt":...}`），供[步骤 13](13-首页组件化A-框架搭建.md) §3.10 的首页提示条与设置面板 `data` 分组使用。

对外 API（13 只调这两个方法，不自己拼路径）：

```java
public final class OfficialDataLocator {
    /// 扫描并落盘；纯 IO，可在 io 线程调用。检测失败返回 detected=false 而不是抛异常。
    public static ScanResult scan();
    /// 读取上次扫描结果；不存在/损坏返回 detected=false。
    public static ScanResult lastScan();
}

public record ScanResult(boolean detected, @NotNull List<Path> sources, boolean ignored,
                         @NotNull Instant scannedAt) { }
```

> 首次启动**不弹模态框**：阶段一没有 dashboard，检测结果只落盘 + 日志一行；阶段四 dashboard 上线后由 13 §3.10 读取 `OfficialDataLocator.lastScan()` 显示提示条与设置入口。

### 4.4 `OfficialDataImporter`（用户触发的导入）

位置：`community.migration.OfficialDataImporter`，接口：

```java
public record ImportRequest(@NotNull Path sourceRoot,        // 官方数据根（本地或用户）
                            @NotNull Set<ImportItem> items,  // 选择导入的类别
                            boolean includeAccounts) { }     // 是否导入账号元数据（私密数据永远不导入）

public record ImportResult(int copied, int skipped, @NotNull List<String> warnings,
                           @NotNull Path receiptPath) { }

/// 执行导入；幂等：同一 sourceRoot + 目标目录组合只成功执行一次（receipt 判定）。
public static ImportResult importFrom(ImportRequest request) throws IOException;
```

**复制映射表**（源 → 目标）：

| 源文件（官方根） | 目标（我们的根） | 类别 | 处理 |
|---|---|---|---|
| `config/launcher-settings.json` | `<本地>/config/launcher-settings.json` | 设置 | 原样复制；复制前校验 `schema` 不超过我们支持的 `LauncherSettings.CURRENT_SCHEMA`，超出则跳过并警告 |
| `config/game-directories.json` | `<本地>/config/game-directories.json` | 游戏目录 | 原样复制（路径是游戏目录，不是启动器目录） |
| `config/game-settings.json` | `<本地>/config/game-settings.json` | 实例设置 | 原样复制；其中键为绝对路径，导入后在 UI 里显示"引用缺失"由上游逻辑处理 |
| `config/authlib-injector-servers.json` | `<本地>/config/authlib-injector-servers.json` | 认证服务器 | 原样复制 |
| `config/user-settings.json` | `<用户>/config/user-settings.json` | 用户设置 | 原样复制 |
| `state/user-state.json` | `<用户>/state/user-state.json` | 用户状态 | 原样复制（含窗口/语言/主题等） |
| `config/accounts.json` / `config/user-accounts.json` | 对应目标 | 账号元数据 | **仅当 `includeAccounts`**；默认 `false` |
| `private/*.json`（账号私密数据） | — | 凭据 | **永不导入** |
| `cache/**`、`logs/**`、`dependencies/**`、`settings.json`（当前格式） | — | — | 不导入 |
| 旧格式 `hmcl.json` / `.hmcl.json` / `settings.json` | `<本地>/hmcl.json`（或对应文件名） | 旧格式 | 复制到我们本地根，**交给上游 `LegacyConfigMigrator` 在下次启动时迁移**；不解析其内容 |
| `versions/`、`mods/`、`saves/` | — | 游戏数据 | 不复制（在游戏目录里，不属于启动器数据） |

**净化规则**（无论哪类，复制前执行）：

1. `version`/`schema` 字段：缺失则补当前 `CURRENT_SCHEMA`；高于当前 schema 则整文件跳过（记 warning）；
2. 下载源字符串：若文件是旧格式（无 schema、只有 `versionListSource` 字符串），按 `LegacyConfigMigrator` 同款映射转为 `DownloadSource` 枚举名（见步骤 07）；
3. `javaDir` 等绝对路径：不存在 → 删除该字段（回退默认 Java），不猜测；
4. 所有指向官方根目录的路径字段（如果发现）→ 重写为我们的对应根（本地/用户分别替换），并在 warnings 里记录；
5. 账号相关文件复制时过滤掉 `clientToken`/`accessToken` 等字段（只保留元数据）；私密数据文件直接跳过。

**receipt 与幂等**：

- receipt 位置：`<用户根>/state/community-import-receipt.json`，内容 `{"source":"<绝对路径>","importedAt":"<ISO8601>","files":[...],"version":1}`；
- 同一 `source` 已成功导入 → 直接返回 `ImportResult(0, n, ["already imported"])`，不覆盖用户此后改过的设置；
- 强制重导：UI 提供"重新导入（覆盖）"二次确认，传 `--force` 语义参数；
- 失败回滚：所有写入先落到目标目录下的临时文件（`*.tmp-<pid>`），全部成功后再原子 `Files.move(REPLACE_EXISTING)`；中途失败删除临时文件，**不留下半份配置**。

### 4.5 与上游加载顺序的关系

`Launcher.start()` 的调用链是：

```
SettingsManager.init();                 // 读取 <本地>/settings.json（旧）或新格式；跑 LegacyConfigMigrator
initializeSettingsRuntime();            // DownloadProviders.init() 等
Platform.runLater(() -> Controllers.initialize(stage) ...)
```

因此：

- **旧格式文件必须在 `SettingsManager.init()` 之前进入我们的本地根**。UI 触发的导入发生在启动之后，无法享受上游旧格式迁移 → 处理方式：旧格式导入后提示"需要重启以完成迁移"，重启时上游自动迁移（receipt 防重复）；这比我们复制 1431 行迁移逻辑便宜得多；
- 新格式文件（带 `schema`）由 `JsonSettingFile` 自动加载，无需重启；但**导入完成后建议重启**（账号与窗口状态在启动时读入），UI 明示；
- 导入器不直接调用 `SettingsManager` 的私有加载函数；它只写文件。加载由下一次启动完成，避免与运行中的状态机竞争。

### 4.7 首次运行（空目录）的完整时序

1. stub 启动 java → `CommunityBootstrap.main`；
2. `CommunityPaths.applySystemProperties()`：计算两个根、创建目录（本地目录在 Windows 设隐藏，可复用上游 `EntryPoint.createHMCLDirectories()` 的行为，但我们的目录由本类创建）；
3. `Main.main` → `EntryPoint.main` → `Launcher.start` → `SettingsManager.init()`：三个目录都不存在文件 → 各 `JsonSettingFile` 使用默认值并标记 `newlyCreated`（上游有该标志）；
4. `OfficialDataLocator.scan()` 在 `Controllers.initialize` 之后异步执行（**不在 FX 线程做磁盘遍历**），结果落盘；
5. 用户正常使用；首次不出现任何模态框。

## 5. 验证

### 5.1 路径与降级

- [ ] 干净 Windows 用户：`%APPDATA%/LMCL/{config,state,private}` 与 `<启动器目录>/.lmcl/{config,state,cache,private,logs}` 被创建，且官方 `%APPDATA%/hmcl` **未被访问**（用 Process Monitor 或临时改名官方目录验证）；
- [ ] 把启动器放进 `C:\Program Files\...`（不可写）：本地根降级为 `%APPDATA%/LMCL/local`，日志有 WARNING，启动成功；
- [ ] `-Dhmcl.dir=D:\tmp\lmcl-local -Dhmcl.home=D:\tmp\lmcl-user` 启动：两处都不用默认路径；
- [ ] 环境变量 `HMCL_LOCAL_HOME` / `HMCL_USER_HOME` 同样生效；
- [ ] Linux（XDG_DATA_HOME 设置/未设置）与 macOS（`~/Library/Application Support/LMCL`）各验证一次；
- [ ] 路径含中文/空格/Unicode → 启动成功，日志路径正确。

### 5.2 导入

- [ ] 用官方 HMCL 3.16.4 生成一份数据目录（含 2 个游戏目录、1 个 authlib 服务器、非默认下载源、自定义主题），导入后重启：设置/游戏目录/认证服务器全部可见；
- [ ] 默认不导入账号：导入前后 `user-accounts.json` 不存在或为空；
- [ ] 私密 token 文件从未被读取（代码评审 + 测试断言 `open` 调用不含 `private/`）；
- [ ] 二次点击导入：返回 "already imported"，不覆盖用户改动；
- [ ] 旧格式（`hmcl.json` 或 `settings.json`）导入 → 提示重启 → 重启后 `launcher-settings.json` 生成、旧文件保留、receipt 存在；
- [ ] 磁盘满/中途失败：目标目录不留 `.tmp-*`，原文件不变；
- [ ] schema 高于当前版本的文件：跳过 + warning，其余文件照常导入。

## 6. 风险与应对

| 风险 | 等级 | 应对 |
|---|---|---|
| 只改了一个根 → 与官方共享账号/用户设置 | **高** | §4.1 强制同时设置两个属性；验收项"官方目录未被访问" |
| 属性注入晚于 `Metadata` 类初始化 → 完全无效 | **高** | Bootstrap 在最前；单元测试断言 `CommunityPaths.applySystemProperties()` 后 `Metadata.HMCL_LOCAL_HOME` 等于预期（需在 `Metadata` 首次访问前调用，测试中用独立 ClassLoader 或 `-D` 预置） |
| 启动器目录不可写 → 用户设置写失败 | 中 | §4.1 降级 + 日志；验收含 Program Files 场景 |
| 导入覆盖用户新配置 | 中 | receipt 幂等 + 默认不覆盖；"重新导入"需二次确认 |
| 旧格式迁移与我们的导入竞争 | 中 | 导入旧格式只复制文件，迁移交给下次启动的上游逻辑；不在运行中调用 `SettingsManager` 私有方法 |
| 与官方同时运行导致实例写坏 | 中 | 用户文档明示"避免同时运行"；日志检测同一游戏目录被占用？（上游无锁，不新增强制互斥） |
| 目录名上线后再改 | 中 | 步骤 03 定案，写入 00 §13 决策记录，发布后冻结 |
| 账号元数据导入后 token 失效 | 低 | 默认不导入账号；若导入，提示"需重新登录" |

---

## 7. 回退方案

- 保留上游默认（不注入属性）即可回到"与官方共享目录"的旧行为：删除 Bootstrap 中 `CommunityPaths.applySystemProperties()` 一行；
- 导入器是独立包，未被上游代码引用，删除文件即可回退（13 的提示条与设置入口同步下线）；
- receipt 与 scan 文件位于我们自己的根下，回退后不影响官方 HMCL。
