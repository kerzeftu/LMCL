# 步骤 18 · 发布准备与风险收口（签名 / SBOM / 灰度 / 回滚）

> **阶段**：阶段五 · 快照与发布 ｜ **优先级**：P1 ｜ **工期**：1–1.5 周
> **前置**：[步骤 17](17-内存优化P1-Windows守护进程.md)（L2 守护）、[步骤 02](02-CI三工作流落地.md)（CI 流水线）、[步骤 20](20-HMCLauncher启动壳重建.md)（stub）、[步骤 03](03-产品身份与合规改造.md)/[04](04-包名Relocate改造.md)/[05](05-自更新禁用与完整性校验.md)（身份链） ｜ **后续**：[步骤 19](19-MD3主题完善.md)
> **代码侵入**：0（只改构建/发布脚本、文档与 CI）
> **产出**：可对外分发的签名产物 + 校验和 + SBOM + 白名单材料 + 灰度/回滚预案；以及**有依据的"L2 发/不发"决策**

## 1. 目标

把项目从"能构建"推进到"**能负责任地发布**"：

1. 首发版本（`3.16.1000`）的 Windows 便携产物完成签名、哈希、SBOM、合规文件；
2. 杀软白名单/误报申诉材料齐备并已提交（若可行）；
3. L2 守护按 [步骤 17](17-内存优化P1-Windows守护进程.md) 的判定表做出**发布 / 不发布**决策（两条路都算成功）；
4. 灰度、撤回、热修流程有明确触发条件与执行人；
5. 用户文档与 FAQ 覆盖安装、数据目录、L2、快照、隐私与 GPL 义务。

完成标志（DoD，满足其一）：

- **A 路线（发布 L2）**：签名产物通过校验、三家杀软无威胁、安全评审通过、灰度无阻断问题、回滚预案演练过；
- **B 路线（不发布 L2）**：书面评估结论（误报率/签名成本/风险不可接受）入档，产物为 `safe` 变体（无 guardian、L2 探测返回不可用），产品用 L0+ 交付。

> 这一步的价值不是"发出去"，而是**让"发/不发、发什么"成为有依据的决策**，而不是临上线才发现装完就报毒、或者发了不该发的东西。

## 2. 发布前决策闸门（先定标准，再动手）

### 2.1 硬门槛（任一不过 → 不发正式版）

| # | 闸门 | 通过标准 | 不通过则 |

### 2.2 L2 专项判定（在 17 的测试全绿之后）

| 维度 | 通过标准 | 不通过则 |
|---|---|---|
| 杀软 | Defender + 360 + 火绒 扫描"无威胁"（或申诉已受理且给出结论） | B 路线 |
| 签名 | guardian 与主 exe 同证书签名 | B 路线（无签名的高权限二进制不可接受） |
| 安全评审 | [17 §2.5](17-内存优化P1-Windows守护进程.md) 检查表 + 独立代码审查通过 | 修复后再评 |

| 知情 | 默认关闭；启用前有明确说明与确认 | 改默认/改文案 |
| 收益 | 内测 10–30 人里，低于 8 GiB 内存的机器启动失败率/卡顿反馈有改善；不出现负反馈集中 | 降级为"实验特性"或不发 |

## 4. 代码签名

### 4.1 结论与方案

| 方案 | 结论 |
|---|---|
| 不签名 | ❌ 不可接受（SmartScreen 拦截 + 高权限二进制无签名） |
| **OV 代码签名证书（PFX）** | ✅ 采用：可自动化、价格相对可控、对 SmartScreen 信誉需累积 |
| EV 证书（硬件令牌/云 HSM） | ⏸ 可选升级：信誉更快，但 CI 集成复杂（需自托管签名机或云签名服务），首发不做硬要求 |

- 证书采购有周期（组织验证、发票/合同流程），**至少提前 2 周启动**；报价以 CA 为准，文档不预设价格；
- 私钥**绝不入库**：PFX 以 base64 存 GitHub Secrets，密码另存；
- 证书有效期通常 1–3 年，到期前 30 天在发布日历中提醒续期（否则新版本签名失效，用户会看到"未知发布者"）。

### 4.2 签名对象与时序（关键：先签名、后算哈希）

```
build → assemble exe/zip → sign all .exe → verify → compute SHA-256 → SBOM → publish
```

| 对象 | 是否签名 | 说明 |
|---|---|---|
| `LMCL.exe`（stub + jar 拼接后的**最终文件**） | ✅ | **不能签 stub 再拼接**：Authenticode 覆盖整个文件，追加 jar 会使签名失效 |
| `lmcl-memopt-guardian.exe`（full 变体） | ✅ | 与主程序**同一证书**，降低杀软对"未知二进制的系统 API 调用"的敏感度 |
| `.jar` | ❌ | jar 内签名是另一套机制（jarsigner），上游自校验已不用我们的 key；不做 |
| `.zip` | ❌ | zip 本身无 Authenticode；内部 exe 已签，另附 `SHA256SUMS.txt` |
| `.sh` / `.deb` | ❌（首发） | Linux 侧不做签名；发布页给哈希 |

### 4.3 CI 签名实现（ubuntu runner，`osslsigncode`）

`02` 选型是单 ubuntu runner（省分钟数）。签名用 `osslsigncode`（支持 PKCS#12 + RFC3161 时间戳），避免额外 Windows runner：

```bash
# Secrets: SIGNING_PFX_BASE64, SIGNING_PFX_PASSWORD；可选 SIGNING_TIMESTAMP_URL
echo "$SIGNING_PFX_BASE64" | base64 -d > /tmp/cert.pfx

osslsigncode sign \
  -pkcs12 /tmp/cert.pfx -pass "$SIGNING_PFX_PASSWORD" \
  -n "LMCL" -i "https://<product-site>/" \
  -ts "${SIGNING_TIMESTAMP_URL:-http://timestamp.digicert.com}" \
  -h sha256 \
  -in  dist/LMCL.exe \
  -out dist/LMCL.signed.exe
mv dist/LMCL.signed.exe dist/LMCL.exe

# 校验（同时验证时间戳有效）
osslsigncode verify -in dist/LMCL.exe
```

- `full` 变体对 guardian 执行同样的命令；
- Windows 本地/发布机可用 `signtool sign /fd SHA256 /tr <ts> /td SHA256 /f cert.pfx /p <pwd> <exe>` 复核；
- 签名后**必须重新计算** SHA-256（签名改变字节）；
- 时间戳服务不可用 → 重试 3 次；仍失败则**中止发布**（无时间戳的签名在证书过期后失效）。

### 4.4 发布页展示

- Release note 附：证书主题、指纹（SHA-1/SHA-256）、有效期；
- 提供 `SHA256SUMS.txt` 与逐文件 `.sha256`（与上游 release 风格一致）；
- 用户校验说明：`certutil -hashfile <file> SHA256` / `sha256sum -c SHA256SUMS.txt`。

## 5. SBOM 与依赖清单

### 5.1 产出

`release/sbom-v3.16.1000.cdx.json`（CycloneDX 1.5 最小子集），字段：

```json
{
  "bomFormat": "CycloneDX",
  "specVersion": "1.5",
  "version": 1,
  "metadata": {
    "component": {"type": "application", "name": "<product>", "version": "3.16.1000"}
  },
  "components": [
    {"type": "library", "name": "jna", "version": "5.18.1", "licenses": [{"license": {"id": "LGPL-2.1-or-later"}}]},
    {"type": "library", "name": "javafx", "version": "<from libs.versions.toml>", "licenses": [{"license": {"id": "GPL-2.0-only WITH Classpath-exception-2.0"}}]},
    {"type": "application", "name": "lmcl-memopt-guardian", "version": "1.0.0", "licenses": [{"license": {"id": "GPL-3.0-only"}}]},
    {"type": "library", "name": "windows-sys", "version": "<from Cargo.lock>", "licenses": [{"license": {"id": "MIT"}}]}
  ]
}
```

### 5.2 生成方式（不引入新依赖）

```bash
# 1) Java 依赖：解析 Gradle 依赖树（输出到 stderr，正则提取 group:name:version）
./gradlew -q :HMCL:dependencies --configuration runtimeClasspath --no-daemon > build/deps.txt
# 2) Rust 依赖：Cargo.lock → (name, version, license)（cargo metadata --format-version 1）
cargo metadata --manifest-path tools/memopt-guardian/Cargo.toml --format-version 1 > build/cargo-meta.json
# 3) 汇总脚本 tools/release/gen-sbom.py（标准库实现，无第三方依赖）→ release/sbom-v<version>.cdx.json
```

- 许可证映射：`libs.versions.toml` 中每个依赖 + `Cargo.lock` 每个 crate 逐一登记；**GPLv3 不兼容的许可证必须为 0**（例如不允许把仅 GPLv2 的库链进 Java 产物）；
- SBOM 随 Release 发布；同时保留在仓库 `release/`，便于 diff。

### 5.3 上游依赖清单复核（首次发布的一次性工作）

- 运行 `./gradlew :HMCL:dependencies --configuration runtimeClasspath` 导出完整传递依赖；
- 对 JavaFX、JNA、Gson、OkHttp、log4j 等逐项确认许可证与再分发要求；
- 结果写入 `NOTICE.md` 的"第三方组件"节 + SBOM；**没有把握的项目不发**（可移除功能/降级）。

## 6. 发布流水线（与 02 对接）

### 6.1 版本号与 tag（替换 02 旧规则）

```bash
git tag v3.16.1000            # 社区编号从 1000 起，预留 0–999 给上游
git push origin v3.16.1000
```

| 项 | 规则 |
|---|---|
| `versionRoot` | 固定 `3.16`（随上游 release 线升级才改变） |
| `buildNumber` | 从 1000 起递增；一个小版本发布一个 tag |
| tag 名 | `v<version>`（**不再带 `-community.N`**；社区标识只出现在关于弹窗与发布页，避免污染版本解析/迁移比较） |
| 版本号来源 | CI 从 tag 取 `3.16.1000` → `-Pversion=`；`Metadata.VERSION` 继续由 `hmcl.version` 属性生成，不硬编码 |
| 上游合并 | 上游发布 `3.16.x` 后，我们不改 `versionRoot`；若上游改 `release/3.17`，按 [步骤 01](01-仓库建立与上游同步机制.md) 升级后再发 `3.17.1000` |

### 6.2 `build-release.yml` 阶段（在 02 的基础上改造）

| 阶段 | 动作 | 失败处理 |
|---|---|---|
| `gate` | tag 格式、`versionRoot` 一致性、`ci.yml` 最新绿、产品名已回填 | 中止 |
| `build` | JDK 17 + `jdk+fx`；`./gradlew build -Pversion=<v>`；构建 stub（20）；构建 guardian（17，x64/x86） | 中止 |
| `assemble` | `makeExecutables` 拼 exe；打 zip（含 JRE/legal/LICENSE/NOTICE/guardian）；压 `.sh`/`.deb`/`.jar` | 中止 |
| `verify-unsigned` | §3.4 的字符串/文件检查；两次构建哈希一致性 | 中止 |
| `sign` | `osslsigncode` 签主 exe + guardian；验证通过 | 中止 |
| `checksums` | 签名后算 SHA-256，生成 `*.sha256` 与 `SHA256SUMS.txt` | 中止 |
| `sbom` | §5 生成 SBOM，校验无 GPLv3 不兼容项 | 中止 |
| `release-dry-run` | 先发 GitHub **prerelease**，附完整资产 | 人工检查 |
| `promote` | 人工确认（`production` environment 审批）→ 转为正式 Release | 保留 prerelease 作回退 |

### 6.3 新增 Secrets（在 02 的 3.3 基础上）

| Secret | 必需性 | 说明 |
|---|---|---|
| `SIGNING_PFX_BASE64` | 首次签名起必需 | OV 证书（base64） |
| `SIGNING_PFX_PASSWORD` | 同上 | PFX 密码 |
| `SIGNING_TIMESTAMP_URL` | 否 | 默认 DigiCert 时间戳；可用 Sectigo 等 |

> 证书轮换：更换证书后旧版本签名仍可验证（时间戳有效），但**新版本必须用新证书重新签**；README/发布页的指纹同步更新。

```
          （EmptyWorkingSet）对"当前用户、未提权"进程做工作集整理；
          不联网、不注入、不杀进程、不写 HKLM、不创建服务。
权限说明：以普通用户权限运行，无需管理员权限。
安全设计：命名管道仅当前用户可连；调用方路径 + 祖先进程 + SHA-256 清单校验；
          固定 4 条命令、无任意 PID 操作；GPLv3 开源源码：<repo URL>
```

- **坦承技术行为**：隐瞒 `EmptyWorkingSet` 反而更容易被当作木马特征；
- 先签名再提交（提交的哈希必须与用户实际下载的一致）；
- 若渠道反馈"个人开发者/无组织验证不接受" → 记入结论，走 B 路线或仅发 safe。

### 7.3 预期管理与兜底

- 即使提交申诉，也可能**不被受理**；产品策略不依赖"白名单成功"；
- 兜底：默认推荐 safe 变体 + 下载页标注"full 变体可能触发杀软误报，请自行决定"；
- 社区反馈模板：要求用户提供杀软名称/版本/隔离文件哈希，不要求关闭杀软。

## 8. 灰度与回滚

### 8.1 灰度节奏

| 阶段 | 人群 | 观察期 | 通过的标志 |
|---|---|---|---|
| R0 内测 | 10–30 人（含低配/HDD/无杀软/有 360） | 1 周 | 无安装失败、无误报阻断、无启动回归 |
| R1 公测 | prerelease 公开，100–300 下载 | 1–2 周 | issue 无 P0/P1；崩溃率与主版本无差异 |
| R2 正式 | 全部用户；推荐链接指向 `safe`（full 单独入口） | 持续 | 无撤回触发条件 |

- 观察指标（**不做遥测**，只用可公开获取的信号）：下载量、issue 标签分布、崩溃报告里的版本分布、用户自愿反馈；
- 每个阶段结束写一段结论入 `docs/审查记录`（发/不发、为什么）。

### 8.2 撤回预案

| 触发 | 动作 | 执行人 |
|---|---|---|
| 多家杀软持续误报 | 推荐链接切 `safe`；发布公告；full 下架 | 发布负责人 |
| guardian 导致启动异常 | 主程序"能力探测失败即降级"已兜底；紧急发 `3.16.1001`（safe 默认） | 发布负责人 + 开发 |
| 安全漏洞（校验绕过/提权风险） | 立即下架 Release、停止分发 guardian、公告；修复合入后重发 | 安全负责人 |
| 数据目录/迁移事故（06） | 下架版本、发布回滚说明、提供手工恢复步骤 | 发布负责人 |
| 证书泄露/误用 | 联系 CA 吊销、换证书、重签并重发；公告旧版本签名失效 | 安全负责人 |

### 8.3 热修流程

```
main（或 release/3.16）→ 修复提交 → CI 绿 → tag v3.16.1001 → prerelease → 验证 → 正式
```

- 热修版本号递增（1000 → 1001），不改 `versionRoot`；
- 同一 tag 不重复推送（release 资产不可变）；紧急情况下先下架旧 Release 再发新 tag。

## 9. 用户文档与 FAQ（随包与站点）

| 文档 | 内容 |
|---|---|
| 快速开始 | 双击 exe / 解压 zip；首次启动选择 Java（或使用内置 JRE）；数据目录位置（06） |

| 快照回滚（16） | 成功启动后自动记录；回滚前自动备份；共享运行目录的影响警告 |

| 常见问题 | 为什么和 HMCL 长得像（基于 HMCL 修改）；能否与官方共存（可以，但不要同时打开同一游戏目录）；如何校验下载文件；GPLv3 源码在哪 |

FAQ 必须回答的"真相"问题：

| 问题 | 回答要点 |
|---|---|
| L2 真的释放内存吗？ | 只是把工作集页放到待机列表，**虚拟提交不变**；可用内存数字会变好看，不代表游戏一定更快 |
| 为什么不需要管理员权限？ | 只操作当前用户、未提权进程；这正是隐私与安全的边界，不是功能缺陷 |
| 会不会拖慢系统？ | 运行中不裁游戏进程、最小间隔 5 分钟；关闭后零影响 |
| 快照占空间吗？ | 硬链接为主，通常几十 MB；上限 2 GiB/作用域，可在界面清理 |
| 会覆盖我的存档吗？ | 快照**不含 `saves/`**；回滚只动 mods/config 等启动相关文件 |
| 更新怎么来？ | 首发不启用自更新；手动下载新版本（05） |
