## 1. 目标

1. 用户点"启动"后、游戏进程真正拉起前，用几秒钟跑一遍**只读**体检，把"为什么起不来"变成启动器直接给出的结论；
2. 体检结论可解释（现象 + 原因 + 建议），且用户永远可以"仍要启动"；
3. 任意检查项异常/超时都只降级为"未检查"，**不影响启动流程**；
4. 建立**唯一的启动钩子契约**（launch hook contract），让"启动前任务、进程创建、120 秒存活判定、退出事件"只有一处注入点；
5. 为 15/16/09 提供稳定 API，后续步骤只写 `community.*` 包，不再碰上游代码。

完成标志（DoD）：

- [ ] 五类检查全部可独立开关，默认全开；
- [ ] 检查项异常/超时 → 该项 `SKIPPED`，启动不受影响（注入异常单测覆盖）；
- [ ] 全程只读：不写实例目录、不联网（抓包 + 只读挂载验证）；
- [ ] 用户取消仅通过 `CancellationException` 静默退出，且启动遮罩正确关闭；
- [ ] 120 秒存活判定有单测（进程运行/提前退出/正常退出三态）且阈值可配置；
- [ ] `LauncherHelper` 的 diff 行数 ≤ 10 行，全部带 `// community:` 注释；
- [ ] 新增 i18n key 已同步四份 `assets/lang/I18N*.properties`（步骤 03 流程）。

## 3. 设计

### 3.1 启动钩子契约（本步骤交付的核心）

新增包 `org.jackhuang.hmcl.community.launch`：

```java
/// 启动事件：所有消费方只读、不得抛异常（钩子内部 catch 全部 Throwable 并记日志）。
public enum LaunchEventKind {
    REQUESTED,            // 用户点了启动（进程尚未创建）
    PREVIOUS_ABNORMAL,    // 上一次启动以 .abnormal 收尾（REQUESTED 时读到的快照）
    TASKS_COMPLETED,      // 启动前任务（体检/快照）结束，即将登录并拉起进程
    PROCESS_CREATED,      // ManagedProcess 已创建
    SURVIVED_THRESHOLD,   // 进程存活 >= 阈值（默认 120s）→ 判定"启动成功"
    EXITED_NORMAL,        // exitType == NORMAL
    EXITED_ABNORMAL,      // exitType != NORMAL（上游同时写 .abnormal + 弹崩溃窗）
    ABORTED_BY_USER       // 用户在体检/登录阶段取消
}

public record LaunchEvent(
        LaunchEventKind kind, String versionId, long timestamp,
        int exitCode, /* -1 表示不适用 */ ExitType exitType, /* null 表示不适用 */
        Duration alive, /* PROCESS_CREATED 之前为 null */
        String gameVersion) {}

public interface LaunchEventListener { void onLaunchEvent(LaunchEvent event); }

/// 启动前任务：在 checkGameState 之后、登录之前串行执行；返回 Task，失败仅记录不阻断。
public interface LaunchStartupTask {
    String id();
    int order();                                   // 100=体检，200=快照（16），300=预留
    Task<?> run(LaunchContext ctx) throws Exception;
}

public record LaunchContext(
        HMCLGameRepository repository, Version version, String versionId,
        JavaRuntime java, GameSettings.Effective setting,
        String gameVersion, boolean interactive /* scriptFile == null */) {}

public final class CommunityLaunchHooks {
    public static void registerStartupTask(LaunchStartupTask task);
    public static void addListener(LaunchEventListener listener);
    public static void removeListener(LaunchEventListener listener);   // 组件 dispose 时必须解绑
    public static void onLaunchRequested(HMCLGameRepository repository, String versionId);
    public static Task<Void> runStartupTasks(LaunchContext ctx);   // 串行、单项失败只记日志
    public static void onProcessCreated(String versionId, ManagedProcess process);
    public static void onProcessExit(String versionId, int exitCode, ExitType exitType);
    /// 16 的回滚前置检查用：该实例（或该运行目录作用域）是否有启动中/已拉起的会话。
    public static int activeSessionCount(String versionId);
    public static boolean isLaunching(String versionId);
}
```

**监听器与启动前任务的发现方式（15/16 依赖）**：`CommunityLaunchHooks` 类初始化时用 `ServiceLoader.load(LaunchEventListener.class)` 与 `ServiceLoader.load(LaunchStartupTask.class)` 各发现一次（模块内 `META-INF/services/org.jackhuang.hmcl.community.launch.LaunchEventListener` 等），再合并 `registerListener`/`registerStartupTask` 的运行时注册；**单个 provider 构造抛异常只记 WARN 并跳过**，不得影响启动。15 的 `PlayRecordTracker`、16 的 `SnapshotCaptureListener` 都走这个机制，避免在 08 里硬编码下游类名（防止 08 反向依赖 15/16）。

内部 `LaunchTracker`：

- `onLaunchRequested`：读 `.abnormal` 是否存在（**必须在 153 行之前调用**）、发 `REQUESTED` / `PREVIOUS_ABNORMAL`、记录 `requestedAt`；
- `onProcessCreated`：发 `PROCESS_CREATED`，用 `Schedulers.io()` 调度一个延迟任务，到期时若 `process.isRunning()` 为 `true` 发 `SURVIVED_THRESHOLD`（"启动成功"的唯一判据）；
- `onProcessExit`：发 `EXITED_NORMAL` / `EXITED_ABNORMAL`（`exitType == INTERRUPTED` 归为 `ABORTED_BY_USER`，不算崩溃），并针对"活过阈值但正常退出"补发一次成功事件（与 `SURVIVED_THRESHOLD` 去重）；
- 事件分发：`CopyOnWriteArrayList` + 每个 listener 独立 try/catch；**绝不在钩子里 `runLater` 阻塞上游线程**，需要 UI 的消费方自行切线程；
- 成功判据的语义（写进用户文档与 15/16 的实现约束）：
  - `存活 >= 120s` ⇒ 启动成功（即便之后正常关闭或崩溃）；
  - `存活 < 120s` 且 `exitType == NORMAL` ⇒ 用户主动秒退，**不算成功也不算崩溃**（"未知"）；
  - `存活 < 120s` 且 `exitType != NORMAL` ⇒ 失败/崩溃（09/16 的触发条件）；
  - `exitType == INTERRUPTED` ⇒ 用户从启动器停止，忽略。

### 3.3 体检任务的插入与交互协议

`runStartupTasks` 在后台线程串行执行 `order` 升序的任务；预检任务（order=100）内部：

```java
// 伪代码：交互式启动才弹窗
CompletableFuture<Boolean> decision = new CompletableFuture<>();
runInFX(() -> new PreflightDialog(report).show(decision::complete)); // true=继续启动
boolean go = decision.get(60, TimeUnit.SECONDS);                      // 超时视为继续
if (!go) throw new CancellationException("preflight aborted by user");
```

- 取消用 `CancellationException`：`LauncherHelper.java:299` 的 `if (ex != null && !(ex instanceof CancellationException))` 会静默跳过弹窗，`onStop` 关闭启动遮罩 → 体验正确；
- **非交互模式**（生成启动脚本，`scriptFile != null`）不弹窗，只把 WARN/ERROR 写日志；
- 打包在遮罩里的等待可能数十秒；`launchingStepsPane` 的上游阶段文案不变（不新增 stage，避免 i18n 侵入）。

### 3.4 五项检查（判定规则与降级）

| # | id | ERROR | WARN | SKIPPED 条件 |
|---|---|---|---|---|
| 1 | `java.compat` | 选中的 Java 不存在/不可执行；`java.major < GameJavaVersion.getMinimumJavaVersion(gameVersion).majorVersion()` | `java.major` 高于上游建议上限（上游无"上限"API 时只对已知不兼容组合提示） | 版本号无法解析 |
| 2 | `memory.budget` | `Xmx > totalMemory * 0.9` | `Xmx > totalMemory - 2GiB - 512MiB` | `totalMemory <= 0` |
| 3 | `disk.space` | 实例目录分区可用 < 500 MiB | 可用 < 2 GiB | `FileStore` 不可读 |
| 4 | `mods.duplicate` | —（只 WARN） | 同 modid 多版本；同文件名不同扩展名（`.jar`/`.jar.disabled`）提示冲突 | 无法读取 `mods/` 或 >500 个 jar（截断为"仅文件名启发式"） |
| 5 | `mods.missing_deps` | —（只 WARN） | 缺失 fabric `depends` / forge `mandatory=true` 的 modid（存在性检查，不做版本范围） | 元数据解析失败率高（>10% jar 无法识别）→ SKIPPED，宁可不说不可乱说 |

实现细节：

- `java.compat`：`setting.getJava(gameVersion, version)` 已在 `checkGameState` 内解析；预检只做"对照"，**不重新探测**。Java 主版本用 `java.getParsedVersion()`；
- `memory.budget`：`setting.getInheritable(GameSettings::maxMemoryProperty)` 可能为 `null`（表示自动，上游 `SUGGESTED_MEMORY`），null 时用建议值计算并标 OK 附实际值；物理内存取 `SystemInfo.getTotalMemorySize()`，阈值函数参数化；
- `disk.space`：`Files.getFileStore(repository.getBaseDirectory())`（**不写文件**）；对 `getBaseDirectory` 所在分区检查；
- `mods.duplicate`：扫描 `repository.getModsDirectory(versionId)`；解析优先复用 `ModManager`/`FabricModMetadata`/`ForgeNewModMetadata`，解析失败的 jar 不猜 modid；
- `mods.missing_deps`：只处理能识别的加载器元数据（fabric `depends`、forge/neoforge `mandatory=true`）；`minecraft`、`java`、`fabricloader`、`forge` 等内置 id 加入白名单；
- 全部检查在 `Schedulers.io()` 并发执行，单任务 800ms 软超时（`CompletableFuture.orTimeout`），总预算 3s；超时结果 `SKIPPED(reason=timeout)`；
- **结果缓存**：内存 LRU，key = `versionId + mods 目录文件列表哈希 + mtime`，TTL 10 分钟；不落盘。

```
⚠️ 模组重复：sodium（sodium-fabric-0.5.1.jar、sodium-fabric-0.5.3.jar）
⚠️ 缺少前置：fabric-api
[仍要启动]  [返回修复]  [不再提示本实例]
```

- 每条可复制文本（`Clipboard`）；
- "返回修复" → `CancellationException`；"不再提示本实例"需二次确认（`Controllers.confirm`），写入 `muted`；
- 文案全部走 i18n，key 清单见 §3.7。

## 5. 测试计划

| 用例 | 期望 |
|---|---|
| 正常启动 | 无弹窗；`REQUESTED→PROCESS_CREATED→SURVIVED_THRESHOLD(120s)` |
| 进程提前崩溃 | 无 `SURVIVED_THRESHOLD`；`EXITED_ABNORMAL`；`.abnormal` 存在；下次启动 `PREVIOUS_ABNORMAL` |
| 用户 3s 内正常关游戏 | `EXITED_NORMAL`、无成功事件、不算崩溃 |
| 用户点"返回修复" | 抛 `CancellationException`，无错误弹窗，遮罩关闭，游戏未启动 |
| 检查项抛 `RuntimeException` | 该项 `SKIPPED`，其他项正常，启动继续 |
| 磁盘检查超时 | `SKIPPED(timeout)`，总耗时 < 3s |
| 只读实例目录 | 预检可跑，无写入（`strace`/审计验证） |
| 断网 | 无网络请求；模组检查照常（本地元数据） |
| `community-settings.json` 非法 JSON | 使用默认值启动，写入备份 + warning |
| 生成启动脚本 | 不弹窗，脚本内容不受影响 |

## 7. 风险与应对

| 风险 | 等级 | 应对 |
|---|---|---|
| 误报让用户困惑（"明明能启动"） | **高** | 非确定性问题一律 WARN；文案用"可能"；"不再提示"按实例记忆 |
| 依赖解析误判（可选依赖成必需） | **高** | 一期只查 fabric `depends` + forge `mandatory=true`；解析失败>10% 整项 SKIPPED |
| 上游重构 `launch0`/`HMCLProcessListener` 导致钩子失效 | **高** | 4 个锚点写进同步 checklist（步骤 01 §上游同步）；集成测试覆盖"启动→存活→退出"全链 |
| 预检阻塞启动 3s+ | 中 | 并发 + 单项超时 + 内存缓存；默认总预算 3s，超预算即跳过剩余项 |
| 弹窗时机与"启动遮罩"冲突 | 中 | 在 `runStartupTasks`（登录前）弹窗，遮罩仍在；取消走 CancellationException |
| `.abnormal` 读取时机错误（被 153 行删掉） | **高** | `onLaunchRequested` 固定在 148 后调用；单测模拟"先写标记再启动" |
| `SURVIVED_THRESHOLD` 计时器在启动器退出后失效 | 低 | 计时器用守护线程；启动器退出时游戏进程是否存活由上游 `LauncherVisibility` 决定，事件丢失可接受（15 的统计以进程退出/日志双源补正） |
| 新增 i18n key 漏一份 properties | 中 | CI 的 `CheckTranslations` 必过；PR 模板加检查项 |
